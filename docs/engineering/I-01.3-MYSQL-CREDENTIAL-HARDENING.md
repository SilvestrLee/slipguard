# I-01.3 — Local MySQL Credential Hardening

**Commission:** `PO-I01.3-001` (Product Office → Engineering Office)
**Closes:** Condition 1 of `I-01.2`'s "Ready with Conditions" acceptance (weak local application password).

## What Changed

The local `slipguard` MySQL application account's password was rotated from a weak, dictionary-word value to a strong, unique, randomly generated 48-character hex credential (`random_bytes(24)`, generated locally, never written to any file this repository tracks).

## Account Topology — One Discrepancy From the Commission's Assumption, Disclosed

The commission's scope named two account variants to update: `slipguard@localhost` and `slipguard@127.0.0.1`. Verified directly against `mysql.user` (as was already independently confirmed during `I-01.2`): **only `slipguard@localhost` exists.** No separate `127.0.0.1` grantee was ever created, and the application has been connecting successfully via `DB_HOST=127.0.0.1` this entire time because MySQL resolves the loopback TCP connection back to the `localhost` account. Rather than fabricate a second account that was never part of the real, working configuration, only the one real account's password was rotated (`ALTER USER 'slipguard'@'localhost' IDENTIFIED BY '...'`). This matches the scope's own non-objectives (do not change the username, do not alter privileges) — it does not introduce a new grantee.

## Verification

- Old password confirmed rejected (`Access denied`) immediately after rotation.
- New password confirmed working via a direct `mysql` client connection.
- `.env` (ignored, untracked) updated — the only file touched with the real value.
- `php artisan config:clear` run; Laravel's live `DB::connection()` confirmed reconnected — `getDatabaseName()` → `slipguard`, `SELECT VERSION()` → `8.0.30`.
- `php artisan migrate:status`: all 23 migrations still `Ran`, 0 pending — no `migrate:fresh`, no schema change.
- `php artisan slipguard:demo` (no `--fresh`): "Demo workspace already populated — no changes made" — confirms the existing demo dataset survived the credential rotation untouched.
- Basic application requests (`/`, `/login`) both returned `200` against the new credential.

## Secret Handling

- The new password exists only in the local, gitignored `.env` and in the MySQL server's own credential store.
- Confirmed via `git grep` across the full tracked tree: the new value appears in zero tracked files.
- Not included in this document, any commit message, or any prior chat output after the value was generated — it was written directly to `.env` via a script argument and immediately discarded from the scratch file that briefly held it.
- `.env.example` was not touched (unchanged, already blank per `I-01.2`).

## Result

Condition 1 from `I-01.2`'s recommendation is closed. `I-01.2`'s other three conditions (`DecisionJournalTest` flakiness, incomplete Phase Seven runtime coverage, no dedicated performance pass) are unaffected by this commission and remain open.
