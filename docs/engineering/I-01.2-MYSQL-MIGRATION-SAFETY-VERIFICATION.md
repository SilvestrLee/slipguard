# I-01.2 — MySQL Migration Safety Verification

**Commission:** `PO-I01.2-001` (Product Office → Engineering Office)
**Question answered:** Can SlipGuard safely adopt MySQL using only the repository's migrations, seeders, configuration and documented setup process — reproduced from a completely fresh database, not the already-repaired local one?

## Environment Verified

| Item | Expected | Actual |
|---|---|---|
| MySQL | 8.0.30, `127.0.0.1:3306` | Confirmed — real `mysqld` process (`/usr/local/mysql/bin/mysqld`), listening on `*.3306` (verified via `netstat`, not just process presence), `SELECT VERSION()` returned `8.0.30` |
| PHP | working runtime, PDO/pdo_mysql/mysqli | `/usr/local/bin/php` 8.5.8, confirmed `PDO`, `pdo_mysql`, `mysqli` all loaded |
| Herd shim | broken, must not be silently used | Confirmed still broken: unqualified `php -v` fails with the same `dyld` `libc++` symbol error documented in `docs/engineering/static-analysis.md`. Every command in this verification used `/usr/local/bin/php` explicitly. |
| Laravel active connection | mysql / 127.0.0.1 / 3306 / slipguard / slipguard | Confirmed via `DB::connection()->getDatabaseName()` and `config()` dumps — all five values matched exactly, plus a live `SELECT version()` returning `8.0.30` |
| `.env` | ignored, no committed credentials | Confirmed (`git check-ignore -v .env`); repo-wide `DB_PASSWORD=`/credential grep found nothing real — every `root` match is legitimate prose, a Tailwind/filesystem `root` path, or Laravel's own standard `env('DB_USERNAME', 'root')` fallback default |

## Fresh MySQL Migration Result — Objective B

The existing `slipguard` database was **not** treated as sufficient proof, per the commission's own instruction — it had been repaired incrementally. A disposable database (`slipguard_mysql_verify`) was created via a root connection (credentials supplied directly by the founder in this conversation, used only in-memory for this verification, never written to any file, and the database was dropped again before this document was written).

```
php artisan migrate:fresh --seed -vvv
```

**Result: every one of the 23 migrations ran, in order, on the first attempt, all in a single batch.** No manual table drops, no orphan repair, no identifier-length error, no duplicate-table error, no foreign-key error. `migrate:status` afterward showed all 23 as `Ran`.

## Seeder and Demo Result — Objective C

```
php artisan slipguard:demo --fresh
```

Completed successfully against the disposable database: 30 betting slips (136 legs), 30 slip analyses (136 leg analyses), 12 journal entries, 18 Market Intelligence fixtures (108 quotes), one demo user (`is_demo = 1`). Re-running without `--fresh` correctly made no changes ("Demo workspace already populated") — idempotent as designed.

Planner sessions/selections/regeneration events seeded as 0 — this is `DemoWorkspaceSeeder`'s own **pre-existing, documented** first-slice scope decision ("Deliberately deferred, not silently dropped... Planner sessions/planning history"), not a MySQL-specific gap.

## Constraint Verification — Objective E

Verified real behaviour, not just schema/name inspection, via a bounded, self-cleaning script against the disposable database:

| Check | Result |
|---|---|
| Planner `(planner_session_id, sequence_number)` unique constraint | **PASS** — duplicate rejected by `planner_regen_session_sequence_unique` |
| Planner cascade delete | **PASS** — regeneration event removed automatically when its session was deleted |
| Market Intelligence quote → fixture foreign key | **PASS** — insert with a nonexistent fixture ID rejected by `mi_quotes_fixture_fk` |
| Market Intelligence cascade delete | **PASS** — quote removed automatically when its fixture was deleted |
| JSON round-trip | **PASS** — `outcomes` stored and read back as a real PHP array with correct values via Eloquent's cast |
| Invalid JSON rejected | **PASS** — a raw non-JSON string insert into the `json` column was rejected |
| Boolean casts | **PASS** — `is_demo`/`is_internal` store as MySQL `tinyint(1)` (confirmed via raw query) but read back as genuine PHP `true`/`false` through Eloquent |

This exact coverage is now a durable, repository-owned test file — `tests/Feature/MySqlIntegrationTest.php` — rather than a one-off script. It self-skips (`markTestSkipped`) under any non-MySQL connection, so it never runs as part of the default SQLite suite and was confirmed to do so (7 skipped, 0 run, under the default `.env`). Run explicitly against a real MySQL connection: `php artisan test tests/Feature/MySqlIntegrationTest.php` — verified 7/7 passing against the disposable database, both before and after a Pint reformat.

## Runtime Workflow Verification — Objective D

Run against the **real** `slipguard` MySQL database (not the disposable one), via a genuine headless-browser session (Playwright + the system's installed Chrome):

- Login, dashboard, logout — **pass**, no SQL exception text, no server errors, no console errors, real MySQL-backed session persistence.
- `/reports`, `/analyze`, `/history`, `/journal`, `/planner/history`, `/profile` — all load without SQL exceptions or 5xx responses.
- A complete, real, end-to-end cycle: created a new betting slip and leg, ran it through the actual `AnalyzeBettingSlip` action, then loaded its real `/analyze/{id}/report` page in the browser and confirmed the structural-risk section rendered correctly. This exercises the deterministic engine, persistence, and the Risk Report UI together against MySQL, not just a page load.

**Scope disclosed honestly**: this covered the highest-value real workflows (auth, dashboard, analysis end-to-end, report rendering, history/journal/planner/profile page loads) — it did not exhaustively walk every sub-item the commission listed (screenshot/PDF upload intake, Labs pages, Operations Console, Market Intelligence fixture browsing UI specifically). Those remain unverified in this pass; none showed any MySQL-related concern in the areas actually covered, and nothing about the areas not covered is MySQL-specific (they were already covered against SQLite in the standard suite).

## Automated Test Results — Objective F

- `tests/Feature/DesignSystemTest.php`: **19 passed, 174 assertions** — matches the commission's own expected baseline exactly.
- Filtered suite (`SlipguardDemoCommand|MarketIntelligence|Planner|PlanningHistory|Dashboard|DecisionJournal|BettingSlip`): 263/264 passed before `--stop-on-failure` halted on the one known `DecisionJournalTest` failure (see below).
- Full suite: **680/689 passed** (689 includes the 7 new, self-skipping MySQL integration tests). Failures observed:
  - Two `PublicPagesTest` logo-motion assertions — confirmed pre-existing and unrelated (tied to the separate, already-disclosed Static Product Mark work; identical signatures to every prior run this session).
  - **A flakiness finding, disclosed rather than glossed over**: `DecisionJournalTest`'s "archive groups by month" assertion failed in one full-suite run earlier in this investigation but **passed** in the final full-suite run reported above. Per the commission's own instruction not to auto-classify failures as unrelated without checking signature consistency — this one's presence is *not* consistent, which is itself the finding: it appears to be a pre-existing flaky test (order-dependent or timing-dependent), not a deterministic regression, and not something this commission introduced (it was already flagged as a known pre-existing issue across this whole session's prior runs, both with and without any MySQL-related change present). Recommend a separate, dedicated investigation — out of this commission's scope to fix.
- No new, consistent failure appeared anywhere as a result of the MySQL work.

## Security and Configuration Review — Objective/Phase 13

- `.env` gitignored; no `DB_PASSWORD=` or real credential found tracked anywhere in the repository (verified by direct grep, false positives from legitimate prose/paths excluded by inspection, not assumption).
- Application MySQL user (`slipguard`) is scoped to `GRANT ALL PRIVILEGES ON slipguard.*` only — confirmed via `SHOW GRANTS`, no global/`*.*` privilege. It cannot create or drop other databases (confirmed directly — its own attempt to create the disposable verification database failed until a genuine root connection was used).
- The application password is **not** the same string as the MySQL root password (confirmed directly — they differ) — no credential reuse.
- **Finding, disclosed not fixed** (per this commission's own "do not change production privilege architecture without explicit scope"): the local application password is a weak, dictionary-word value. Low real-world risk in this specific context (localhost-only, loopback-bound MySQL, single-developer machine), but should be strengthened before any staging/production use — flagged as a condition, not corrected here.
- `APP_ENV=local`, `APP_DEBUG=true` — appropriate for local; unchanged, no environment-specific correction needed here.
- No shell script in the repository references `DB_PASSWORD` or any credential.
- Demo credentials are fictional (`demo@slipguard.local`).
