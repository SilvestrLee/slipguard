## 1. Repository Readiness Report (summary)

The public site is in reasonable shape structurally (a real, working design token system; a real, if partially under-used, shared component library; real test coverage across navigation/theme/accessibility) but has two categories of real friction the Experience Blueprint will run into immediately: **CTA markup duplication** (§2) and **a stale production build** (§7). Neither blocks starting implementation; both should be fixed early rather than compounded by six more homepage sections repeating the same pattern.

## 2. Component Inventory

**Existing, reusable, already used publicly**: `<x-card>`, `<x-badge>`, `<x-alert>`, `<x-empty-state>`, `<x-metric-card>`, `<x-page-header>`, `<x-search-trigger-button>`, `<x-language-selector>`/`<x-language-modal>`, `<x-theme-toggle>`, `<x-command-palette>`, `<x-modal>`, `<x-public-nav>`, `<x-public-footer>`, `<x-device-frame>` (built this session, currently unused — dormant, see below).

**Components requiring extension**: none found that are structurally inadequate — the gap is adoption, not capability (§ below).

**Components requiring replacement**: none.

**A real, verified duplication finding**: `grep` across every `resources/views/pages/*.blade.php` file for `<x-primary-button>`/`<x-secondary-button>` usage returns **zero matches, everywhere**. Every marketing CTA on every public page — home, about, analyse, planner, reports — is a hand-written `<a>` tag repeating the same `inline-flex h-12/h-14 items-center justify-center rounded-md bg-gradient-button...` class string independently. `home.blade.php` alone has 3 such inline CTA blocks. This is real, load-bearing evidence for the Refactoring Assessment (§5): seven more homepage sections each adding their own CTA (per `U-20.3`'s "progressive CTA" plan) will each duplicate this same markup a further time unless fixed first.

**Missing shared components**: none required for the currently-reviewed `R-01.8`/`R-01.9`/`R-01.10` content specifically — everything they reference already exists. `R-01.10`'s Conflict Five (the multi-stage workspace reveal) would need a genuinely new pattern (a "callout" component) if it's ever built — not yet designed, correctly deferred per that document's own recommendation, not assumed to exist here.

## 3. Dependency Analysis

- **`home.blade.php` is 739 lines**, the largest public file by a wide margin (next largest, `public-nav.blade.php`, is 337). Adding `U-20.3`'s further sections directly into this file will make it harder to review/maintain — worth extracting each homepage chapter into its own partial/component before adding more, not after.
- **The Fixed Atmospheric Layer and Static Product Mark are both real, shared, already-centralized mechanisms** (CSS keyframes + a documented Alpine `x-data` pattern) — no duplication risk there; new sections can reuse them directly.
- **`resources/js/app.js` is minimal** (2.3KB built) — almost all interactivity is server-driven (Livewire/Volt) or plain Alpine inline in Blade, not custom JS. Low JS-coupling risk for new sections.
- **The device-mockup exception's supporting code (`x-device-frame`, `.device-float-a/b` CSS) is dormant** — built for the removed mobile section, unused but present, zero current coupling risk, ready to reuse if that section returns.

## 4. Technical Risks

| Risk | Category | Likelihood | Impact | Mitigation |
|---|---|---|---|---|
| CTA markup duplication compounds as more sections are added | Maintainability | High (already true today) | Medium — a copy/label change requires editing N places, easy to miss one | Extract a shared marketing-CTA component before `U-20.3` implementation begins, not after |
| `home.blade.php` grows past a reviewable size | Maintainability | High if sections are added inline | Medium | Extract each homepage chapter to its own partial as it's built |

| `R-01.10`'s deferred Conflict Five (multi-stage reveal) has no component yet | Implementation readiness | Certain if `U-20.3` is built as specified | Low if deferred as recommended, High if implemented ad hoc without going through the Gap Rule | Don't build it until it's actually designed — already the stated recommendation |

## 5. Refactoring Assessment (bounded to what the approved direction actually needs)

**One real, justified recommendation**: extract a shared public-marketing CTA component (wrapping the existing `bg-gradient-button`/border-outline treatments already defined in `COMPONENT_PRINCIPLES.md`'s Buttons section) before `U-20.3` implementation adds more sections. This isn't speculative — it's fixing something already duplicated five times, not preventing a hypothetical future duplication.

**Nothing else recommended.** No architectural perfection sought, matching §8's own instruction — the token system, component library, and motion primitives are all real and sufficient for the reviewed content.

## 6. Testing Readiness

Real, current counts, verified this pass: `HomepageTest` 15, `PublicPagesTest` 17, `GlobalShellTest` 30, `ThemeSystemTest` 6, `ThemeCompletionTest` 7, `DesignSystemTest` 19, `MobileNavigationDrawerTest` 3 — **97 tests** already covering navigation, theme switching, responsive drawer behaviour, and design-system consistency on the public site specifically. This is real, substantial coverage, not a gap.

**Recommended additional tests, once `U-20.3` is actually implemented**: one test per new homepage section confirming its content renders (matching the existing `HomepageMobileComingSoonTest` pattern already used and later removed alongside its section) and one confirming the extracted CTA component renders identically to what it replaces, before deleting the old markup.

## 7. Performance Baseline

**A real caveat before the numbers**: `public/build/manifest.json` is timestamped 09:11 today, before the language modal, several concurrent contributors' homepage edits, and other same-day changes. **This baseline is stale and should not be trusted for post-implementation comparison without rebuilding first.**

As currently built: `app.css` 105KB, `app.js` 2.3KB. Image handling already follows a sound pattern for the existing homepage dashboard preview (dual PNG/WebP, `loading="eager"` only for the one above-the-fold hero image) — the same convention should extend to any new section screenshots.

## 8. Summary Answers (per the commission's own acceptance criteria)

- **What already exists?** A real token system, a real (if under-used) component library, real motion primitives (Fixed Atmospheric Layer, Static Product Mark, the standard reveal/duration/easing system), 97 real tests across the public site.
- **What can be reused?** All of it, directly — nothing in `R-01.8`/`R-01.9`/`R-01.10` requires a new primitive beyond the one already-designed device-mockup exception and the one already-deferred callout pattern.
- **What must change?** One thing, concretely: extract the duplicated CTA markup into a shared component before adding more sections.
- **What technical risks exist?** Listed in §4 — none severe, none blocking, all named with a real mitigation.
- **What preparation should occur before implementation?** The CTA extraction (§5), a fresh build before treating the performance numbers as a real baseline (§7), and confirming `U-20.3` itself is actually resolved (still outstanding, per `R-01.10`'s own note) before section-specific work begins.
