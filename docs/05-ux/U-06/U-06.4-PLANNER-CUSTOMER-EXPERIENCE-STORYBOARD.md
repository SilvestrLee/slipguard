## 1. Executive Summary

This document is the complete customer-experience specification for the Planner — the first customer-visible design phase of Programme U-07, commissioned by `PO-U06.4-002` once the Planner's architecture (`ADR-008`, `ADR-009`), backend (`U-07.5`), and application services (`U-07.6`) were constitutionally accepted and closed.

It defines, within those already-settled boundaries: the end-to-end customer journey, every screen and state, the interaction and navigation model, the component and copy systems, and the accessibility/responsive specification — implementation-ready for Engineering without further product interpretation, with one narrow, explicitly scoped exception (§31).

**What this document does not do:** redesign the Planner's mathematics, lifecycle, revision model, or export behaviour. Every screen described here is a presentation of facts that already exist in the accepted backend (`PlannerSession`, `PlannerSelection`, `PlannerRegenerationEvent`) — nothing here requires a new column, a new state, or a new orchestration step.

## 4. Experience Principles

1. **The customer decides; SlipGuard explains.** Every screen answers "why" before showing a number, exactly as `EXPLAINABILITY_SYSTEM.md`'s Explanation Hierarchy already requires for the Risk Report — the Planner is the same philosophy applied across multiple revisions instead of one static report.
2. **A professional workspace, not a generator.** No screen ever presents a leg the customer didn't type themselves. The Planner's voice is descriptive ("this leg contributes the most structural risk"), never directive ("replace this leg," "you should stop here").
3. **Nothing is silently recalculated.** Every figure on screen traces to a specific, numbered Revision (`PlannerRegenerationEvent.sequence_number`) the customer can always identify.
4. **Two artifacts, never one ambiguous one.** The original slip and the Planner's working selection are visually and structurally distinct at every moment — the customer is never left wondering which one they're looking at (§24).
5. **Calm, not urgent.** No countdowns, no "act now," no artificial cycle ceilings shown before one is actually decided (DR-02).
6. **Reversible until export.** Confirming a selection (`Complete`) is not a point of no return — the customer can keep editing (`Complete → Evaluated` is an accepted transition, per `ADR-009`) right up until they choose to export.

## 5. Customer Journey Map

```text
Workspace (Ready slip exists)
        │
        │  "Plan this accumulator"
        ▼
Planner Session Opens (Draft → Evaluated, automatic first Revision)
        │
        ▼
Understand the Slip (Revision 1: overall score/band + every leg listed)
        │
        ▼
Primary Finding: Weakest Leg (named, ranked, explained)
        │
        ├──► Lock a leg (keep it — no new Revision)
        ├──► Unlock a leg (no new Revision)
        ├──► Remove a leg (→ new Revision)
        └──► Add a replacement leg the customer chooses (→ new Revision)
        │
        ▼
Compare Revisions (on demand — never auto-surfaced, §31)
        │
        ▼
Confirm This Selection ("Complete" — still editable after)
        │
        ▼
Export to a New Betting Slip (PD-009: original preserved, untouched)
        │
        ▼
Return to Workspace — original slip and new slip both visible, independent
```

Abandon is reachable from `Draft`, `Evaluated`, or `Complete` at any point (dashed exit not drawn above for clarity — see §16's Frame B-01) and never mutates the source slip.

## 7. Screen Inventory

1. **Workspace entry point** — existing Ready-slip card/detail, extended with a "Plan this accumulator" action.
2. **Planner Workspace** — the session's home screen: original-slip reference panel, current selection list, Primary Finding, action bar.
3. **Leg detail / edit panel** — inline expansion for lock, unlock, remove, add-replacement.
4. **Compare Revisions view** — side-by-side or stacked comparison of any two Revisions.
5. **Confirmation panel** — the "Complete" moment.
6. **Export screen** — the "Exported" moment and its two-artifact confirmation.
7. **Abandon confirmation** — a lightweight modal, reachable from every non-terminal state.
8. **Empty/loading/error states** — six Planner-specific states (§25), layered onto the screens above rather than separate pages.

No screen here is net-new outside this inventory — no dashboard, settings, or navigation redesign is introduced.

## 8. Navigation Flow

- The Planner Workspace is a **single persistent screen** for the life of a session — locking, unlocking, removing, adding, and comparing all happen in place (expand/collapse, per `MOTION_SYSTEM.md`'s existing pattern), never a multi-page wizard. This matches `COMPONENT_PRINCIPLES.md`'s Reports component precedent (in-place reveal, not a new page per state).
- Confirmation and Export are two distinct, sequential in-place panels reached from the same screen — never separate routes — because `Complete → Evaluated` must remain a one-click "keep editing" action, not a browser-back.
- Abandon is available from a persistent, secondary (never primary-styled) action in the same action bar at every non-terminal stage — reachable in one click from anywhere in the session, per Interaction Principle "clear recovery path."
- On export, the customer is returned to the Workspace entry point (§7.1), where both the original and the newly exported slip now appear as independent cards.

## 9. Entry Experience

### Frame E-01 — Ready Slip, Planner Offered
**Purpose:** establish that the Planner is an alternative path available on any slip the customer has already fully entered and confirmed as `Ready`, exactly matching `DR-03`'s resolution (`PD-007`) — no separate candidate-entry screen exists.
**Content:** the existing Ready-slip card/detail (Workspace or builder-confirmation screen) gains a second action, "Plan this accumulator," positioned beside the existing "Analyse" action — equal visual weight, neither framed as more prominent than the other (the customer chooses which path fits their intent).
**Customer question:** "Now that my slip is ready, what can I do with it?"
**Confidence established immediately by:** a one-line sub-caption under the new action — "SlipGuard will show you which selection carries the most structural risk, and let you try alternatives you choose yourself" — sets expectation before the click, consistent with `TRUST_SIGNALS.md`'s "never decorative" rule.

### Frame E-02 — Session Opening
**Purpose:** bridge the click to the first Revision without a dead moment.
**Content:** a brief in-place loading state (§25.1) while `StartPlannerSession`/`EvaluatePlannerSession` run — sub-millisecond per E-06D.1's benchmark, so this is a transition, not a wait state requiring a progress bar; a simple inline spinner per `MOTION_SYSTEM.md`'s Loading Behaviour is sufficient.
**Customer question:** "Is something happening?"

## 10. Original Slip & Lock Presentation

### Frame L-01 — Original Slip Reference Panel
**Purpose:** make `PD-008`'s guarantee visible, not just true in the database.
**Content:** a compact, always-visible panel (collapsed by default, expandable) showing the original slip exactly as submitted — every leg, unmodified — labelled **"Your original slip"** with a persistent lock icon (`ICONOGRAPHY.md`-approved metaphor, not a novel glyph) and the statement: *"This slip stays exactly as you entered it. SlipGuard never changes it — you're working on a separate copy below."*
**Customer question:** "Wait — is SlipGuard changing what I already entered?"
**Trust mechanism invoked:** this is the Planner's own addition to `TRUST_SIGNALS.md`'s mechanism list — stated once here, reused verbatim rather than reworded per screen.

### Frame L-02 — Lock Explanation (on attempted direct edit)
**Purpose:** handle the one place `PD-008`'s hard lock becomes customer-visible as friction — if the customer navigates back to the builder for this same slip while a session is open.
**Content:** the builder's own edit action, when blocked by `BettingSlipLockedByPlannerException`, shows: *"This slip is currently part of an open planning session. Finish or abandon that session to edit it directly."* with a direct link back into the open session (never a dead end).
**Customer question:** "Why can't I edit my own slip right now?"

## 11. Evaluation & Primary Finding

Follows `EXPLAINABILITY_SYSTEM.md`'s Explanation Hierarchy exactly, with the Planner's Primary Finding populated by the now-implemented weakest-leg ranking (the Future Compatibility note that document already reserved for E-06D):

```text
Overall Structural Risk  →  Primary Finding  →  Top Contributing Factors  →  Supporting Details  →  Data Quality  →  Rule Set Information  →  Analysis Metadata
```

### Frame P-01 — Overall Structural Risk (this Revision)
**Purpose:** orient the customer to the current selection's overall standing before naming any single leg.
**Content:** Structural Score and Risk Band for the *current* Revision, labelled with its Revision number ("Revision 1"); identical band colour/copy system as the existing Risk Report (`DESIGN_TOKENS.md`'s risk-band tokens, `EXPLAINABILITY_SYSTEM.md`'s Language Rules) — no new risk-communication pattern invented for the Planner.
**Customer question:** "How structurally risky is my current selection?"

### Frame P-02 — Primary Finding: Weakest Leg
**Purpose:** name the single leg the MSC ranking identifies as rank 1 (the largest structural contributor), educating rather than criticising.
**Content:** the leg's own detail (event, market, selection, odds) with one plain sentence: *"This selection currently contributes the most to your slip's structural risk"* — never "worst," "wrong," or "bad." Directly beneath it, the two facts the ranking already computes: what would change if this leg were removed (`scoreWithoutLeg`/`bandWithoutLeg`) and which reason codes would appear or disappear (`reasonCodesGainedWithoutLeg`/`reasonCodesLostWithoutLeg`), rendered as one or two plain sentences, e.g. *"Without this selection, the slip's band would move from High to Moderate."*
**Customer question:** "Which selection matters most, and why?"
**Prohibited interpretation:** never implies the customer *should* remove it — stated as a fact about structure, not an instruction (per `PD-007`/Experience Principle 2).

### Frame P-03 — Top Contributing Factors (Other Legs, Ranked)
**Purpose:** show where every other leg stands, not just the single weakest one.
**Content:** the full ranked list (rank 2..N), each leg showing its own MSC value in relative terms only ("contributes less than [weakest leg]"), never a raw `mscPrecise` decimal in the default view (progressive disclosure, below).
**Customer question:** "What about my other selections?"

### Frame P-04 — Supporting Details (expand per leg)
**Content, hidden until expanded** (mirrors `EXPLAINABILITY_SYSTEM.md`'s Progressive Disclosure exactly): the precise `mscPrecise` value, market complexity classification, gate-dependency flag if applicable, and the full reason-code lists — same "collapsed by default, in-place reveal" pattern as the Risk Report, no new disclosure mechanism.

### Frame P-05 — Data Quality, Rule Set Information, Analysis Metadata
**Content:** identical in kind to the existing Risk Report's own Frames F-05/F-07 (`U-03.2`) — data quality band, rule-set/engine/taxonomy/input-schema versions, this Revision's timestamp — reused, not redesigned, per Trust Signals' "never invented ad hoc per screen."

## 12. Revision Workflow (Lock / Unlock / Remove / Add)

### Frame R-01 — Lock a Leg
**Purpose:** let the customer mark a leg as "keep this, don't touch it" without triggering a new evaluation (`ToggleSelectionLock` deliberately does not re-evaluate, per `U-07.5`'s implementation — the math doesn't depend on lock state).
**Content:** a per-leg toggle labelled **"Keep this selection"** (never the bare word "Lock" as a customer-facing verb — see §21's Copy Guardrail on this exact word) with a small persistent indicator once active.
**Customer question:** "Can I protect a selection I'm confident about while I look at changing others?"
**No new Revision is created** — the screen must not show a Revision-count change or any loading state on this action.

### Frame R-02 — Remove a Leg
**Purpose:** remove a selection from the working set.
**Content:** a "Remove" action per unlocked leg; on confirmation, `RemovePlannerSelection` runs and a **new Revision** is produced automatically — the screen transitions directly to the updated Primary Finding (Frame P-02) for the new Revision, with a one-line transition statement: *"Revision 2 — updated after removing [selection name]."*
**Customer question:** "What happens to my results if I take this out?"

### Frame R-03 — Add a Replacement Leg
**Purpose:** let the customer type in a different selection of their own choosing — never a system suggestion (`PD-007`).
**Content:** the **same leg-entry form already used in the E-03 slip builder** (`BettingSlipValidationRules::legRules()`, reused not re-derived) — sport, competition, event, market, selection, odds. No "suggested alternatives" list, no autocomplete pulling from any odds/fixture source (Capability B is out of scope; no such data source exists). On save, a new Revision is produced exactly as in R-02.
**Customer question:** "How do I try something different?"

### Frame R-04 — Invalid Entry
**Content:** identical validation-error presentation to the existing slip builder (`Illuminate\Validation\ValidationException` surfaced the same way) — no new error-styling pattern for the Planner specifically.

## 13. Compare Revisions

### Frame C-01 — Compare Entry Point
**Purpose:** let the customer answer "what changed / what improved / what stayed the same" **only when they ask** — this view is never auto-opened, never summarized on the main Planner Workspace screen, and never accompanied by evaluative language (§31 — this is the deliberate boundary that keeps the baseline design inside DR-01 Option 1).
**Content:** a secondary action, **"Compare revisions,"** available once at least two Revisions exist.
**Customer question:** "How do I see what's changed since I started?"

### Frame C-02 — Comparison View
**Purpose:** present two Revisions side by side (or stacked on mobile, §26) with no ranking of "better" beyond the plain, already-existing risk band scale itself.
**Content:** for each of the two selected Revisions: Revision number and timestamp, Structural Score and Band, the full leg list with additions/removals visually marked (added/removed badges, not colour alone — `ACCESSIBILITY.md`'s Colour Independence), and each Revision's own Primary Finding. A neutral factual statement only, e.g. *"Revision 3's overall band is Moderate; Revision 1's was High"* — stating the fact, never "you improved" or "this is better."
**Customer question:** "What's actually different between these two?"
**Constitutional note:** this is the exact scope described as safe in `U-07.2` DR-01 (Option 2's "neutral factual trend display" is what this Frame already resembles) but this Frame is **customer-pulled, not system-pushed** — it never appears unless the customer opens it — which keeps it inside Option 1 without needing DR-01 resolved first (§31 explains this distinction in full).

### Frame C-03 — Return to an Earlier Revision
**Purpose:** `PD-008`'s "adopt a non-latest revision" question, left open at product-decision level for Engineering to confirm the exact mechanism (`U-07.2` DR-05 resolution note). This document specifies the **customer-facing behaviour** only, not the mechanism: from the Compare view, an earlier Revision can be selected as **"the current working selection"** — presented identically regardless of whether Engineering implements this as a fresh customer re-entry of that Revision's legs or a dedicated one-click restore, since both produce the same visible result (a new Revision matching the chosen one's legs).
**Customer question:** "I liked an earlier version better — can I go back to it?"

## 14. Confirmation ("Complete")

### Frame A-01 — Confirm This Selection
**Purpose:** the moment the handover calls "Approval" — internally `Evaluated → Complete` (`PO-U07.6-CL-001`: no new state, business language only).
**Content:** a clearly primary action, **"Confirm this selection,"** shown against the current Revision's full detail (so the customer confirms a specific, visible thing, never an abstract "finish" click). Directly beside it, a statement making authorship explicit: *"You're confirming this exact combination of selections. Nothing is placed or submitted anywhere yet."*
**Customer question:** "Am I sure this is what I want, and do I understand I'm the one deciding?"
**Ownership design requirement satisfied:** the copy explicitly states the customer is deciding, not SlipGuard approving — directly answering the handover's "the customer should clearly recognise they — not SlipGuard — are making the final decision."

### Frame A-02 — After Confirming (Still Editable)
**Purpose:** correct a natural but wrong assumption that confirming is final.
**Content:** once `Complete`, the screen keeps every lock/unlock/remove/add action visible (not hidden or disabled) with a small persistent note: *"You can keep changing your selections — confirming again will update this."* Any further edit runs `Complete → Evaluated` transparently, identical in presentation to Frame R-02/R-03's transition.
**Customer question:** "Did confirming lock me out of making further changes?"

## 15. Export

### Frame X-01 — Export This Selection
**Purpose:** the final action, available only once `Complete` (`ExportPlannerSession` throws `InvalidPlannerSessionTransitionException` otherwise — the UI must never present this action before that state).
**Content:** action labelled **"Create a betting slip from this selection."** Directly beside it, the three PD-009 facts stated plainly and in this order: *"Your original slip stays exactly as you entered it — it isn't changed."* / *"This selection becomes a brand new betting slip."* / *"Every revision you tried is kept in this session's history — nothing is deleted."*
**Customer question:** "What exactly happens to my slips when I do this?"

### Frame X-02 — Export Complete
**Purpose:** confirm the outcome as two independent, equally real artifacts — never framed as one slip "replacing" or "updating" the other.
**Content:** two cards, visually equal weight, both linking onward: **"Your original slip"** (unchanged, still `Ready`, still analysable on its own) and **"Your new slip"** (the exported result, also `Ready`, independently analysable). No "old vs. new" hierarchy implied by size, colour, or ordering beyond original-first (chronological, not evaluative).
**Customer question:** "Where did everything end up?"

## 16. Abandon

### Frame B-01 — Abandon Confirmation
**Purpose:** a low-friction exit that never implies loss, since nothing about the original slip was ever at risk (`AbandonPlannerSession` never touches the source slip).
**Content:** a lightweight confirmation modal: *"Abandon this planning session? Your original slip is completely unaffected either way."* — stated even before the customer asks, since this is a factual reassurance about the *original slip specifically*, not proactive guidance about whether they *should* abandon (that distinction is exactly why this is compatible with DR-01 Option 1 — see §31).
**Customer question:** "If I leave now, do I lose anything?"

## 21. Copy Guardrails (Planner-Specific Addendum to `TRUST_SIGNALS.md`)

- **The word "Lock" is never shown to the customer as a verb or claim.** `PlannerSelectionLockState` is an internal/engineering name only. Customer-facing copy always uses **"Keep this selection"** / **"selection kept"** instead. This is a deliberate disambiguation, not an oversight: `TRUST_SIGNALS.md`'s Forbidden Language list already bans "Lock" as a betting-marketing claim (implying a guaranteed win) — the Planner's own per-leg lock *feature* must never be surfaced under the same word, to avoid any reading, however unintended, that a "locked" leg is being described as a safe or guaranteed one.
- No leg is ever called "weak," "bad," or "wrong" — only "contributes the most/least to structural risk," per Experience Principle 2 and `EXPLAINABILITY_SYSTEM.md`'s existing "Structurally elevated," never "Dangerous," pattern.
- No Revision comparison ever uses "better," "improved," or "worse" as an evaluative verdict — only the risk band's own already-approved labels, stated as fact (§13 C-02).
- No cycle-count copy implies a limit, a warning, or an approaching ceiling — a bare "Revision {n}," nothing else, until DR-02 is resolved (§31).
- No confirmation or export copy uses `Guaranteed`, `Winning strategy`, `Safe bet`, `Sure odds`, or any other entry on `TRUST_SIGNALS.md`'s Forbidden Language list — verified against that list line by line while drafting §20.

## 30. UX Rationale

- **Why a single persistent screen instead of a multi-step wizard (§8):** the customer's actual task (lock/remove/add, repeated an arbitrary number of times, §12) is inherently non-linear — a wizard would force an artificial forward-only structure onto a task the architecture itself (`U-07.1` §5's self-looping `Evaluated` state) already models as iterative.
- **Why Compare is customer-pulled, never auto-surfaced (§13, §31):** this is the single design choice that keeps the entire document buildable today without waiting on DR-01 — every other requested capability (understanding, confidence, control) is achievable through facts the customer explicitly requests, never through the Planner initiating commentary.
- **Why "Keep this selection" replaces "Lock" in customer-facing copy (§21):** `TRUST_SIGNALS.md`'s Forbidden Language already reserves "Lock" as a marketing term implying guaranteed outcome; reusing the internal engineering name verbatim in the UI risked exactly the kind of unintentional dual meaning that document exists to prevent.
- **Why the Primary Finding never says "remove this" (§11 P-02):** `PD-007` draws a hard line at the Planner ever choosing on the customer's behalf — an instruction, however softly worded, would cross from explanation into suggestion.
- **Why Confirm remains editable (§14 A-02):** the accepted lifecycle itself allows `Complete → Evaluated` (`ADR-009`); hiding further-edit affordances after confirming would contradict behaviour Engineering has already built and tested, not merely a design preference.
- **Why the Export screen shows two equal-weight cards, not one updated card (§15 X-02):** `PD-009`'s entire rationale (recorded in `DECISION_LOG.md`) is that customers must be able to distinguish original intent from Planner-guided outcome — a hierarchy implying one slip "replaced" the other would undo that rationale visually even though the data model gets it right.

## 31. Constitutional Gap Register — DR-01, DR-02, DR-04

This is the one section the handover's Repository Consistency instinct (echoing `PO-U07.5-AC-001`/`PO-U07.6-AC-001`'s pattern) requires stating precisely rather than glossing over.

**DR-01 (Messaging Philosophy) — genuinely gates a narrow slice, not the whole document.** What is gated: any copy where the Planner itself would proactively assert something evaluative about completion ("no further improvement found," Option 3) or abandonment ("this accumulator has remained Very High risk," Option 4), unprompted by the customer. **What is not gated, and is fully specified above:** every fact-on-request screen in this document (§11 Primary Finding, §13 Compare, §14 Confirm, §15 Export) — none of these are proactive; all are either the direct result of a customer action or a response to a customer's explicit request to view something. If DR-01 resolves to Option 1 (no proactive messaging, this document's baseline), **nothing changes.** If it resolves to Option 2 (neutral trend), the only addition is an optional, still-neutral trend indicator Product Office may choose to surface passively on the main Planner Workspace screen (not specified here, since it doesn't exist yet as a decision) — no restructuring of any Frame in this document. If it resolves to Option 3 or 4 (directive guidance), that is new copy requiring its own Compliance-reviewed wording (per DR-01's own Product Implications), added as new statements alongside the existing Frames, not a redesign of them.

**DR-02 (Regeneration Cycle Limit) — fully non-blocking.** This document shows "Revision {n}" with no ceiling anywhere. If a cap is chosen later, Engineering adds one warning string at the moment the cap is reached (per DR-02's own Explainability requirement, "hitting it must be explained in plain language") — no screen in this document requires modification to accommodate that string.

**DR-04 (Session Retention) — confirmed non-blocking by its own register entry**, and treated as such throughout this document (§3, §7.1); no design decision here depends on its resolution.
