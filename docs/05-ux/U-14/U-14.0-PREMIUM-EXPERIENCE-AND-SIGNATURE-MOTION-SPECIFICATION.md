## 1. Constitutional Conflict Found Before Drafting — Not Silently Resolved

**§8's Signature Motion Language directly contradicts `MOTION_SYSTEM.md`'s existing, Locked "Logo Rotation" rule**, verified directly, not assumed:

> "The logo does not rotate, spin, or animate as a decorative flourish. The only permitted logo motion is a subtle opacity fade on page load (200ms)... the logo is a mark of trust, not a mascot." — `MOTION_SYSTEM.md`, unchanged since U-01.

§8 asks for a scroll-linked deterministic rotation of "the inner intelligence element" as "the platform's signature interaction." This is not a minor overlap — it is the literal thing the existing rule was written to forbid.

**This is not treated as an oversight to silently work around either way.** §8's own specification is detailed, deliberate, and internally consistent (explicit forbidden list — infinite rotation, bounce, elastic easing, spring physics, decorative motion, hero-only gimmicks — that itself reads as an *extension* of `MOTION_SYSTEM.md`'s existing restraint philosophy, not a rejection of it). Per this repository's own precedent for exactly this situation (`U-12.0`'s gradient system amendment, where a similarly detailed and deliberate Product Office specification superseded a prior "no gradients" rule and was recorded as an explicit constitutional amendment rather than silently built around), **§2 below proposes amending `MOTION_SYSTEM.md`'s Logo Rotation section to permit this one, narrowly-specified exception — not yet applied to that document, since this is UX Studio's proposal, not a self-granted approval.** Product Office acceptance of this specification is what would actually amend `MOTION_SYSTEM.md`; until then, the rule stands as written and no implementation may proceed.

## 2. Proposed Signature Motion Language (pending acceptance)

**Element:** the logo mark's inner glyph only (not the wordmark, not the whole lockup) — matching the existing brand asset's own composition (`brand/slipguard-logo-light-transparent.svg`).

**Behaviour, fully deterministic — tied to scroll position, never to elapsed time:**

| State | Behaviour |
|---|---|
| Initial (top of page) | Perfectly still. No motion, no timer, no auto-play. |
| Scrolling down | Rotation angle is a direct, linear function of scroll position within a fixed range (e.g. 0–24° across the first 100vh of scroll, then holds) — never open-ended, never continuous/infinite. |
| Scroll stops | No further motion — the rotation is scrub-driven, not time-driven, so "stopping" simply means the angle stops changing. Nothing eases on its own after scroll stops, since there is no independent animation to ease. |
| Return to top | Rotation angle returns to 0 by the same linear function, run in reverse — an inherent property of scroll-linked (scrubbed) motion, not a separate reset animation. |

**Technical constraints:**
- `transform: rotate()` only — no `width`/`height`/`margin`/layout-affecting properties (GPU-accelerated, compositor-only, confirmed against UI UX Pro Max's own Scroll Reveal/Parallax guidance, consulted for this specification — see §5).
- Driven by a scroll-position listener (`passive: true`, matching the existing header-condense pattern already in `<x-public-nav>`), not a scroll-triggered *timed* animation library — this is what makes it genuinely scrub-driven/deterministic rather than a "play once" reveal.
- `prefers-reduced-motion: reduce` disables the rotation entirely (logo stays static at 0°), consistent with `app.css`'s existing global reduced-motion block.
- Present only in `<x-public-nav>` (the public site's own header), not the authenticated in-app navigation — the commission's own framing ("the platform's signature interaction," discussed throughout in the context of public pages/homepage) supports this scope; extending it to the authenticated header is not addressed here and would need its own decision.

**Forbidden, restated from the commission's own list and cross-checked as already consistent with `MOTION_SYSTEM.md`'s existing philosophy:** infinite/continuous rotation, bounce, elastic easing, spring physics, decorative motion unrelated to scroll position, hero-only gimmicks (a signature element should be consistent site-wide, not a one-page trick).

## 3. Premium Visual Rhythm — Audit and Recommendations

Reviewed every public page (`U-13.0`'s delivery) against the commission's rhythm criteria. Finding: the underlying tokens already support the request (`container-marketing`, `gradient-hero`, the `space-*` scale, `elevation-1/2`) — this is a **section-composition** gap, not a missing-token gap.

- **Section spacing is already consistent** (`py-16 sm:py-20`/`py-20` throughout every public page) — no change recommended; inconsistent spacing was not found.
- **Every public page hero currently follows an identical template** (eyebrow label → h1 → supporting paragraph, centred) except Home's split two-column hero. Recommendation: this is *consistent*, which the commission's §13 explicitly still wants ("its own visual identity... while remaining part of one product") — not a defect, but there is room for **one deliberate point of difference per page** without breaking the shared language: e.g. Reports' hero could show a small, static preview fragment of the sample report card (reusing the existing risk-band badge styling) beside its heading, the way Home's hero already does at full size. This is a content-composition recommendation, not a new component.
- **CTA placement is consistent** (one primary CTA per page, at the end) — matches `COMPONENT_PRINCIPLES.md`'s Buttons rule ("exactly one primary... per screen") already.
- **Card density on `/analyse`'s factor grid** (5 cards in a 2-column grid) is the single densest moment on the public site. Recommendation: no change — 5 short, clearly-labelled cards is well within UI UX Pro Max's own "1-2 key animated elements, no excessive density" guidance (§5), and `VISUAL_INSPIRATION.md`'s dense-dashboard rejection is about *data* density (numbers, tables), not a handful of short explanatory cards.

## 4. Component Polish — Reviewed Against the Commission's Checklist (§17)

Buttons, forms, cards, navigation, alerts, dropdowns, modals, metrics, empty states: all already implemented via the shared primitives (`U-12.0`'s `x-card`/`x-badge`/`x-alert`/`x-empty-state`/`x-metric-card`, plus the pre-existing button/input/dropdown/modal components) with consistent hover/focus/loading treatment, confirmed by direct inspection, not assumed. **Two items on the commission's checklist have no current instance in this product and are not designed speculatively, per Just-in-Time Documentation**: tables (no tabular data view exists anywhere in the customer-facing product) and skeleton loaders (the product's existing loading-feedback pattern is a text status line, e.g. Slip Index's "Analysing your slip," which was a deliberate choice already reviewed under `U-12.0`, not an omission to fix here).

## 5. Specialist Design Capability Usage

**UI UX Pro Max** — queried three times. (1) "Premium restrained motion / scroll interaction" (`--domain gsap`): confirmed the Scroll Reveal "Subtle" tier (fade + 8–16px translate, no re-trigger on scroll-back) as already matching `MOTION_SYSTEM.md`'s existing rule almost exactly — a genuine cross-validation, not a new finding — and explicitly flagged "Complex" hover tiers (elastic easing, magnetic mouse-follow) as inappropriate, which independently confirms the commission's own §8 forbidden list. (2) "Logo/brand-mark motion" (`--domain ux`): no direct logo-rotation precedent found, but returned "animate 1–2 key elements per view maximum" — supports treating the logo as the site's *one* signature element rather than adding further motion elsewhere. (3) Informed the reduced-motion and compositor-only (`transform`/`opacity`) constraints in §2.

**21st.dev/Magic** — queried on "premium SaaS scroll-linked logo animation." Returned only partner/client "Logo Cloud" carousel components (an unrelated concept — showcasing *other companies'* logos, not a brand's own mark) and a "Motion Footer" component built on glassmorphism, magnetic buttons, aurora glow, and giant masked typography. **Nothing adopted** — the Logo Cloud results don't apply to a single-mark signature interaction at all, and the Motion Footer is exactly the decorative-excess pattern §8 and `VISUAL_INSPIRATION.md` both already reject. A consistent, expected negative result given every prior 21st.dev query this project has run.

## 8. Engineering-Ready Implementation Guidance (if §2 is accepted)

1. Amend `MOTION_SYSTEM.md`'s Logo Rotation section per §2's exact text before writing any code — the Gap Rule requires the document to change first.
2. Add a scroll-position listener to `<x-public-nav>` (same `passive: true` pattern already used for its condense behaviour), mapping scroll position to a bounded rotation angle applied via `transform: rotate()` on the logo glyph only.
3. Guard with `window.matchMedia('(prefers-reduced-motion: reduce)')`, matching the existing pattern in the homepage's Intelligence Section count-up animation.
4. No new Blade component required — this is a small addition to the existing `<x-public-nav>` markup/Alpine state, not a new pattern beyond the one being documented here.
5. Add a Feature test asserting the reduced-motion guard and the scroll-listener's presence, matching this repository's established testing discipline for motion (`tests/Feature/HomepageTest.php`'s existing pattern).
