Per the same constitutional boundary as `U-14.0` (`docs/offices/UX_STUDIO.md`: never writes application code; never introduces a new pattern without prior documentation and Product Office approval), this is a specification, not an implementation. Two parts of it are genuinely safe for Engineering to implement immediately once accepted (§1); two parts have real, verified conflicts that must be resolved by Product Office/Compliance before any code is written (§2, §3).

## 1. Navigation Simplification — No Conflict, Engineering-Ready As Specified

Removing "About" and "SlipGuard Labs" from primary navigation, leaving **Home, Analyse, Planner, Reports, Pricing** (+ Dashboard when authenticated), is a straightforward information-architecture change — no new component, interaction, or visual pattern involved (`<x-public-nav>`'s existing active-state loop already generalises to any list of items). Nothing here conflicts with any Locked document. **This part requires no Gap-Rule step — it is ready for direct Engineering implementation once Product Office accepts this specification as a whole.**

## 2. Footer Information Architecture — One Verified Conflict, Flagged Before Drafting

The commission's suggested "Community" column (Roadmap, Join Beta, Feature Requests, Research Updates) was checked against `docs/00-governance/DECISION_LOG.md`'s `SD-002` entry before being accepted into this specification, not assumed compatible. **"Feature Requests" is the literal thing `SD-002` explicitly defers**: *"Explicitly deferred, not approved for MVP: ...feature-request submission, community discussions, roadmap comments... forums..."* — the same entry that approved SlipGuard Labs' actual MVP scope as "feature awareness, roadmap status display, 'Notify Me,' and 'Join Beta' only." A "Community" column framed around discussion/requests is the same shape of thing, not merely one bad link inside an otherwise fine column.

**Resolution proposed in this specification, not self-granted**: drop the "Community" column entirely from the footer. Fold "Roadmap" and "Join Beta" into the **Company** column as links to the existing, already-accepted SlipGuard Labs page (which already presents exactly that content) rather than as separate, implied-to-be-new destinations. "Feature Requests" and "Research Updates" are not built into this specification at all — they would require their own `SD`-numbered scope expansion before any page (real or stub) references them, since a stub page named "Feature Requests" would itself misrepresent a capability `SD-002` deliberately excluded.

**Revised footer structure proposed:**

| Column | Links |
|---|---|
| Product | Analyse, Planner, Reports, Dashboard |
| Company | About, Pricing, SlipGuard Labs, Contact |
| Resources | Methodology (→ `/analyse`, not a duplicate page), Release Notes |
| Legal | Privacy, Terms |

**Decision Journal / Planning History**, named in the commission's Product column, are not customer acquisition or evaluation destinations — they are mid-journey authenticated screens with no public-facing content of their own (an unauthenticated visitor gains nothing from a footer link that immediately redirects to login for a screen they've never seen described anywhere). Not included in the footer, consistent with §3's own principle ("every destination represents a genuine workflow... no filler"). "Documentation," "FAQ," and "Supported Sports" are not included either — no real content exists for them yet, and per the same reasoning applied to Pricing/Privacy/Terms in `U-13.0`, a stub with no real content adds a link without adding value; these are left as a named, deferred opportunity (§5) rather than manufactured placeholders for their own sake.

## 3. SlipGuard Labs Ecosystem & Release Notes — Real Architecture Question, Not Resolved Here

Two things verified directly before drafting recommendations:

1. **`/labs` requires authentication today** (`routes/web.php`, inside the `auth` middleware group) — the commission's "public research, public transparency" framing (§12) is a genuine access-boundary change, not a visual one.
2. **`LabsFeatureInterest`'s `user_id` is required, not nullable** — "Notify Me"/"Join Beta" are built as per-authenticated-user toggles. Making Labs public without further work would either (a) show the page read-only to guests, with Notify Me/Join Beta prompting login (a normal, already-used pattern — Dashboard does the same today), or (b) require anonymous/email-based interest capture, which is new data collection outside `SD-002`'s accepted scope and adjacent to what it explicitly deferred ("email campaigns," "notification automation").

**This specification recommends (a)** — a public, read-only `/labs` teaser (feature list + status badges, no interest actions) with Notify Me/Join Beta visible but routing through login, exactly like Dashboard already does for guests — since it requires no new data model and no new `SD`-scope decision. **It does not decide this** — that determination belongs to Architecture Office (access-boundary design) and Compliance Office (per `docs/00-governance/DECISION_LOG.md`'s `U-10.2` precedent of reviewing exactly this kind of guest-data question), named as the next required step, not silently assumed.

**Release Notes** is recommended as a genuinely new, real, buildable page — it doesn't require inventing product capability, only documenting what has already shipped (this repository's own `CHANGELOG.md` is the authoritative source; a public Release Notes page would be a curated, customer-facing rendering of already-true history, not a new claim). Proposed structure, informed by the commission's own example: Version, Date, Area affected, Summary, Why it matters — engineering-register tone, not marketing language, matching the commission's own instruction. **Not built in this pass** — pending acceptance of the footer/Labs resolution above, since Release Notes' own footer placement (`Resources`, per §2) depends on it.

## 4. Specialist Design Capability Usage

**UI UX Pro Max** — queried on minimal navigation/footer IA and on B2B/trust-focused product patterns. Confirmed "Breadcrumbs: use for sites with 3+ levels of depth" as directly applicable *if* the Labs ecosystem (§3) is eventually built with nested sub-pages — flagged as a future recommendation for that specific case, not adopted now since no nested structure exists yet. The B2B/enterprise product-type match ("Trust & Authority + Minimal," professional blue + neutral grey) cross-validates the existing palette and restrained direction already in place — no change indicated.

**21st.dev/Magic** — queried on footer/release-notes composition. Five of six results were decorative SaaS footer templates (oversized wordmarks, glass-shader panels, animated sections) — rejected, same reasoning as every prior query this project has run. One result ("Orbit Footer" — a compact footer with inline "docs and status" developer links) informed a structural point, not a code adoption: it supports keeping the Resources column **lean** (a couple of real links) rather than manufacturing a full column of placeholder pages — consistent with §2's recommendation to drop unbuilt destinations rather than pad the footer with them.

## 5. Deferred, Named Explicitly (Not Silently Dropped)

Documentation, FAQ, Supported Sports, and a fuller SlipGuard Labs ecosystem (Experiments, Beta Programmes, Rule Set Updates, Feature Progress, Version History, Research Articles) are real, plausible future public-site content — none is built or stubbed in this pass, since doing so without real content would itself be the "decorative filler page" this commission's own §8 explicitly rejects.

## 6. Browser Verification

**Not performed.** No browser automation tool exists in this environment — unchanged, stated explicitly.
