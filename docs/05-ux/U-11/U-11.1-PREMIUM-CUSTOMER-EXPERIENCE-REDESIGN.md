## 0. How To Read This Document

Per `PO-U11.1-CL-001`: OddStorm is context only (specialist credibility, tool organisation, betting-domain fluency) — it does not influence density, visual identity, or business model. The existing Locked UX Constitution remains fully authoritative and **unamended**. This document does not redesign any deterministic mathematics, Planner logic, or governance — every recommendation below is presentation-layer only, and every proposed screen element is checked against what the repository actually persists (§3), per the handover's own §9.7 instruction.

## 1. Executive Summary

The platform's functional foundation is strong and current, confirmed directly rather than assumed. The most valuable finding of this audit is that **a meaningful share of the requested redesign already has an approved specification that was simply never built** — most notably the entire homepage (`HOMEPAGE_STORYBOARD.md`, sections 1–7), which today renders as a single hero and nothing else. Closing that gap is the single highest-leverage recommendation in this document, ahead of any new design work.

A second finding: two screens the commissioning handover (§7) describes as "Placeholder" are not — `SlipGuard Labs` and `Planning History` are both fully implemented, tested, working features (§3.2). What reads as sparse is either unpublished admin content (Labs) or genuinely low data volume for a new account (Planning History), not missing engineering.

## 4. Customer Journey (Updated)

```text
Landing (public)
   ↓
Register / Sign in
   ↓
Dashboard — "what's true right now"
   ↓
Analyze Slip — the working tool
   ↓
Report — understanding
   ↓
Journal — reflection
   ↓
Planner — improvement, if the customer chooses it
   ↓
History / Planning History — the accumulated record
   ↓
(returns to Dashboard, now richer)
```

This is the same shape `U-04.1`/`U-06.4` already established; this document's contribution is making the Dashboard (§8.2) the honest, real-data hub that closes the loop back to every other screen, which it currently does not do (§2, R-7).

## 5. Landing Page

### 5.1 What Already Exists, Unbuilt

`HOMEPAGE_STORYBOARD.md`'s seven sections (Hero → Problem → How SlipGuard Works → Example Report → Trust → Journal → CTA) are **Approved** and describe almost exactly what the commissioning handover asks for: evidence-first messaging (§4, "Example Report"), mechanism explanation (§3, "How SlipGuard Works"), differentiation from prediction products (§5, "Trust"). None of it required new UX Studio design work — it required implementation, which never happened. `welcome.blade.php` today is the Hero section alone.

**Primary recommendation: implement `HOMEPAGE_STORYBOARD.md` as already approved**, before any further landing-page design work is considered — this closes the majority of the "product depth" gap the handover names, at zero new design cost.

### 5.2 One Proposed Addition (Not a Redesign)

`HOMEPAGE_STORYBOARD.md` predates Programme U-07 — it has no Planner section. The commissioning handover explicitly wants the Planner's existence communicated (§7, "what the Planner does"). Proposed: a new section **"3a. Plan Your Accumulator,"** inserted between "How SlipGuard Works" and "Example Report," following the exact same frame template as the document's existing sections:

- **Purpose:** introduce the Planner as the natural next step after understanding a slip's structural risk.
- **User emotion:** "I'm not just told what's wrong — I can do something about it, and I choose what."
- **Primary message:** every replacement is the customer's own choice; the Planner explains structural consequences, never suggests or predicts (`PD-007`).
- **Visual priority:** one plain sentence plus a single before/after structural score example — no live demo, no interactive Planner on the marketing page.
- **Interaction:** none required, matching every other narrative section.
- **Exit action:** continue scrolling.

This is an addition, not a redesign of the six existing sections, and follows their own established template exactly — flagged here as a proposal per the Frontend Work Rule, not built into `HOMEPAGE_STORYBOARD.md` unilaterally.

## 6. Dashboard — "What's True Right Now"

### 6.1 Current State (Verified, §2 R-7)

Hero greeting, Recent Analyses (real data, good), Progress counts (real, appropriately minimal), a **hardcoded, always-empty Journal section**, and a static Trust list. No Planner presence anywhere.

### 6.2 Redesign

Within `VISUAL_INSPIRATION.md`'s anti-density constraint (no new chart, no wall of numbers — every item below already exists in the current page's own visual language, just corrected and extended):

- **Journal section (fix, not redesign):** read `Auth::user()->journalEntries()->latest()->first()`, matching the exact Journal Card pattern already defined in `COMPONENT_PRINCIPLES.md` and already built for the real Journal screen (`U-08.2`). Show the real most-recent reflection, or the genuine `EMPTY_STATES.md` "No Journal Entries" state if none exists — never a hardcoded placeholder regardless of real data.
- **Planner presence (new section, same visual weight as "Recent Analyses"):** if the customer has any non-terminal `PlannerSession`, show one card — source slip, current status, latest revision's score/band — linking to the Planner Workspace. If none, no section at all (not an empty state for a capability the customer hasn't touched yet — matches the existing Dashboard's own restraint principle, keeping the page honest about what's actually happening rather than advertising unused features).
- **No new "Discipline Index" or trend chart** — confirmed absent from the repository (§3); not designed here regardless of the handover's evocative language, per its own explicit prohibition.

## 7. Analyze Slip

Functionally complete (`U-04.1`/`E-03`). Recommended refinements, all working within existing `COMPONENT_PRINCIPLES.md` Analysis Cards conventions, not a new pattern:

- Slip-card status badges (Draft/Ready/Analysed/Archived) already exist in `betting-slips/index.blade.php` using an older `bg-amber-100`/`bg-blue-100` ad hoc colour convention that predates `DESIGN_TOKENS.md`'s later-accepted risk/status token system. Recommend migrating these specific badges to the established token pattern (`text-risk-{token} bg-risk-{token}/10 border-risk-{token}/30`, already used by History/Report/Planner) for visual consistency — a token-alignment fix, not a new component.
- Add a single, calm line under a newly-analysed slip's action row: "Analyse another slip" as a secondary link (mirrors the Report screen's own existing exit-action pattern, `U-03.2` §20.10) — encourages continued engagement without urgency framing.

One observation: "Planning History" and "History" are adjacent, similarly-named items; recommend no renaming (`U-08.1`'s own terminology was already reviewed and accepted, `PO-U08.1-AC-001`) but do recommend distinct icons (`ICONOGRAPHY.md`-approved metaphors only) to aid quick visual scanning — a minor addition, not a navigation restructure.

## 13. Empty State Redesign

`EMPTY_STATES.md`'s existing 15 states are reused verbatim throughout this document — no new empty state is invented. The one genuine gap: **Planning History's empty state currently reads plainly** ("Nothing here yet... Once you plan an accumulator, you'll be able to look back on it here") but doesn't yet exist as a named entry in `EMPTY_STATES.md` itself (it was written inline during `U-08.2`'s implementation, not registered centrally). Proposed: formalise it as a new `EMPTY_STATES.md` entry ("No Planning History") using its existing copy verbatim — a documentation registration, not new content.

## 14. Motion & Interaction Specification

Per §2 (R-2/R-3/R-4): every interaction below maps to `MOTION_SYSTEM.md`'s existing, unamended vocabulary.

- **Cards (Analysis, Journal, Planner, Labs):** hover = elevation increase only (shadow deepens), Instant (100ms) — no position/size change, per Hover Behaviour.
- **Buttons:** scale to 0.98 on press, 100ms — already specified, unchanged.
- **Section reveals (homepage only, once implemented per §5):** opacity 0→1, translate-y 8px→0, 300ms, `ease-out`, once per section, never re-triggering — already specified, unchanged. Not applied to routine list/card rows anywhere (History, Journal, Dashboard), per the existing "never for routine UI" rule.
- **Logo:** opacity fade on page load only. No scroll-linked motion (§2 R-2, not adopted).
- **Risk band reveal after analysis:** already specified (fade + 8px rise, 300ms) — unchanged, remains the one "deliberate" reveal moment in the product.

### 14.1 Proposed Addition — Scroll-Responsive Header (Requires Approval, Not Assumed)

If Product Office wants the header to feel more "settled" during long scrolls (homepage primarily, once §5.1 is implemented), the following is proposed as a **new, narrow `MOTION_SYSTEM.md` entry**, not assumed pre-approved: past a fixed scroll threshold, the header's vertical padding reduces by a fixed amount (not a continuous scroll-tied morph) and gains a background blur plus a single subtle shadow — a two-state toggle (expanded/condensed), not a continuously-interpolated transformation, keeping it consistent with the existing system's preference for discrete, purposeful state changes over continuous scroll-linked animation. Duration: Standard (200ms), `ease-in-out`. This remains a proposal; it is not implemented or treated as approved by this document.
