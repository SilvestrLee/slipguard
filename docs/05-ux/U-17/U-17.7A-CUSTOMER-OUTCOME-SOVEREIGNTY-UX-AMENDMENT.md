**Repository/governance reviewed first**: `U-17.7` in full (this amendment touches only its candidate-leg presentation and processing copy — its planning-brief form, milestone-disclosure pattern, Reports reuse, no-valid-candidate/changed/regeneration states, and Planner transition are all unaffected and unchanged), `COMPONENT_PRINCIPLES.md`'s Forms/Cards/Badges/Alerts inventory, `EXPLAINABILITY_SYSTEM.md`'s Language Rules, `HUMAN_DESIGNED_EXPERIENCE_STANDARD.md`'s Evidence Before Theatre principle (directly load-bearing here — see §3 below).

**UI UX Pro Max queried** (`ux` domain: "radio button group selection accessible form choice"; "progressive disclosure incremental form feedback validation"). Findings: form submission needs a visible loading→success/error state (adopted — §5's evaluation step); labels must be programmatically associated with inputs, never placeholder-only (adopted — §7); tab order must match visual order (adopted — §9 accessibility). One explicit rejection: the "AI Interaction Feedback Loop" result (thumbs-up/down, "Regenerate" framed as an AI-improvement signal) — SlipGuard's own existing "Try a different candidate" button (`U-17.7` §8, unchanged) must stay a plain, bounded, one-time action, never reframed as feeding an improvement loop, which would misstate the fact that nothing here learns or adapts.

**21st.dev MCP queried** (`radio group selection card options equal choice picker`, 6 results). One explicit, important rejection: "Radio Group Card"'s selected-state treatment (a border highlight plus "a glowing green dot" in the corner) is rejected outright — green-as-selected on a sporting outcome reads as "this is the winning/good choice," exactly the gambling-adjacent color signaling `DESIGN_LANGUAGE.md` and `ADR-012` already prohibit (colour must never imply a value judgement about a sporting outcome). Plain shadcn "Radio Group" and "Reshaped Radio"'s larger-touch-target sizing option are the only genuinely useful references — adopted in spirit (native-feeling radio semantics, generous touch target) and reimplemented in Blade/Tailwind per the standing Tool Invocation Policy, never installed.

**Verdict**: every element below is composed from `COMPONENT_PRINCIPLES.md`'s existing inventory (Forms, Cards, Badges, Alerts, Empty States) plus the native HTML `<input type="radio">` element (a Forms primitive already covered by that document's own "native form controls, styled consistently" principle — not a new component). No new `COMPONENT_PRINCIPLES.md` entry is required by this amendment.

## 1. What changes and what doesn't

`U-17.7` assumed the Builder itself resolved a candidate leg to one outcome (§5: "Match Result — Arsenal Win 2.10" presented as already decided). `U-17.6A` established that this is the customer's decision. This amendment touches exactly four points in `U-17.7`:

- **§4 (Candidate-ready screen)** — becomes an *opportunity review* screen: ranked slots with their surviving outcome options, not a finished candidate.
- **§5 (Candidate leg presentation)** — becomes an *outcome selection* control per slot, per §7 below.
- **§8 (Regeneration states)** — "Replacement Needed" is added as its own real state, distinct from the existing "Try a different candidate" regeneration button (see §12).
- **§9 (Acceptance transition)** — unchanged in destination (still the existing Planner Workspace), but now happens only after every slot has a customer choice *and* evaluation has run clean.

Everything else in `U-17.7` — the planning-brief form (§2), the milestone-disclosure processing pattern (§3), the no-valid-candidate empty state (§7), the changed-odds alert (§8's first half), the Reports/Explanation Hierarchy reuse (§6), mobile/accessibility/theme inheritance (§10), the public demo boundary (§11) — is unaffected and still governs exactly as written.

## 2. Constitutional sequence this amendment designs around (per the commissioning memo §3)

```
Builder discovers eligible opportunities (ranked slots)
  ↓
Customer reviews opportunities
  ↓
Customer chooses one outcome per opportunity
  ↓
SlipGuard evaluates the completed candidate
  ↓
Planner
```

## 3. Opportunity review screen (amends `U-17.7` §4)

Once processing completes (the existing milestone-disclosure sequence, unchanged), the customer sees every proposed slot at once — not one at a time, matching `U-17.7` §2's own "one page, not a stepped wizard" philosophy applied consistently. Each slot is an existing `<x-card>`:

```
Arsenal vs Chelsea · Sat 15:00
Match Result · Evidence: Fresh

Choose the outcome you want SlipGuard to evaluate:
○ Arsenal to Win — 1.85
○ Draw — 3.60
○ Chelsea to Win — 4.50
```

A running, real, honest counter sits above the slot list: **"3 of 5 selections made."** This is the one progress signal shown before evaluation — a literal count, not a preview of a risk score, per `HUMAN_DESIGNED_EXPERIENCE_STANDARD.md`'s Evidence Before Theatre principle: combined odds and structural risk are genuinely uncomputable until every slot has a choice, so nothing claiming to be a live risk preview may appear before that point. The primary action, **"Evaluate Candidate"** (`<x-primary-button>`), is disabled until the counter reaches the full leg count — a real, not decorative, disabled state.

## 4. Outcome selection control (amends `U-17.7` §5)

**Plain native radio inputs, one group per slot, styled consistently with this product's existing form controls — never cards with differentiated visual weight.** This is the single most consequential decision in this amendment: every option within a slot must render at *identical* visual weight — same size, same border, same type treatment, differing only in label text and price. No highlight, badge, "recommended," star, or color implies one outcome is preferable to another. This directly operationalizes Customer Outcome Sovereignty in pixels, not just in copy — a UX principle strong enough to name on its own:

> **Outcome Parity** — within a single opportunity, every outcome option must be visually indistinguishable in emphasis from every other. Where an interface shows several correct answers to different questions (a risk *band* has a genuine best/worst per `DESIGN_LANGUAGE.md`'s existing severity-color use), it may use hierarchy. Where an interface shows several *equally valid customer choices* about an uncertain sporting event, it must not.

Selection is immediate on click/tap (no separate "confirm" step per slot — matches `MOTION_SYSTEM.md`'s existing instant-feedback expectations for a simple form control) but triggers no evaluation yet; evaluation is the explicit, separate action in §3/§5 below. The selected state uses the existing focus/selection treatment already used for other radio-style controls in this product (`U-17.7` §2 point 6's own risk-ceiling radio selection) — the accent colour, never a status colour (never green, never a risk-band colour), since accent already means "this is chosen," while a status colour would mean "this is good," which is exactly the implication Outcome Parity forbids.

## 5. Evaluation step (new, follows `U-17.7` §3's own processing pattern)

Clicking "Evaluate Candidate" reuses the exact same milestone-disclosure pattern `U-17.7` §3 already specifies for the initial discovery step — this is genuinely the same *kind* of moment (a real, possibly-multi-stage calculation), not a new pattern:

```
Checking your selections
Calculating structural risk
Checking odds target
Candidate ready
```

Collapses to a single inline spinner under ~2 seconds per `MOTION_SYSTEM.md`, exactly as §3 already specifies. Three outcomes follow, corresponding directly to Increment 1's own `EvaluateCandidateSelections` result types:

- **Constructed** → the existing candidate-ready screen (`U-17.7` §4's headline/Risk Indicator/Reports reuse, entirely unchanged — this amendment only changed how legs were *chosen*, not how a finished candidate is *presented*).
- **Replacement Needed** → §12 below.
- **No Valid Candidate** → the existing empty-state pattern (`U-17.7` §7, unchanged).

## 6. Copy register additions (amends `U-17.7` §13, still inherits `U-17.4`'s approved register otherwise)

| Moment | Copy |
|---|---|
| Slot heading | "Choose the outcome you want SlipGuard to evaluate." — never "SlipGuard recommends," never a bare market name with no framing |
| Selection confirmation (inline, next to the checked option) | "You selected {outcome}." — first person, customer as subject, never "We selected" |
| Opportunity discovery framing | "We found this opportunity because {plain CBE reason}." — never a sentence about either team's chances |
| Evaluate button (disabled state) | "Choose an outcome for every opportunity to continue" |
| Progress counter | ":count of :total selections made" — a literal count, never a percentage or score |

All four directly apply `EXPLAINABILITY_SYSTEM.md`'s existing "does this describe the slip's structure, or the future?" test — nothing new was invented in that document, only new copy checked against it.

## 7. Interaction detail (per the commissioning memo §7)

- **Radio, not cards** — per §4 above.
- **Immediate local selection, deferred evaluation** — per §5.
- **Keyboard**: native `<input type="radio">` semantics give arrow-key movement within a group and Tab/Shift+Tab between groups for free — no custom keyboard handling to build or get wrong.
- **Mobile**: single column, each radio option a full-width row with a minimum 44×44px touch target (confirmed against UI UX Pro Max's own touch-target guidance), never a horizontal chip row that could wrap oddly with a price label attached.
- **Visual emphasis**: none between options, per Outcome Parity (§4). Between *slots*, only the existing rank-neutral ordering already established (slots appear in the order the Builder discovered them — no re-sorting based on which the customer already chose).

## 8. Progressive feedback (amends `U-17.7` §3's scope slightly, per the commissioning memo §10)

The *only* progressive feedback before full evaluation is the literal selection counter (§3). No partial risk score, no partial odds total, no per-selection "this looks risky" indicator appears before every slot has a choice — because none of those facts exist yet (combined odds is a product across all legs; structural risk factors read the whole slip). Promising progressive insight the engine cannot yet produce would be exactly the fabricated-progress pattern `HUMAN_DESIGNED_EXPERIENCE_STANDARD.md` prohibits by name. This is a real constraint found by checking `EvaluateCandidateSelections`' own contract, not a UX preference.

## 9. Accessibility (per the commissioning memo §15, extending `U-17.7` §10 — no new rules, direct application)

Each slot's radio group is a `<fieldset>` with a `<legend>` naming the fixture and market ("Arsenal vs Chelsea — Match Result") so a screen reader announces the question before the options. Each option's label is programmatically associated with its input (never a placeholder or bare adjacent text). Focus order follows visual order (top-to-bottom through slots, then the Evaluate button) — a direct application of `ACCESSIBILITY.md`'s existing rule, not a new one. Colour is never the only signal for "selected" (the native radio's own filled/unfilled state already satisfies this without extra treatment).

## 10. Mobile (per the commissioning memo §16, extending `U-17.7` §10)

Vertical stacking throughout — slot cards, radio options, and the counter/button footer all single-column below tablet width, matching `COMPONENT_PRINCIPLES.md`'s existing Forms stacking rule directly. No horizontal scroll anywhere in this screen.

## 11. Visual hierarchy across stages (per the commissioning memo §13)

Three stages, each with a distinct heading so the customer always knows which one they're in — reusing the existing `<x-page-header>` pattern, not inventing a stepper/breadcrumb component:

1. **"Review your opportunities"** (selection stage — §3/§4).
2. **"Evaluating your candidate"** (the milestone-disclosure moment — §5).
3. **"Your candidate"** (the existing, unchanged candidate-ready screen — `U-17.7` §4).

## 12. Replacement Needed (new state, follows from `EvaluateCandidateSelections`' own `ReplacementNeeded` result)

Distinct from `U-17.7` §8's existing "Try a different candidate" button (which remains, unchanged, as the customer's own *voluntary* one-time regeneration). Replacement Needed is the Builder surfacing a *forced* consequence of the customer's own choices — a risk-ceiling or odds-target breach — and must never silently swap a leg:

```
[ x-alert variant="caution" ]
Arsenal vs Chelsea no longer fits within your risk limit.

Choose an outcome for the next available opportunity:
Liverpool vs Everton
○ Liverpool to Win — 1.75
○ Draw — 3.80
○ Everton to Win — 4.20
```

Every other already-chosen slot remains visible, read-only (its radio group disabled, its chosen answer still shown as plain text) — never re-opened, matching the constitutional guarantee that a slot the customer already decided is never silently revisited. Only the one flagged slot accepts a new choice. Submitting it re-triggers evaluation (§5) — this may itself produce another Replacement Needed (up to the existing bound: `CandidateConstructionRuleSet2026_1::MAX_RISK_REPLACEMENT_ATTEMPTS`/`MAX_ODDS_ADJUSTMENT_ATTEMPTS`, both already implemented and tested in Increment 1) or a Constructed/No-Valid-Candidate result.

## 13. Empty states (per the commissioning memo §14)

| State | Treatment |
|---|---|
| No opportunities available | `U-17.7` §7's existing empty state, unchanged copy pattern (specific `CBR-00x` reason, only the relevant action shown) |
| All slots completed, awaiting evaluation | Not an empty state — the Evaluate button simply becomes enabled; no interstitial screen |
| Candidate invalid after evaluation | `U-17.7` §7's existing pattern, reused verbatim |
| Evidence unavailable for a slot mid-review | Cannot occur within one review session — evidence is acquired once, before slots are ever shown (`BuildAccumulatorCandidate`'s own contract); flagged here only to confirm it was checked, not left ambiguous |

## 15. Engineering implementation notes (per the commissioning memo §17)

- The Livewire component (Increment 2, not yet built) needs one array property mapping slot index → chosen `CandidateLeg` identifier, and one nullable property holding the last `EvaluateCandidateSelections` result. Both map directly onto Increment 1's already-implemented, already-tested contracts (`ChosenSlot`, `ConstructedCandidate`/`NoValidCandidate`/`ReplacementNeeded`) — no new engine-facing shape is needed.
- "Evaluate Candidate" calls `EvaluateCandidateSelections::execute()` once, synchronously, per the existing sub-2-second collapse rule in `MOTION_SYSTEM.md` — no polling or async job required at this scale (2-8 legs).
- Replacement Needed's re-submission calls the same method again with the updated `chosenSlots` array and incremented attempt counters — both already parameters of the existing method signature, nothing new to add there either.
- No transition animation beyond the existing reveal/loading patterns already documented in `MOTION_SYSTEM.md` — this amendment introduces no new motion.

## 16. Explicitly out of scope (per the commissioning memo §18, confirmed unaffected)

Builder architecture, deterministic mathematics, candidate ranking, Planner behaviour, accepted product principles, prediction, AI recommendations — none of these are touched by this amendment. Only the presentation of an already-existing engine contract changed.
