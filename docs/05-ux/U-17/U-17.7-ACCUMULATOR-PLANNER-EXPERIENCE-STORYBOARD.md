## 0. Specialist Design Capability Usage (`PO-GOV-UX-002`, mandatory for this commission)

**Repository/governance reviewed first**, per the standing requirement: `DESIGN_LANGUAGE.md` (decision-support-instrument personality, calm-not-exciting, progressive disclosure), `COMPONENT_PRINCIPLES.md` (full inventory — every component this storyboard needs already exists: Cards, Badges, Risk Indicators, Alerts, Forms, Progress Indicators, Timeline, Empty States, Dialogs), `EXPLAINABILITY_SYSTEM.md` (the Explanation Hierarchy and Language Rules this experience must not violate), `MOTION_SYSTEM.md` (Loading Behaviour, Reveal Animations, the existing milestone-disclosure pattern from `PO-U07.X.1-001`).

**UI UX Pro Max queried** (`ux` domain, two searches: multi-step configuration forms, and results-review/no-results patterns). Findings: a real-processing step indicator is recommended for genuine multi-step flows (adopted — §5 below); "no results" states should show a specific reason and next action, never a blank/dead-end screen (adopted — §14, already independently required by `U-17.6`'s own reason-code framework, reinforced not introduced by this consultation).

**21st.dev/Magic queried** (`get_inspiration`, planning-brief/candidate-review/no-results query). Returned only low-confidence (~0.52-0.55) results with no genuine fit — an LLM model-selector, a coach-scheduling card, a plan-approval tool, and two pricing cards. None adopted; none are React/shadcn patterns compatible with Blade/Livewire in any case, and none address SlipGuard's actual product shape (a constraint-configuration form feeding a deterministic, explainable result, not a booking or pricing flow). Consistent with this session's repeated finding for this tool on SlipGuard-specific work: genuine consultation, legitimate "nothing to adopt" outcome.

**Verdict**: every component this storyboard specifies is composed from `COMPONENT_PRINCIPLES.md`'s existing inventory. **No new component principle is added to that document by this storyboard** — per its own Just-in-Time rule ("add a new component's principles here when it's first built, not speculatively"), any genuinely new visual grammar this experience turns out to need at implementation time must go through the Gap Rule then, not be pre-invented here. Two compositions flagged as worth watching at that point: the "planning brief" form (composed entirely from existing Forms + Section Headers) and the "candidate leg" card (composed from the existing Card + Risk Indicator + Badge primitives) — both compositions of existing things, not new components, but noted here so implementation doesn't quietly invent a fourth card variant without checking first.

## 1. Experience decision

**Feature name: "Plan an Accumulator"** (Option C from `U-17.4`/the commission's own §27), paired with the description **"Tell SlipGuard your constraints — it builds a candidate from supported fixtures for you to review."** Rejected: "Accumulator Builder" (already too close to implying SlipGuard "builds" in the sense of deciding, when the customer's constraints and review are what actually govern the outcome — a subtle but real distinction worth the more modest verb "Plan"); "Build a Candidate" (accurate but a flatter, less inviting label for a customer-facing nav entry). "Plan an Accumulator" reads as an action the customer takes, not a service SlipGuard performs *to* them — consistent with `DESIGN_LANGUAGE.md`'s "the customer remains the final decision-maker" personality.

**Entry point**: a new, secondary card on the existing Analyze Slip index, beside (never replacing) "New Slip" — matching `COMPONENT_PRINCIPLES.md`'s existing Cards component exactly, no new card variant. Two clearly distinct entries:

```
[ Analyze a Slip ]           [ Plan an Accumulator ]
You already have selections   Tell SlipGuard your constraints —
— see where the risk is.      it builds a candidate to review.
```

## 2. Planning-brief flow (§59.4, §29–§35)

**One page, not a stepped wizard** — the brief has six fields, well within `DESIGN_LANGUAGE.md`'s "generously spaced, not a dense form" tolerance for a single scroll, and a wizard would cost more taps for a customer who already knows what they want than it saves in per-step clarity. Grouped sections, each a plain `<x-card>` (existing component, no new variant), in this order:

1. **Competitions** — multi-select chips, Premier League / La Liga / Serie A only (no disabled "coming soon" entries for unverified competitions — `COMPONENT_PRINCIPLES.md`'s Badges anti-pattern against implying features that don't exist). At least one required.
2. **Planning window** — three preset chips (Next 24 hours / Next 3 days / Next 7 days), matching the existing chip-style control already used elsewhere (e.g. History's status filter tabs) rather than a calendar widget — the 1–7 day range doesn't need date-picker precision.
3. **Number of legs** — a compact segmented control, 2/3/4/5/6/7/8, default 5 highlighted but not visually "rewarded" (no larger text or accent fill implying more legs is better — directly answering the commission's own §32 caution).
4. **Markets** — five checkboxes for the default-enabled families, plainly labelled (Match Result, Double Chance, Draw No Bet, Total Goals, Both Teams to Score), all pre-checked; a collapsed "More markets" disclosure (existing expand/collapse pattern, `MOTION_SYSTEM.md`) reveals Half-Time Result, unchecked by default — Correct Score does not appear anywhere in this form, full stop, matching `U-17.6`'s exclusion directly.
5. **Target odds (optional)** — a plain "No target" toggle default-on; switching it off reveals a min/max decimal-odds pair using the existing Forms component's paired-short-fields pattern (already documented for "odds + a small unit label").
6. **Maximum structural risk** — reuses the *existing* Risk Indicator's own band vocabulary (Low/Moderate/High/Very High) as a plain radio selection, not a new risk-styled control — defaults to High per `U-17.6`'s own stated default, with copy explicit that this is a ceiling, not a target: "SlipGuard will not exceed this even if it means fewer legs match your other choices."

**Review step**: a plain summary card (§36 of the commission, adopted near-verbatim) before the primary action, itself just a `<dl>` inside an existing Card — no new component.

**Primary action**: **"Find a candidate"** (`<x-primary-button>`, exactly one per screen per `COMPONENT_PRINCIPLES.md`'s Buttons rule). Rejected entirely, per `U-17.4`'s approved-language register: "Generate," "Get picks," anything implying SlipGuard is producing a recommendation rather than searching within stated constraints.

## 3. Processing experience (§59.5, §37, §38)

Reuses the **exact milestone-disclosure pattern already built and shipped for the Planner Workspace** (`PO-U07.X.1-001`'s "What SlipGuard just did") rather than inventing a new progress component — this is precisely the kind of reuse the Just-in-Time principle asks for. Real, honest stages (not the commission's own more elaborate 11-stage list, several of which describe acquisition work that per `U-17.5` happens before construction, not during it — matching the same "don't claim work is happening live that already happened" discipline `U-17.5` itself applied):

```
Planning brief checked
Supported fixtures found
Markets checked
Candidate built
Structural risk checked
Candidate ready
```

Per `MOTION_SYSTEM.md`'s Loading Behaviour: under ~2 seconds, this may collapse to a single inline spinner rather than a full staged reveal — the staged version is for the genuine >2s case, and which case applies is a real, measurable fact at implementation time, not a design guess made here.

**Request-too-broad state** (§38): a plain `<x-alert variant="caution">` (existing component) — "This planning brief is too broad to process in one request. Try fewer competitions or a shorter planning window." No mention of API credits or quotas, matching the commission's own instruction directly.

## 4. Candidate-ready screen (§59.6, §39–§43)

Headline reuses the exact Risk Indicator component (`COMPONENT_PRINCIPLES.md`) already used everywhere else structural risk appears — **no new "candidate ready" visual treatment invented**:

```
[ Risk Indicator: Moderate — existing component, unchanged ]
Candidate ready for your review
5 legs · Combined indicative odds 9.42 · Evidence: Fresh
```

Directly below, in the same always-visible position `DESIGN_LANGUAGE.md`'s Data Explanation Philosophy already requires for every risk indicator: the plain-language odds disclosure from `U-17.4`'s approved register — *"Odds are time-stamped provider data for planning purposes and may change. SlipGuard does not place the bet or guarantee bookmaker availability."* Never buried, never a hover tooltip.

**No celebratory treatment** — no confetti, no "success" framing beyond the plain factual headline, matching `PO-U07.X.1-001`'s own already-established restrained precedent for the Planner's own completion moment (a small checkmark accent was judged sufficient there; the same restraint applies here, arguably more so given the higher regulatory sensitivity `U-17.4` already flagged for this specific capability).

## 5. Candidate leg presentation (§59.7, §40–§41)

Each leg is a composition of the existing Card + Badge primitives, not a new component:

```
Arsenal vs Chelsea · Sat 15:00
Match Result — Arsenal Win        2.10
Fresh evidence · Included: matches your selected market order
```

Inclusion explanations pull directly from `U-17.6`'s own real rule IDs (`CBE-001`–`CBE-009`) translated to plain language exactly as `ReasonCode` already is for Capability A — no new translation mechanism. Explicitly forbidden, matching `EXPLAINABILITY_SYSTEM.md`'s Language Rules table directly: "strong pick," "great form," "likely," "confident," "best selection" — every one of these already fails that document's own "does this describe the slip's structure, or the future?" test, so this storyboard doesn't need a new rule, only to apply the existing one to new copy.

## 6. Structural-risk and evidence disclosure (§59.9, §59.10, §43–§44)

The candidate's whole-slip structural analysis reuses the **existing Reports component and Explanation Hierarchy verbatim** — headline → band → weakest leg → main reasons → per-leg detail, progressive disclosure exactly as `EXPLAINABILITY_SYSTEM.md` already mandates for every other analysis screen. This storyboard does not propose a second, Capability-B-specific risk presentation; doing so would violate `COMPONENT_PRINCIPLES.md`'s own anti-pattern ("reordering the hierarchy for visual variety").

Evidence freshness and construction timestamp are always visible (matching the milestone-disclosure precedent); rule-set versions and normalisation detail sit behind the same progressive-disclosure boundary `EXPLAINABILITY_SYSTEM.md` already draws for "Rule Set Information" and "Analysis Metadata" — reused, not redesigned.

## 7. No-valid-candidate experience (§59.11, §47)

A plain `<x-empty-state>` (existing component, exactly the pattern already used for History/Journal/Planning History's own "nothing here yet" states) — not a new failure-screen design:

```
No accumulator candidate satisfies all of your current planning constraints.
[ specific U-17.6 reason, e.g.: "The target odds could not be reached
  without exceeding your risk limit." ]

[ Edit planning brief ]   [ Back to workspace ]
```

Only the action relevant to the actual failure reason is shown (per `U-17.6` §19's own reason-to-action mapping) — never a generic "try again" that implies the customer did something wrong.

## 8. Changed / invalid / regeneration states (§59.12, §59.13, §45–§48)

**Changed**: an inline `<x-alert variant="info">` above the affected leg — "Odds changed since this candidate was built" — with the updated combined odds recalculated in place, never a full-page interruption.

**Invalid**: the same empty-state pattern as §7, reason-specific ("This candidate can no longer be accepted in its current form"), offering rebuild or brief-edit, never silent auto-repair.

**Regeneration**: exactly one button, **"Try a different candidate"**, visible only before acceptance and only once (`U-17.6`'s own ≤1 pre-acceptance regeneration bound) — after it's used, the button is simply gone, replaced by "Edit planning brief" — no counter, no "regenerations remaining" gamified framing.

## 9. Acceptance and Planner transition (§59.14, §50–§51)

Primary action: **"Use this candidate in Planner"** (adopted directly from the commission's own §50 recommendation, which is already well-judged against `U-17.6`'s own `ADR-013` boundary — it names the actual lifecycle transition rather than implying a wager). On acceptance, the customer lands directly on the existing, completely unmodified Planner Workspace (`PO-U07.X.1-001`) — same premium header, same Session Timeline, same lock/remove/add/compare/confirm/export — with **zero Capability-B-specific controls surviving into that screen** (no duplicate "regenerate," no second edit affordance), a direct, simple consequence of `ADR-013`'s boundary rather than a new interaction design.

## 10. Mobile, accessibility, and theme (§59.15–§59.17, §55–§58)

No new rules — this experience inherits `RESPONSIVE_RULES.md`, `ACCESSIBILITY.md`, and `DESIGN_TOKENS.md`'s light/dark treatment exactly as every other screen in the product already does, since every component used here (Cards, Forms, Badges, Risk Indicators, Progress Indicators, Empty States, Alerts) already has its own responsive/accessible/themed behaviour documented. The one genuinely new mobile consideration: the planning-brief form's segmented leg-count control and market checkboxes must stack per `COMPONENT_PRINCIPLES.md`'s existing Forms rule ("single-column field stacking below tablet width") — not a new rule, a direct application of one that already exists.

## 11. Public demo boundary (§59, §53)

Any public-facing preview of this capability (homepage, marketing) uses fictional fixtures only, per `U-17.4`'s own recommendation, reusing the exact convention the real Demo Workspace (`PO-U17.0-001`) already established for fictional-but-realistic content — not a new rule invented for this feature specifically.

## 13. UX copy register (§59.20)

Directly inherits `U-17.4`'s approved/cautioned/prohibited language register verbatim — this storyboard adds no new approved phrases beyond what's already specified there (feature name, candidate-ready wording, no-result wording were all already settled by Compliance; UX's job here was placement and hierarchy, not new copy invention).

## 14. Engineering handoff (§59.21)

Every state in §12 maps to an existing component with documented behaviour — Engineering's job is composition and wiring to `U-17.5`'s architecture and `U-17.6`'s rule engine, not new component construction. The two flagged compositions (§0) should get their own `COMPONENT_PRINCIPLES.md` entries at the moment they're actually built, matching that document's own Just-in-Time rule — this storyboard deliberately does not pre-write them.

## 15. UX risk register (§59.22)

- **The "maximum structural risk" control reuses risk-band vocabulary customers already associate with *evaluating* a slip, now used to *constrain* construction** — a subtle dual-use of the same words that needs real user testing at implementation time, not assumed clear from this document alone.
- **A five-checkbox default-all-on market selector risks customers never noticing they could narrow it** — acceptable for MVP (matches `U-17.6`'s own default-enabled set), flagged as a real usability tradeoff, not a hidden one.
