## 9. Executive Experience Statement

The Analysis Experience should feel like an independent professional assessment — a calm, structured review that explains itself, the way a well-written insurance report or a clean bank statement does. It should never feel like a sportsbook, a tipster product, a prediction service, a casino interface, a research dashboard, or a gamified betting application (`docs/05-ux/DESIGN_LANGUAGE.md`'s Design Philosophy and Product Personality; `docs/05-ux/VISUAL_INSPIRATION.md`'s Explicitly Rejected list).

**Core customer outcome:** a first-time customer should understand the Overall Structural Risk, the Main Contributing Factor, the Data Quality Band, and any report limitations within approximately 15 seconds, without needing to open a single disclosure (§15).

## 10. Experience Principles

### 10.1 Clarity Before Completeness
The initial report shows only what orients the customer. Everything else is one controlled disclosure away (§24), never a second screen.

### 10.2 Explanation Before Mathematics
Every number is preceded by what it means. No formula, trace value, or internal code ever appears before its plain-language explanation (`docs/05-ux/EXPLAINABILITY_SYSTEM.md`: "Explain first, score second").

### 10.3 Transparency Without Alarm
A Limited Analysis states its limitation plainly and visibly — it is never hidden, and never styled as a system failure when the analysis itself remains usable (PD-02).

### 10.4 Structural Risk, Not Outcome Prediction
Every state — Full, Limited, and Unavailable alike — restates that SlipGuard evaluates how a slip is built, not what will happen in the match it references (`docs/00-governance/VISION_AND_PRINCIPLES.md`).

### 10.5 Calm Over Excitement
No flashing, pulsing, celebratory animation, aggressive danger styling, countdowns, or casino-style motion, anywhere in this experience (`docs/05-ux/MOTION_SYSTEM.md`'s Forbidden Animation Patterns).

### 10.6 Mobile First
The primary specification is mobile (§35). Desktop expands spacing and comfort; it never restructures the report into a dashboard grid (`docs/05-ux/COMPONENT_PRINCIPLES.md`'s Reports: "never becomes multi-column even on desktop").

## 11. End-to-End Journey Map

```text
Analysis submitted
        ↓
Brief truthful transition (§13)
        ↓
Analysis result resolved
        ↓
Branch:
    ├── Full Analysis (§16)
    ├── Limited Analysis (§17)
    └── Unavailable Analysis (§18)
        ↓
Customer understands result (§15, within ~15 seconds)
        ↓
Customer explores supporting explanation (§24, Level 2/3 disclosure)
        ↓
Customer reviews Data Quality and methodology
        ↓
Customer exits (§38):
    ├── Analyse another slip
    └── Return to dashboard
```

No stage above is invented — every stage maps to an implemented or approved repository state (`U-03.1`'s Analysis Lifecycle Inventory, §9). No queue, processing, or retry-after-failure stage is included, because none exists (analysis is synchronous, `U-03.1` §9).

## 13. Analysis Transition Storyboard

**Objectives** (PD-07): confirm receipt, reassure without fabricating progress, disappear immediately on result, work with the current synchronous request, remain understandable with motion disabled.

**Required content:**

| Element | Content |
|---|---|
| Heading | "Analysing your slip" |
| Supporting sentence | "SlipGuard is reviewing the structural risk in your selections." |
| Visual treatment | A static or gently-assembling SlipGuard mark (opacity shift only, `duration-standard`, `ease-out`) plus a restrained, non-spinning status indicator — no percentage, no step counter |
| Accessible status announcement | `role="status"` region announcing "Analysing your slip" once, on transition start |
| Reduced-motion fallback | Static mark, static label, no assembling/opacity animation — information identical, motion removed (`docs/05-ux/MOTION_SYSTEM.md`'s Reduced Motion Accessibility) |
| Request-failure fallback | See §21.13, Request Failure Panel — distinct from any analysis outcome |

**Prohibited copy** (verbatim from the directive, binding): "Reading selections," "Calculating risk," "Comparing markets," "Checking historical patterns," "Preparing recommendation," "Almost finished" — none of these stages are implemented; displaying them would fabricate internal processing that doesn't exist (PD-07's prohibition on "invented queue stages" and "fake processing milestones").

**Approved copy** (PD-07's own recommended direction, adopted as-is, not marked proposed — Product Office supplied this wording directly):
> Analysing your slip
>
> SlipGuard is reviewing the structural risk in your selections.

No specific duration is promised anywhere in this copy, consistent with the prohibition on fake estimated times.

## 14. Completion Transition

- The transition panel is **replaced in place**, not navigated away from — same URL, same scroll position, no full-page reload feel.
- The report heading (`<h1>`, Frame F-01/L-01/U-01's heading) enters the DOM as the first heading after the application's own page chrome, so it is immediately next in both visual and screen-reader reading order.
- **Focus does not move automatically** unless the customer would otherwise lose context entirely (e.g., if the transition panel and the report render in genuinely different scroll regions — not expected in this single-column, in-place design, so no forced focus movement is specified).
- A `role="status"` live region announces completion once: "Analysis complete" (Full/Limited) or "Analysis unavailable" (Unavailable) — a single, terse announcement, not a repeat of the full report content (screen readers will encounter the report content naturally via normal reading order immediately after).
- Layout shift is minimised because the transition panel and the report headline occupy comparable vertical space by design (§35's spacing rules apply identically to both).
- Reduced motion: the swap from transition to report is an instant content replacement, no cross-fade.

## 15. First 15 Seconds Hierarchy

Visible immediately, in this order, without any interaction:

1. Whether an analysis is available (Full / Limited / Unavailable).
2. Whether it is Full or Limited (if available at all).
3. The Overall Structural Risk (Structural Score, where available).
4. The Risk Band.
5. What the Risk Band means (one sentence).
6. The Main Contributing Factor.
7. The Data Quality Band.
8. The primary next action.

**Never in the initial view** (moved to Level 3/4, §19): all factor traces, raw inputs, normalized values, internal reason-code identifiers, internal contribution calculations, engine identifiers, schema versions, taxonomy versions, database identifiers, the numeric Data Quality score, excluded/unsupported features, weakest-selection wording, or recommendations of any kind.

## 16. Full Analysis Storyboard

### Frame F-01 — Analysis Complete
**Purpose:** confirm successful completion, orient the customer.
**Content:** report heading ("Your slip's structural risk" — proposed, see §27); Full Analysis status; analysis timestamp (relative, e.g. "Analysed just now" — pattern already shipped on the Dashboard, U-02); one-line deterministic-analysis statement (§32).
**Customer question:** "Did SlipGuard complete the analysis?"

### Frame F-02 — Overall Structural Risk
**Purpose:** present the headline result.
**Content:** Structural Score (0–100 integer); Risk Band label; one-sentence band explanation (§28); a color-independent icon + text label (never color alone, `docs/05-ux/ACCESSIBILITY.md`'s Colour Independence).
**Customer question:** "How structurally risky is this slip?"
**Prohibited interpretation:** never implies likelihood of loss, likelihood of winning, or permission to place the bet (`docs/09-compliance/PRODUCT_GUARDRAILS.md`).

### Frame F-03 — Main Contributing Factor
**Purpose:** identify the single largest slip-level contributor.
**Content:** heading "Main Contributing Factor"; customer-facing factor name (§22, factor name register below); one plain-language sentence explaining how it contributed; an optional supporting value **only when it already exists in the persisted trace and is unambiguous** (flagged as an Open Issue, §41, since the exact customer-safe trace field mapping needs Engineering confirmation — see §22).
**Customer question:** "What contributed most to this result?"

### Frame F-04 — Supporting Contributing Factors
**Purpose:** show the next most meaningful contributors.
**Content:** factors ordered by persisted `adjustedContribution`, highest first, excluding the Main Contributing Factor itself (PD-05); a short initial list (proposed: up to 2 more, i.e. 3 total including the Main Contributing Factor — see §23); an expansion control revealing the complete set of 6; explicit treatment for zero-contribution, not-evaluated, and RF-006-inactive factors (§23).
**Customer question:** "What else influenced the result?"

### Frame F-05 — Data Quality
**Purpose:** communicate how complete and reliable the available information was.
**Content:** Data Quality Band only (PD-04); one-sentence explanation (§29); a short note connecting it to report availability (e.g., that Limited/Unavailable outcomes are driven by data quality/market recognition, for a reader who wants to understand why this matters at all).
**Customer question:** "How complete was the information used?"

### Frame F-06 — Trust and Methodology
**Purpose:** reinforce deterministic analysis and the no-prediction boundary.
**Content:** concise trust statement + no-prediction statement (§32, both already-approved language reused from the U-02 Dashboard's Trust panel); an expandable methodology disclosure link ("How was this analysis produced?").
**Customer question:** "Why should I trust this report?"

### Frame F-07 — Report Details (expandable)
**Content:** Rule Set version, engine version, input schema version, market taxonomy version, analysis timestamp (absolute, in this expanded view — the headline used a relative time). No internal database IDs.

### Frame F-08 — Exit Actions
**Approved:** "Analyse another slip" (primary); "Return to dashboard" (secondary); "Edit this slip" appears only if the slip's `BettingSlipStatus` still permits it (it does not, for an Analysed slip that isn't also Archived — per `U-03.1`'s Lifecycle Inventory, `Analysed→[Archived]` only, so Edit is **not** available for a completed Full Analysis's own slip under today's lifecycle rules; flagged in §41 since this reads oddly if a customer expects to "fix" a Full Analysis they're unhappy with — that expectation itself may be a Product Office question, not a UX one to resolve here).

## 17. Limited Analysis Storyboard

A Limited Analysis is a **completed, valid analysis with a visible constraint** — never presented as failed, unavailable, or a technical error (PD-02).

### Frame L-01 — Limited Analysis Status
**Content:** clear "Limited Analysis" label, distinct in wording and (per `ACCESSIBILITY.md`) not by color alone from both Full and Unavailable; no apology language.
**Copy (proposed):**
> Limited analysis available
>
> SlipGuard completed the analysis, but some slip information could not be fully evaluated.

### Frame L-02 — Overall Structural Risk
Same content as Frame F-02 (Structural Score and Risk Band **are** produced for a Limited Analysis — `U-03.1` §9/§15 confirms the full numeric score is shown alongside the limitation flag, never withheld). The limitation notice (Frame L-03) must appear in the same initial view, not below the fold — the risk result is never shown without its limitation context, per the directive's explicit instruction.

### Frame L-03 — Limitation Summary
**Content:** which category of information was incomplete (drawn only from repository-supported reasons — `MarketUnrecognized` and/or `NormalizationPartial` reason codes, per `U-03.1` §10); a statement that the report reflects what SlipGuard *could* evaluate; a statement that the limitation affects completeness, not outcome probability.
**Copy (proposed):**
> Some selections in this slip use markets SlipGuard could only partially recognise. The result above reflects everything SlipGuard was able to evaluate — it doesn't affect how the score itself is calculated for the selections that were fully understood.

### Frame L-04 — Main Contributing Factor
Same structure as Frame F-03, shown only when the persisted result actually contains one (it does, by construction — a Limited Analysis still runs the full factor pipeline, `U-03.1` §10). No overstatement of precision beyond what Full Analysis states.

### Frame L-05 — Supporting Factors
Same as Frame F-04, with one addition: where `factorsNotEvaluated` is non-empty (only ever `RF-005`, per `U-03.1` §12), that factor is shown in a visually and textually distinct "not evaluated" treatment, never silently omitted and never shown as if it contributed 0 by calculation.

### Frame L-06 — Data Quality
Band only (never the numeric score, PD-04); explanation ties explicitly to the Limited state (§29's Limited band copy).

### Frame L-07 — Recovery or Next Action
**Approved (PD-09, resolving OI-03):** "Analyse another slip" (primary); "Return to dashboard" (secondary). No "Edit this slip" action — a Limited Analysis transitions the slip to `Analysed`, the same as a Full Analysis, so editing is not reachable under today's lifecycle. No recommendation of *which* selection to change (PD-03's prohibition extends here directly).

### Frame L-08 — Methodology and Metadata
Identical structure to Frame F-06/F-07.

## 18. Unavailable Analysis Storyboard

An Unavailable Analysis must never resemble a completed report — no score, no band, no factor list.

### Frame U-01 — Analysis Unavailable
**Copy** (adapted from the already-approved `docs/05-ux/EMPTY_STATES.md` "Unavailable Analysis" entry, not newly proposed):
> We couldn't analyze this slip
>
> [reason-specific supporting text, Frame U-02]

### Frame U-02 — Reason
Only repository-supported reason categories (`U-03.1` §9, §15's gate tiers):

| Reason | Trigger | Copy | Source |
|---|---|---|---|
| Unsupported sport | Tier 1 hard gate — any leg not football | "SlipGuard doesn't support [sport] yet. Structural risk analysis is currently available for football only. We're evaluating other sports for future coverage." | Verbatim, already approved: `EMPTY_STATES.md`'s "Unsupported Sport" entry |
| Too many unrecognised markets | Tier 2 — unrecognized-market proportion >25% | "Too many selections on this slip couldn't be recognized." | Verbatim, already approved: `EMPTY_STATES.md`'s "Unavailable Analysis" entry's own worked example |
| Insufficient usable information | Tier 3 — deduction-score gate lands Insufficient | "The available information for this slip wasn't enough for SlipGuard to produce a reliable structural assessment." | **PROPOSED UX COPY — PRODUCT OFFICE APPROVAL REQUIRED.** Flagged in §41: per `U-03.1` §16, this path is not currently reachable through partial-normalization deductions alone under Rule Set 2026.1 (the deduction floor is 60, above the Insufficient threshold of 40) — this copy is written defensively, for a state the gate's own logic defines but today's arithmetic cannot actually produce. |

### Frame U-03 — Recovery Action
**Approved (PD-10, correcting `U-03.1` §9):** "Analyse another slip" (primary); "Return to dashboard" (secondary). No "Edit this slip" action — `U-03.1` §9's claim that an Unavailable outcome keeps the slip `Ready` does not hold: `App\Actions\Analysis\AnalyzeBettingSlip::execute()` calls `markAnalysed()` unconditionally for all three availability outcomes, verified directly in code during U-03 implementation (2026-07-25). This makes all three outcomes (Full/Limited/Unavailable) consistent: none offer "Edit this slip," since a completed analysis of any kind transitions the slip to `Analysed`, and only `Analysed→[Archived]` is a legal transition from there.

### Frame U-04 — Trust Statement
**Copy (proposed):**
> SlipGuard doesn't produce a structural risk score when it can't evaluate a slip responsibly. Refusing to guess is part of how this analysis stays trustworthy.

**Prohibited on this screen:** Structural Score, Risk Band, Main Contributing Factor, any factor ranking, completed-analysis Data Quality presentation, or Rule Set detail presented as though a valid report exists.

| Level | Content | Why |
|---|---|---|
| **1 — Immediate** | Report state; Full/Limited status; Structural Score (where available); Risk Band; one-sentence band meaning; Main Contributing Factor; Data Quality Band; primary action | The 15-second understanding requirement (§15) — nothing here requires interaction |

## 20. Report Structure

Single vertical reading flow, every breakpoint, matching `COMPONENT_PRINCIPLES.md`'s Reports component exactly:

1. **Analysis state** — Purpose: orient. Priority: highest. Question: "What am I looking at?" Content: Full/Limited/Unavailable header. Variants: 3. Default visibility: always shown. Interaction: none. Empty behaviour: N/A (always present). Accessibility: `<h1>`. Prohibited: none.
2. **Overall Structural Risk** — Purpose: headline result. Priority: highest. Question: "How risky is this slip?" Content: score + band + one sentence. Variants: 4 bands × (Full/Limited); absent on Unavailable. Default visibility: always shown (except Unavailable). Interaction: none at this level. Empty: N/A on Unavailable (section omitted entirely, not shown empty). Accessibility: `<h2>`, band conveyed by text+icon. Prohibited: outcome language.
3. **Main Contributing Factor** — Purpose: primary explanation. Priority: high. Question: "What drove this?" Content: name + one sentence. Variants: 6 possible factors, RF-006 never appears here. Default visibility: always shown (Full/Limited). Interaction: none. Empty: "no meaningful contributor" copy (§23). Accessibility: `<h2>`. Prohibited: weakest-selection language (PD-03).
4. **Supporting Contributing Factors** — Purpose: secondary explanation. Priority: medium. Question: "What else mattered?" Content: ranked list. Variants: 0–5 remaining factors. Default visibility: 2–3 shown, rest expandable. Interaction: expand/collapse. Empty: omit section if genuinely nothing beyond the Main Contributing Factor is meaningful. Accessibility: `<h3>` + expand button with `aria-expanded`. Prohibited: invented tie-break scores.
5. **Data Quality** — Purpose: completeness signal. Priority: medium-high (higher on Limited). Question: "How complete was the input?" Content: band + sentence. Variants: Strong/Good/Limited (Insufficient never appears on a completed report, §29). Default visibility: always shown. Interaction: none. Empty: N/A. Accessibility: `<h2>`, band as text. Prohibited: numeric score (PD-04).
6. **Limitation information** — Purpose: transparency. Priority: high, Limited only. Question: "What couldn't be evaluated?" Content: Frame L-03. Variants: market-unrecognized / partial-normalization, or both. Default visibility: shown only when `limited_analysis: true`. Interaction: none. Empty: section entirely absent on Full/Unavailable. Accessibility: part of primary reading order, not a collapsed aside. Prohibited: alarm styling.
7. **Trust statement** — Purpose: credibility. Priority: medium. Question: "Why trust this?" Content: §32. Variants: none (same on Full/Limited; adapted wording on Unavailable, Frame U-04). Default visibility: always shown. Interaction: none. Accessibility: `<h2>` or clearly labelled region. Prohibited: legalistic tone.
8. **Methodology** — Purpose: depth on demand. Priority: low by default. Question: "How was this produced?" Content: §21.9. Variants: none. Default visibility: collapsed. Interaction: expand. Accessibility: button, `aria-expanded`/`aria-controls`. Prohibited: raw traces by default.
9. **Report details** — Purpose: full traceability. Priority: lowest. Question: "What exactly produced this?" Content: 4 version strings + timestamp. Default visibility: collapsed. Interaction: expand. Accessibility: same pattern as Methodology. Prohibited: internal database IDs.
10. **Exit actions** — Purpose: intentional departure. Priority: always present, visually calm. Content: §38. Default visibility: always shown, typically at the end of the flow (and optionally, per `RESPONSIVE_RULES.md`, a lightweight persistent primary action is acceptable — see §35, not a competing second CTA). Accessibility: real buttons/links, 44×44 minimum.

Visible, calm, factual. Communicates deterministic analysis, structural-risk-not-prediction, honest limitations, versioned Rule Set (§32).

### 21.9 Methodology Disclosure
Expandable. Answers "How did SlipGuard reach this assessment?" Does not reveal raw mathematical traces by default — a plain-language walkthrough of the factor categories considered, not the `FactorTrace` data itself.

### 21.11 Primary Action Group
Approved: Analyse another slip; Return to dashboard (PD-09/PD-10: "Edit this slip" is never valid under today's lifecycle for any completed analysis outcome — dropped from this group entirely, not merely conditional). Heading, reason (from the Frame U-02 table), recovery action, secondary action, trust statement (Frame U-04).

### 21.13 Request Failure Panel
Used only when the report request itself fails to load or submit — never conflated with Analysis Unavailable, which is a valid, defined analysis outcome, not a failure. Content per `docs/05-ux/EMPTY_STATES.md`'s "Network Failure" / "Unexpected Error" entries (already approved, reused verbatim): retry action, return action, `role="alert"` announcement.

## 23. Contributing-Factor Ordering Rules

**Order:** meaningful factors by `adjustedContribution`, highest first (PD-05, no recalculation).

**Ties:** stable secondary ordering by canonical Risk Factor order (`RF-001`→`RF-006`) — no invented tie-break score.

**Zero contributions:** excluded from the initial summary (Frame F-04/L-05); available in the expanded methodology view, where transparency requires showing all 6 factors were genuinely considered.

**RF-006:** never presented as an active risk signal. In the expanded methodology view only, stated plainly: "Relationship analysis between selections is not active in the current Rule Set." Never implied to be a missing or broken feature — it is an explicit, permanent, documented design choice (`RISK_RULE_SET_2026_1.md` §11).

**Factors not evaluated:** visually and textually distinct from both "zero contribution" (calculated, genuinely low) and "inactive by Rule Set" (RF-006 specifically) — a factor that could not be meaningfully calculated at all (only ever RF-005, and only when no selection has a known market complexity, `U-03.1` §12). Proposed treatment: a small "not evaluated" label distinct from a score.

**Fewer than three meaningful factors:** show only the meaningful ones — never pad with zero-value factors to reach a fixed count.

**No meaningful contributors:** a calm summary state (proposed copy): "No single factor stood out as the main driver of this slip's structural risk — the score reflects a combination of smaller contributions." Never implies the slip is safe (`docs/09-compliance/PRODUCT_GUARDRAILS.md`).

## 36. Accessibility Specification

**Semantic structure:** one page-level `<h1>` (the Analysis State Header, §21.2); logical, unbroken heading order thereafter (`<h2>` for major sections per §20, `<h3>` for sub-sections like individual supporting factors); a `<main>` landmark; disclosure controls are `<button>` elements, never `<div>`/`<a>` with a click handler.

**Screen-reader order** (matches visual order exactly, per §15/§20): report state → Structural Risk → Risk Band → Main Contributing Factor → supporting factors → Data Quality → trust statement → methodology → details → actions.

**Status communication:** transition start and completion (§13, §14); Limited status announced as part of normal reading order (it's a heading, not a toast); Unavailable status same; request failure via `role="alert"` (§21.13). No excessive repetition — each state is announced once, on arrival.

**Colour independence:** every Risk Band and Data Quality Band pairs its color with text and an icon (`ACCESSIBILITY.md`'s Colour Independence; `COMPONENT_PRINCIPLES.md`'s Risk Indicators).

**Focus management:** submission → no forced focus change (page remains where the customer submitted from until transition renders in place); transition → no forced focus change; completion → no forced focus change (§14's reasoning); Limited/Unavailable → same, since both render in the same location as Full would have; request failure → focus moves to the Request Failure Panel's heading, since this genuinely interrupts the expected flow; opening/closing disclosures → focus remains on the toggle button, `aria-expanded` updates.

**Keyboard navigation:** every control operable via `Tab`/`Shift+Tab`/`Enter`/`Space`; no custom widget requires arrow-key interaction (nothing in this spec needs a composite ARIA widget — no tabs, no listbox, no slider).

**Motion reduction:** decorative assembly motion in the transition panel is removed entirely under `prefers-reduced-motion`; status changes remain immediate; no delayed fades anywhere; all information present in the motion-enabled version remains present (`MOTION_SYSTEM.md`'s Reduced Motion Accessibility, already implemented globally as of U-02 — this specification introduces no new motion the existing global rule doesn't already cover).

**Contrast:** every text/background, icon, border, and focus-ring pairing meets `docs/05-ux/ACCESSIBILITY.md`'s ratios (4.5:1 body text, 3:1 large text/non-text) in both light and dark mode, using the already-canonical `DESIGN_TOKENS.md` values (U-02, Product-Office-accepted).

**Zoom and text scaling:** single-column layout at every breakpoint (§35) means 200% zoom and increased text size degrade gracefully by construction — nothing here depends on fixed-width multi-column layout that could overlap or clip.

Visible without obscuring navigation — not a fixed/sticky element competing with the row list.

### Open Behaviour
On open: focus moves to the drawer's close control (the first meaningful element, consistent with `ACCESSIBILITY.md`'s Focus States — never silently moved without a clear reason, and opening a drawer is a clear reason); background content becomes inert (not focusable, not announced); background scroll stops; the drawer is announced as a navigation landmark (`role="navigation"` or `<nav>`, with an accessible label e.g. "Main menu"); the current page stays visually recognisable behind a subdued overlay (`opacity-overlay`, `DESIGN_TOKENS.md`); no underlying layout reflow. Motion: short horizontal slide + overlay opacity fade, `duration-deliberate` (300ms per `DESIGN_TOKENS.md`'s scale, within the addendum's 200–300ms guidance), `ease-entrance`. No spring, bounce, overshoot, or full-screen spinning transition (`MOTION_SYSTEM.md`'s existing prohibitions apply directly, not newly invented here).

### Close Behaviour
Closes via: the visible close control; selecting a navigation destination; `Escape`; activating the overlay. After closing: focus returns to the menu trigger (`ACCESSIBILITY.md`'s "a modal or drawer must return focus cleanly to the element that opened it on close" — already an existing accessibility rule, applied here); page scroll position is unchanged; no duplicate announcements.

### Reduced Motion
Slide animation removed entirely; drawer shows/hides via an immediate or minimal-opacity transition; all interaction and focus behaviour preserved unchanged; navigation access never depends on animation completing (`MOTION_SYSTEM.md`'s Reduced Motion Accessibility, already globally implemented as of U-02 — this introduces no new motion category the existing global rule doesn't already cover).

### Mobile Safe-Area Treatment
The drawer's top/bottom padding respects device safe areas (notches, home indicators) — a standard viewport-safe-area accommodation, specified as behaviour only, not as framework-specific implementation (per the source addendum's own instruction: "Do not describe implementation libraries or framework-specific code").

### Relationship to the Analysis Report
Opening the drawer from an Analysis Report screen preserves: scroll position, expanded disclosure states (§24), and the current analysis state (Full/Limited/Unavailable) — the customer returns to exactly where they were after closing, with no reload or reset. The drawer is a navigation layer over the report, never a new report state, and never interrupts the report's own progressive-disclosure model (§24).

### Accessibility (drawer-specific, additive to §36)
Semantic `<nav>` landmark with an accessible label; accessible label on the close button; focus containment while open (`Tab`/`Shift+Tab` cycle within the drawer only); `Escape` closes; `aria-expanded` on the trigger; `aria-controls` linking trigger to drawer; `aria-current="page"` on the active destination; background content marked inert (or equivalently inaccessible to assistive technology) while open; screen-reader reading order matches visual order (header → primary navigation → account → supporting → footer action); text/icon contrast per `ACCESSIBILITY.md`'s ratios; 44×44px minimum touch targets throughout; visible keyboard focus on every interactive element.

## 45. Tablet and Desktop Navigation

The source inspiration is mobile-specific; it must not override the already-approved desktop behaviour in `docs/05-ux/RESPONSIVE_RULES.md`.

**Mobile:** the full-height drawer specified above (§42–§44).

**Tablet:** per `RESPONSIVE_RULES.md`'s existing, unchanged rule — "horizontal nav bar retained if all primary destinations fit; otherwise collapses to the mobile pattern early." Where it collapses, it uses the same drawer specified here (not a separate side-sheet variant, to avoid maintaining two navigation patterns for no clear benefit — a wider side-sheet is permitted only if a future usability finding justifies the added complexity; not specified as needed today).

**Desktop:** retains the existing, already-implemented full horizontal navigation bar (`RESPONSIVE_RULES.md`: "full horizontal nav bar with all primary destinations visible"). The drawer pattern is **never** used on desktop, including as a stylistic choice for visual consistency with mobile — the customer must not lose navigation efficiency on larger screens.
