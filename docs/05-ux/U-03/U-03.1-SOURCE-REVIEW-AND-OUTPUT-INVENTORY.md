## 7. Executive Summary

The repository contains **enough approved mathematical and architectural information to begin designing most of U-03**, but **not enough approved product/UX decision on several customer-facing concepts** the U-03.1 directive specifically asked about. This is not a repository-quality problem — it is an accurate reflection of where the product genuinely is: the Risk Engine (deterministic mathematics) is fully implemented and internally consistent; the *presentation* of its output to a customer has not been designed or approved at all yet (no report screen exists in any form).

**Clearly available** (implemented, internally consistent, directly evidenced):
- The full Risk Engine output contract — every factor, score, band, reason code, data-quality score/band, and the three-tier analysis-availability gate — is implemented, tested (317/317 passing at time of review), and traceable to `docs/03-data-science/RISK_RULE_SET_2026_1.md`.
- The persisted record (`SlipAnalysis`/`LegAnalysis`) that any future report screen would read from — every column is known and stable.
- The betting-slip lifecycle (Draft/Ready/Analysed/Archived) and analysis-eligibility rules.
- The full UX Constitution (14 documents) governing how *any* screen must look, behave, and read.

**Ambiguous or unresolved** (a real decision is missing, not merely undocumented):
- **Rule Set 2026.1 itself is still `Proposed`, not `Accepted`** (`docs/00-governance/DECISION_LOG.md`, 2026-07-24 entry, unchanged as of this review). The mathematics U-03 would present are not yet formally approved for production use — a governance fact, not an engineering defect (see §8).
- **Weakest-selection presentation has zero implementation** — `docs/00-governance/PRODUCT_GLOSSARY.md` defines "Weakest Leg" as an approved *concept*, but `RISK_RULE_SET_2026_1.md` §G states explicitly "no weakest-leg implementation," and this review found zero code (not even partial) anywhere in `app/`. This is the single largest gap for U-03: `UX_RULES.md`'s Risk Report Hierarchy names "Weakest leg" as its third stage, and `EXPLAINABILITY_SYSTEM.md`'s own Explanation Hierarchy marks it "today: the top contributing factor" as a stated placeholder — the UX Constitution already anticipated this gap, it did not overlook it.
- **Recommendations have zero implementation and are explicitly reserved.** `docs/00-governance/DECISION_LOG.md`'s 2026-07-25 entry names "Recommendations" among concepts that "remain intentionally undefined and must not be implemented without separate Product Office approval."
- **No route displays a completed analysis to a customer at all.** `history` and `journal` are both literal `coming-soon` placeholders; there is no report/analysis-detail route in `routes/web.php` today.
- **Whether the numeric data-quality score (0–100) is ever shown to a customer, versus only its band, is undecided** — no UX document addresses this.

**No governance conflicts were identified** — every enum, threshold, and reason code found in code matches `RISK_RULE_SET_2026_1.md` exactly (see §23, Conflict Register, which is consequently short). The gaps above are *absences* of a decision, not *contradictions* between two existing decisions.

**Escalation is required before U-03.2** for exactly the items listed in §24 — none of them block starting U-03.2's storyboard work for the parts of the Analysis Experience that don't depend on weakest-selection or recommendations (the full/limited/unavailable score presentation, the explainability hierarchy for contributing factors, data quality, and Rule Set metadata are all fully specified). See §26 for the exact readiness classification.

## 9. Analysis Lifecycle Inventory

Two genuinely distinct, non-interchangeable status concepts exist in the implementation. Conflating them would be a real design error, so both are recorded fully.

**A — `BettingSlipStatus`** (`app/Domain/BettingSlip/BettingSlipStatus.php`): the *slip's own* lifecycle, before and after analysis.

| Stage | Internal Status | Customer-Visible Status | Trigger | Exit Condition | Retry Possible | Source |
|---|---|---|---|---|---|---|
| Draft | `draft` | "Draft" (badge, slip index — confirmed shipped UI) | Slip created | `markReady()` or `archive()` | N/A (editable indefinitely) | `BettingSlipStatus.php`; `resources/views/livewire/betting-slips/index.blade.php` |
| Ready | `ready` | "Ready" (badge) | `markReady()` from Draft or `returnToDraft()` reversal | `AnalyzeBettingSlip::execute()` succeeds → Analysed; or `returnToDraft()`; or `archive()` | Yes — can return to Draft | `BettingSlipStatus.php:36-44` (`allowedTransitions()`) |
| Analysed | `analysed` | "Analysed" (badge) | Successful `AnalyzeBettingSlip::execute()` | `archive()` only — **terminal for editing, no path back to Ready** | No — `Analysed→[Archived]` only | `BettingSlipStatus.php:36-44`; `docs/adr/ADR-007-ANALYSIS-PERSISTENCE-BOUNDARY.md`'s "Known Gap" section (re-analysis not reachable) |
| Archived | `archived` | "Archived" (badge) | `archive()` from any non-terminal status | None — terminal | No | `BettingSlipStatus.php:36-44` |

**B — `AnalysisAvailability`** (`app/Domain/Risk/Results/AnalysisAvailability.php`): the *outcome* of running analysis on a Ready slip — a separate concept, produced once, at the moment `Ready→Analysed` happens.

| Stage | Internal Status | Customer-Visible Status | Trigger | Exit Condition | Retry Possible | Source |
|---|---|---|---|---|---|---|
| Full | `full` | **Not yet defined in UX Constitution** — no explicit customer label found for this state name; implicitly "just show the score" | Gate passes both Tier 1 and Tier 2, Tier 3 band is Strong/Good | N/A — persisted, terminal per-analysis | N/A | `AnalysisAvailability.php`; `RISK_RULE_SET_2026_1.md` §17 |
| Limited | `limited` | Not yet defined; `EMPTY_STATES.md` has no dedicated "Limited Analysis" entry (only "Unavailable Analysis" and "Unsupported Sport" are defined states) | Tier 2 unrecognized-proportion >0% and ≤25%, or Tier 3 deduction score lands 40–64 | N/A — persisted, terminal | N/A | Same |
| Unavailable | `unavailable` | "We couldn't analyze this slip." (`EMPTY_STATES.md`'s Unavailable Analysis entry — approved copy exists) | Tier 1 sport hard-gate, or Tier 2 >25% unrecognized, or Tier 3 Insufficient | N/A — persisted, terminal per-analysis. **Correction, 2026-07-25 (see `DECISION_LOG.md` PD-10):** this row previously stated the slip "stays Ready, not Analysed"; verified false during U-03 implementation — `AnalyzeBettingSlip::execute()` calls `markAnalysed()` unconditionally for all three availability outcomes, same as Full and Limited | No — editing is not reachable for any completed analysis outcome under today's lifecycle (`Analysed→[Archived]` only) | `DetermineAnalysisAvailability.php`; `AnalyzeBettingSlip.php`; `EMPTY_STATES.md`'s "Unavailable Analysis" / "Unsupported Sport" entries |

**Internal-only states not customer-exposed**: `NormalizationStatus` (`Complete`/`Partial`/`Unrecognized`/`Unsupported` — a per-leg normalization classification, `app/Domain/Risk/Taxonomy/NormalizationStatus.php`) drives the gate but is never itself a customer-visible status; it surfaces only indirectly through `AnalysisAvailability`/`DataQualityBand` and specific reason codes.

**States asked about in the U-03.1 directive that do NOT exist in this repository, confirmed by direct grep and file review**: `submitted`, `accepted`, `queued`, `validating`, `parsing`, `analysing` (as a distinct pending/in-progress persisted state), `partially completed` (as a distinct status word — the closest concept is `Limited` availability, not a lifecycle stage), `failed`, `expired`. **Analysis in this codebase is synchronous** — `AnalyzeBettingSlip::execute()` runs to completion inside one request/transaction (confirmed: `app/Actions/Analysis/AnalyzeBettingSlip.php`, no job/queue dispatch, no `ShouldQueue` anywhere in `app/Actions/Analysis/`). There is no queued/processing/retry-after-failure lifecycle to design for today — see §22.

Answering the directive's specific verification questions:
- **Selection-level or slip-level?** All six factors are slip-level (computed once per slip, not once per leg) — confirmed by every factor class's single `calculate(NormalizedBettingSlip $input): FactorResult` signature.
- **Can multiple factors apply simultaneously?** Yes — all 6 are always computed for every slip (`CalculateStructuralRisk.php`'s pipeline has no early exit); a slip's `factorResults` array always has exactly 6 entries.
- **Do factors have severity?** Indirectly, via which reason code(s) fired (Low/Medium/High per Rule Set §18's table) — there is no separate numeric or enum "severity" field on `FactorResult` itself.
- **Do factors have ordering?** Not encoded in data — `factorResults` is a PHP associative array keyed by factor code (`RF-001`..`RF-006`); any display ordering is undecided (§24).
- **Do factors include approved explanations?** No — see the Risk Engine Output Inventory's "Factor description" row (§10): only internal trace notes exist, no customer copy.
- **Do factors include approved recommendations?** No — see §17.
- **Can factors be absent?** No — always all 6, but RF-005 can appear in `factorsNotEvaluated` (a separate array) when no leg has a known complexity.
- **Can factors be unavailable due to missing data?** Only RF-005, and only in that one specific circumstance (empty known-complexity pool) — this is the *only* documented case of a factor being flagged as not meaningfully evaluated; RF-006 is a different case (deliberately, permanently inactive, not "missing data").

No customer labels were invented for this register, per the directive's explicit instruction (§12: "Do not create new labels... The purpose is inventory, not UX transformation").
