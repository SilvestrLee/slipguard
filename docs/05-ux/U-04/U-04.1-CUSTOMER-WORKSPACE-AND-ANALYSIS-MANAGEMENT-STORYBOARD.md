## 1. Executive Summary

The Customer Workspace is where a customer goes after signing in to browse everything SlipGuard has already produced for them — completed analyses and their own reflections on them — and to decide what to do next. It is not a new capability so much as the organisation of two things that already exist in the repository as unbuilt placeholders: `history` and `journal` (both `coming-soon` today, `routes/web.php`). Nothing here performs analysis; every screen in this milestone reads persisted data only, the same boundary U-03's Report screen already established (ADR-007).

**Core customer outcome:** a returning customer should be able to answer "what have I already analysed, and what did I decide about it?" within a few seconds of arriving, using only already-existing product vocabulary (`docs/00-governance/PRODUCT_GLOSSARY.md`: Journal — "a simple record of what the user decided and what they later learned").

- The Dashboard's existing Recent Analyses section (U-02) already establishes the Analysis Card pattern in production; this milestone extends it into a full list, it does not introduce a new visual language.

## 3. Experience Principles

Same six as U-03 (§10 of `U-03.2`), restated for continuity, not reinvented:

1. **Clarity before completeness** — the workspace shows what's needed to decide what to do next, not everything at once.
2. **Explanation before mathematics** — n/a here (no scores are computed), but Journal entries never present the customer's own note as if it were a system-generated insight (`COMPONENT_PRINCIPLES.md`'s Journal Cards anti-pattern).
3. **Transparency without alarm** — an empty workspace is normal for a new customer, never framed as a deficiency.
4. **Structural risk, not outcome prediction** — Analysis Cards never restate or re-derive a score; they show the persisted band, unchanged (ADR-007).
5. **Calm over excitement** — no streaks, no "day 1," no gamified organisation (`PRODUCT_GUARDRAILS.md`).
6. **Mobile first** — the workspace's information order is identical across breakpoints; desktop adds spacing, not new structure.

## 4. Customer Journey

```text
Sign in
   ↓
Dashboard (existing, U-02)
   ↓
Workspace entry (Analyze Slip / History / Journal — existing nav, U-03's drawer)
   ↓
┌──────────────┬───────────────────┐
History         Journal
   ↓                 ↓
Browse completed   Browse own entries
analyses (Analysis  (Journal Cards)
Cards)
   ↓                 ↓
Open a report      Open/add an entry
(existing report   linked to an
screen, U-03 —     analysis
no re-analysis)
   ↓                 ↓
Exit: back to workspace, or continue to Analyze Slip
```

No queue, sync, or async stage is introduced — History and Journal are both simple, synchronous list reads.

### Journey states covered

| State | Behaviour |
|---|---|
| First-time customer, no analyses | Both History and Journal show `EMPTY_STATES.md`'s existing empty states, CTA to Analyze a slip |
| One analysis, no journal entries | History shows one card; Journal shows "No Journal Entries," CTA "Add a journal entry" |
| Multiple analyses, some journalled | History shows all cards, newest first; Journal shows only entries that exist, each linked to its analysis |
| Analysis exists, customer wants to add a journal entry | Reachable from the Report screen's exit actions (see §16, OI-02) or from Journal directly |
| Archived slips | A slip's own status (`Draft`/`Ready`/`Analysed`/`Archived`) is independent of whether it has an analysis; History shows analyses, not slip status — an archived slip's prior analysis remains visible and reopenable, since the analysis record itself is never deleted (`SlipAnalysis` has no delete path today) |

## 5. Workspace Information Architecture

The "Customer Workspace" is not a fifth new page — it is the existing authenticated navigation structure (Dashboard, Analyze Slip, History, Journal — already in both the desktop nav and U-03's mobile drawer) treated as a coherent whole for design purposes. This milestone's actual new screens are **History** and **Journal**; Dashboard and Analyze Slip are unchanged (out of scope, already delivered).

```text
Dashboard (existing)
├── Analyze Slip (existing)
├── History (this milestone — replaces coming-soon)
│     └── Analysis Report (existing, U-03 — reused, not modified)
└── Journal (this milestone — replaces coming-soon)
      └── Journal Entry detail/edit (this milestone)
```

**Entry points:** primary nav (desktop + mobile drawer, unchanged labels/routes), Dashboard's "Recent Analyses" cards (currently non-interactive per U-02's own scope note — this milestone is what makes them link somewhere real, into History's same report-opening behaviour).

**Exit points:** Analyze Slip (new analysis), Dashboard (return), the Report screen's existing exit actions (unchanged, PD-09/PD-10 compliant — no "Edit this slip" anywhere).

## 6. Screen Inventory

### 6.1 History

| Field | Value |
|---|---|
| Purpose | Browse all completed analyses |
| Entry conditions | Authenticated; reachable from nav at any time |
| Primary information | A reverse-chronological list of Analysis Cards (`COMPONENT_PRINCIPLES.md`) |
| Primary action | Open a card → the existing Report screen |
| Secondary action | Analyze a slip (if the list is non-empty, a lightweight persistent link; if empty, the primary CTA per `EMPTY_STATES.md`) |
| Customer objective | "What have I already had analysed?" |
| Empty state | `EMPTY_STATES.md`'s "No History," verbatim |

### 6.2 Journal

| Field | Value |
|---|---|
| Purpose | Browse and record reflections on completed analyses |
| Entry conditions | Authenticated; reachable from nav at any time |
| Primary information | A single column of Journal Cards (`COMPONENT_PRINCIPLES.md`), each referencing its linked analysis |
| Primary action | Add a journal entry (linked to an analysis) |
| Secondary action | Edit an existing entry inline (per Journal Cards' own interaction rule) |
| Customer objective | "What did I decide, and what did I learn?" |
| Empty state | `EMPTY_STATES.md`'s "No Journal Entries," verbatim (its own two-variant CTA: "Analyze a slip" if none exist, "Add a journal entry" if analyses exist but no entries do) |

### 6.3 Journal Entry (add/edit)

| Field | Value |
|---|---|
| Purpose | Record or update one reflection |
| Entry conditions | From Journal's own "Add" action, or from a specific analysis (see OI-02) |
| Primary information | A reference to the linked analysis (read-only — cannot be changed after creation, avoiding an entry silently detaching from its context) and a free-text reflection field |
| Primary action | Save |
| Secondary action | Cancel / discard |
| Customer objective | Write down a decision or a lesson while it's still fresh |

No "Analysis Detail" screen is separately specified — reopening an analysis from History uses the **existing Report screen unmodified** (§7).

## 7. Analysis Detail Access

Per the directive's explicit requirement: opening a card from History must communicate, without ambiguity, that **no analysis is being performed** — this is the same, already-persisted report the customer received at submission time. This is already true of the existing Report screen (it reads `$bettingSlip->analysis` only, per ADR-007) — History simply needs to link to it correctly, the same way U-03.3's Stage 5 already fixed the slip index's own "View" link to do. No new screen, no new behaviour, no new copy beyond the existing Report screen's own "Analysed :time" timestamp (already communicates this was a past event, not a live one).

## 8. Loading States

Both History and Journal are simple synchronous database reads (no external calls, no queued work) — the same category as the existing slip index and Dashboard. No dedicated loading storyboard is needed beyond what `MOTION_SYSTEM.md`'s general Loading Behaviour already covers (a brief, honest, non-fabricated wait with no invented progress stages, consistent with U-03's PD-07 precedent). No new motion pattern is introduced.

## 9. Error/Recovery States

- **Request failure** (page fails to load): `EMPTY_STATES.md`'s existing "Network Failure"/"Unexpected Error" entries, reused verbatim (same pattern U-03.2 §21.13 already established for the Report screen).
- **Permission denied** (attempting to open another customer's analysis or journal entry): `EMPTY_STATES.md`'s existing "Permission Denied" entry, reused verbatim — enforced server-side the same way `SlipAnalysisPolicy` already does for the Report screen; a `JournalEntryPolicy` following the identical ownership convention (`UserPolicy`'s established pattern) would be Architecture/Engineering's job to define, not UX's.

No new error states are needed — every case maps to an already-approved `EMPTY_STATES.md` entry.

## 10. Responsive Specification

**Mobile (primary):** single-column list for both History and Journal (Journal is *always* single-column per its own existing component rule; History's Analysis Cards already stack to full-width single column below tablet). Cards are full-width, 44×44px+ tap targets (whole-card click target, per `COMPONENT_PRINCIPLES.md`).

**Tablet:** identical order and column count to mobile; increased padding/spacing only, within `container-standard`.

**Desktop:** identical order and column count — **History does not become a grid or a table.** `COMPONENT_PRINCIPLES.md`'s Analysis Cards rule ("never presents the full Risk Report Hierarchy... a card is a summary") extends naturally to the list level: a scannable single column, not a dense multi-column dashboard. `container-standard` (960px) bounds History's width; `container-narrow` (640px) bounds Journal's, consistent with its "personal, reflective content" framing.

No new breakpoint behaviour beyond what `RESPONSIVE_RULES.md` already specifies for lists of cards.

---

## 11. Accessibility Specification

- One page-level `<h1>` per screen ("History" / "Journal"), landmark `<main>` (inherited from the shared layout, already implemented).
- Each Analysis Card and Journal Card is a real link/button (whole-card click target — implemented as an `<a>` wrapping the card content, not a `<div onclick>`).
- Risk band on each Analysis Card: label + icon, never colour alone (already the established, tested pattern from the Dashboard's own Recent Analyses cards, U-02).
- Journal Card's own note vs. system text distinction: different text weight/label, never colour alone (`COMPONENT_PRINCIPLES.md`'s own accessibility rule for this component).
- Journal Entry form: visible `<label>` on the reflection field (never placeholder-as-label, per this repository's existing form convention, `security-authorization`/form conventions already established in the slip builder).
- Empty states: real text, not baked into an image (already `EMPTY_STATES.md`'s standing rule).
- Reduced motion: no new motion is introduced; the existing global `prefers-reduced-motion` rule (`resources/css/app.css`) already covers any transition used here.

## 13. Interaction Specification

- **History card:** whole-card click → Report screen (`wire:navigate`, matching the existing pattern). Hover/focus: elevation + border shift only (`MOTION_SYSTEM.md`'s Hover Behaviour), no colour-only feedback.
- **Journal card:** click → inline edit or a simple edit action (per `COMPONENT_PRINCIPLES.md`'s own rule — UX Studio does not mandate which of the two here; either is compliant, Engineering may choose based on form complexity once the entry field is scoped).
- **Add journal entry:** a single, clearly primary button; no destructive action anywhere in this milestone lacks a confirmation step (matching the slip index's existing delete-confirmation pattern).
- **Navigation:** unchanged — History/Journal already exist as nav destinations; this milestone changes only what renders behind them.

## 14. Engineering Notes

- Reuse the Report screen exactly as built in U-03 — do not create a second "read persisted analysis" view. History's card links point at the same `analyze.report` route.
- `JournalEntry` (or equivalent) persistence, its policy, and its relationship to `SlipAnalysis`/`BettingSlip` are Architecture Office's decision, not specified here (§16, OI-01) — this document assumes a journal entry references exactly one analysis, immutably, but does not prescribe the schema.
- No change to `AnalyzeBettingSlip`, the Risk Engine, or any persisted analysis field — this milestone is presentation and a new, additive Journal capability only.
- Dashboard's Recent Analyses cards (U-02) become genuinely interactive once the Report screen route exists for every listed analysis — it already does (U-03) — so this is a small, already-unblocked follow-up, not new scope.
