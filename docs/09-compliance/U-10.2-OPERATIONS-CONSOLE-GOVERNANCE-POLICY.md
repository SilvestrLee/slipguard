## 1. Executive Summary

Every one of `U-10.1`'s five Open Questions is resolved below (§8) as compliance policy — none required escalation to Product Office as a strategic question, since all five were access-control/retention/terminology judgements squarely within this office's Consulted-on-security-and-authorization remit (`docs/offices/COMPLIANCE_OFFICE.md`). The one area requiring genuine, deliberate caution is **Journal entries** (§3, Category B below) — a customer's own private reflections are qualitatively different from structural analysis data, and this policy restricts them further than `U-10.1`'s architecture implied by default.

## 2. Operations Permission Model (Area A)

**Policy: `is_internal` alone is insufficient. Operations Console access to customer data requires a distinct permission from general internal-staff status.**

Today's single `is_internal` flag correctly gates the Filament panel's existence, but conflates "can manage Labs feature content" (no customer PII involved) with "can view a specific customer's private betting history and Journal reflections" (materially more sensitive). Least privilege requires these be separable. This document does not prescribe the exact mechanism (a second boolean, a role column, a permission table) — that is Architecture's/Engineering's implementation choice — but the requirement itself is policy: **an internal user must not be able to view customer-specific data solely by virtue of `is_internal = true`; a second, explicit grant is required.**

Roles should reflect actual job function, not be invented speculatively: at minimum, distinguish "can view customer support data" from "can manage Labs content." Further subdivision (Support vs. Operations vs. Administrator, as the handover's own Area A suggests) is not mandated now — it should be introduced only when a real, distinct job function needs it, consistent with `PRODUCT_GUARDRAILS.md`'s general preference against speculative complexity.

## 3. Customer Data Visibility Policy (Area B)

| Category | Visibility | Rationale |
|---|---|---|
| Customer profile (name, email, registration date) | **Visible** | Necessary baseline for identifying the customer being supported. |
| Analyses (structural score, band, timestamp) | **Visible** | Already deterministic, already-computed structural facts — no more sensitive than what the customer themselves already sees in their own Report screen. |
| Planner sessions (status, revisions, exports) | **Visible** | Same reasoning as analyses — structural facts, not personal reflection. |
| Planning History | **Visible** | A read-only list over the same Planner session data already approved above. |
| **Journal entries** | **Restricted — not shown by default** | **Category B finding.** A Journal entry is the customer's own free-text reflection — closer to a private diary than a structural record. Defaulting to full visibility, as `U-10.1`'s architecture implicitly allowed by listing it alongside the other read models, treats a customer's private thoughts the same as a computed score. This document requires: Journal entry content is hidden from the default Customer Overview and only becomes viewable through a distinct, deliberate action (e.g. an explicit "View Journal" step within the console) — and that specific access must itself generate its own audit entry (§5), separate from and in addition to the general "customer record opened" event. This is a heightened-sensitivity category, not a blocked one — support staff may still need it for legitimate cases (e.g. a customer disputing what they recorded) — but it must never be incidentally visible while looking at something else. |
| Internal identifiers (database IDs) | **Visible** | Not customer-facing information; operationally necessary for support staff to reference specific records precisely. |
| Device/session metadata (IP, user agent, last activity) | **Visible, but presented only when relevant to the support task at hand** (see §6) | Already-retained operational data (§6), not newly collected; proportionate for troubleshooting, disproportionate to surface prominently on every customer's general overview. |

## 4. Support Notes Governance (Area C)

- **Who may create:** any Operations Console user holding the customer-data-visibility permission defined in §2.
- **Editability: none.** Notes are **append-only** once saved — this resolves `U-10.1`'s OQ-2 in favour of its own stated recommendation. A correction is made by adding a new note, never by altering the original. This mirrors this product's own already-established philosophy elsewhere (`SlipAnalysis`, `PlannerRegenerationEvent` — neither is ever mutated after creation) rather than inventing a new one for internal tooling.
- **Version history:** not applicable — append-only means there is nothing to version.
- **Deletion:** **never permitted**, for the same reason. A note that turns out to be wrong or no longer relevant is superseded by a later note, not erased — the support record's own integrity depends on this exactly as much as the customer-facing audit trail does.
- **Customer visibility:** never — restated from the handover's own instruction, not weakened here.

## 5. Audit Logging Policy (Area D)

**Mandatory fields, confirmed:** operator identity, action performed, affected customer, timestamp, originating IP (where available — already captured in the existing `sessions` table per `U-10.1` §2/§8, not new collection).

**Granularity (resolves `U-10.1`'s OQ-3):** audit at the **session-event level**, not the individual-field-view level. Opening a specific customer's record in the console is one auditable event ("customer record viewed"); it need not generate a separate row for every individual analysis or Planner session subsequently scrolled past within that same visit. **Exception:** per §3, viewing Journal entry content specifically is its own, additional audit event, given its heightened sensitivity — this is the one deliberate departure from pure session-level granularity, and it is deliberate, not an oversight.

**Before/after values:** not applicable to this initial scope — the console is read-only plus append-only notes; there is no "edit" action that produces a before/after pair. If a future Product Office decision ever introduces a genuine write/edit action to the console, that decision must include its own before/after audit requirement at that time — not retrofitted as an afterthought.

**Retention: indefinite, immutable.** Audit records are never deleted or altered after creation, matching this product's standing philosophy for every other historical record it keeps (`SlipAnalysis`, `PlannerRegenerationEvent`, and now `SupportNote`, §4). An audit trail that could itself be edited or purged defeats its own purpose.

## 6. Operational Diagnostics Policy (Area E)

| Item | Determination |
|---|---|
| IP address | **Proportionate — approved.** Already retained by the existing `sessions` table for ordinary session-management reasons; using it for the narrower, legitimate purpose of customer support is not new collection, only a new authorized viewer of data that already exists. |
| Browser / user agent | **Proportionate — approved.** Same reasoning as IP address. |
| Session identifiers | **Proportionate — approved.** Necessary to correlate a reported issue with an actual session. |
| Operating system | Derivable from the same `user_agent` string already covered above — no separate collection or policy needed. |
| Application version | **Deferred**, resolving `U-10.1`'s OQ-5 as that document itself recommended. No concrete support scenario has yet demonstrated a need for it; revisit if Engineering identifies a real case, rather than building it speculatively now. |
| Request identifiers | **Deferred**, same reasoning — this would require new instrumentation (a correlation-id mechanism) that does not exist anywhere in this application today; not proportionate to build for a hypothetical need. |

"Support Note," "Operations Log" / "Audit Entry," and "Customer Timeline" are all confirmed appropriate — neutral, professional, accurately descriptive of internal tooling, and none collide with any customer-facing term this product already uses in a conflicting sense. No renaming required.

None of the above required escalation. One item is named for Product Office awareness, not decision, since it is a scope/prioritization question rather than a compliance judgement: whether the Journal-entry access restriction in §3 should also apply retroactively to any future export/reporting feature built on top of the Operations Console — this document's restriction covers only the console itself as currently architected.

## 10. Compliance Recommendations for Engineering Implementation

- Implement the customer-data-visibility permission (§2) as a genuine, separate authorization check — not merely a UI-level hide, since `U-10.1` §4's own independent-authorization architecture already requires this discipline.
- Journal entry content (§3) must require its own explicit view action and its own audit row — a generic customer-overview page load must not eagerly load Journal entry text alongside everything else, even if technically convenient.
- `SupportNote`'s append-only rule (§4) should be enforced at the model level (no `update`/`delete` action exposed anywhere), not merely by UI omission — consistent with how `JournalEntryPolicy` already enforces its own no-delete rule at the authorization layer, not just by hiding a button.
- Audit log immutability (§5) should be enforced the same way `PlannerRegenerationEvent` already is — no `updated_at` column, no update path in any action.
