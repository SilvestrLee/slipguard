## 0. The one principle every decision below is checked against

This framework decides **structural suitability within customer-stated constraints and available evidence** — never likelihood of winning. Every rule below was tested against a single question before being written down: *does this rule require knowing or guessing anything about which team is more likely to win?* Any rule that failed that test was rejected outright, not softened. This is the same discipline `CalculateStructuralRisk`/`RankLegsByStructuralWeakness` already apply to Capability A, extended here to a genuinely new problem (constructing a candidate, not just scoring one), not relaxed for it.

---

## 1. Executive framework decision

Capability B constructs a candidate through four cleanly separated stages — **eligibility** (may this leg exist in the candidate universe at all), **ranking** (among eligible legs, which order do we consider them in), **construction** (assemble a combination satisfying the brief), and **whole-slip evaluation** (the existing, unmodified Risk Engine has final say). No stage ever asks "which team will win." The construction algorithm is a bounded greedy assembly with limited deterministic replacement — not a search, not an optimiser, not a model.

---

## 2. Input contract confirmation (§43.2)

**Mandatory planning-brief fields**: competitions (must be a non-empty subset of the enabled allowlist, `U-17.5` §1: Premier League/La Liga/Serie A for MVP), planning window (1–7 days, per `U-17.1`'s own MVP boundary), leg count (see §12 — a real, smaller-than-20 MVP range, not the full Builder ceiling), allowed markets (a non-empty subset of the five **default-enabled** families in §7).

**Optional fields**: target combined-odds range, structural-risk ceiling (defaults to the existing `RiskBand::High` if unset — never silently defaults to "no ceiling," since an unconstrained ceiling isn't a real customer choice, it's an omission), excluded competitions/markets/fixtures.

**Deliberately not in the MVP input contract**: evidence-quality minimum (hard-coded to `Fresh`-only, §13 — not customer-configurable, since a customer lowering this threshold would be choosing to receive weaker evidence without understanding the tradeoff), fixture-diversity/competition-diversity constraints beyond the allowlist itself (§15/§16 — deferred, matching `U-17.1`'s own original MVP deferral of these exact fields).

## 3. Eligibility rule set (§43.3)

Deterministic, ordered, hard gates — a leg failing any rule is excluded with that rule's reason code, never silently dropped.

| Rule ID | Name | Gate |
|---|---|---|
| `CBE-001` | Competition Enabled | Competition must be on the verified, Product-Office-enabled allowlist (`U-17.5` §1) |
| `CBE-002` | Fixture Window | Kickoff must fall within the planning brief's window and not have passed |
| `CBE-003` | Fixture Status | Fixture must not be postponed, cancelled, or already completed |
| `CBE-004` | Market Family Verified | Market must be one of the seven `U-17.5`-confirmed families, and specifically one of the five default-enabled ones (§7) unless explicitly requested |
| `CBE-005` | Canonical Mapping Confidence | The provider's outcome strings must map unambiguously to a canonical selection (e.g. a Double Chance outcome string that doesn't parse cleanly into "X or Draw"-shape is excluded, not guessed at) |
| `CBE-006` | Evidence Freshness | Evidence quality must be `Fresh` (§13 — hard gate, not a ranking factor) |
| `CBE-007` | Odds Validity | Decimal odds must be present, numeric, and within the configured per-leg min/max (§9) |
| `CBE-008` | One Leg Per Fixture | A fixture already represented by a selected leg cannot contribute a second one (§14) |
| `CBE-009` | No Customer Exclusion | The leg's fixture/competition/market must not appear on the brief's own exclusion list |

Rules `CBE-001`–`CBE-004` run against the cheap, bulk-acquired evidence first (`U-17.5` §4's own sequencing) — this is a construction-framework requirement, not just an acquisition optimisation, since it means the expensive per-event evidence is never even requested for a fixture that was always going to fail an early gate.

## 4. Quote-selection method (§9 of the commission, a real decision grounded in real trial data)

**Recommended: Option C — Conservative (lowest valid) available quote**, not Option A (a single configured reference bookmaker).

**Why, with the actual evidence**: `U-17.3`'s real per-market trial samples returned a *different* bookmaker for nearly every market family inspected — Pinnacle for `h2h`, 1xBet for `btts` and `double_chance`, Coral for `draw_no_bet`. No single bookmaker was present across all seven confirmed families in the real data this framework has to work with. A configured single reference bookmaker (Option A) would therefore leave several market families with no usable quote at all on a real request, defeating the purpose of choosing it for consistency. The conservative-lowest approach requires no single bookmaker to cover everything, is fully deterministic (no ties possible in practice, and where they occur, the earliest-alphabetical bookmaker key wins as a stable, arbitrary-but-reproducible tiebreak), and is the option least likely to overstate a candidate's combined odds to the customer — a real compliance-adjacent benefit, not just a mathematical convenience.

## 5. Combined-odds calculation (§17)

Product of every selected leg's decimal odds, calculated with `brick/math`'s `BigDecimal` (matching `ADR-002`'s existing "fixed-precision decimals, never floats" rule — no new precision policy invented here), retained at full internal precision, displayed rounded to 2 decimal places. The exact per-leg quotes used are preserved on the candidate snapshot (`U-17.5` §5) so the calculation is always reproducible after the fact, even if the provider's own live price later changes.

## 6. Structural-risk integration (§43.8, §20, §21)

The existing, unmodified `CalculateStructuralRisk`/`RankLegsByStructuralWeakness` engine has final authority — this framework never recreates or approximates it. Sequence:

```
1. Assemble a provisional candidate (greedy, §11)
2. Convert to the existing NormalizedBettingSlip shape (no new normalization logic — reuse NormalizeFootballMarket unmodified)
3. Run the real, existing engine
4. If structural score exceeds the brief's risk ceiling (or the default High-band ceiling):
   a. Identify the weakest contributor via the existing RankLegsByStructuralWeakness output (no new ranking math)
   b. Replace it with the next-ranked eligible, not-yet-tried leg for that same fixture slot
   c. Re-run the engine
   d. Repeat up to 3 replacement attempts (bounded — not exhaustive search)
5. If still over ceiling after 3 attempts: return No-Valid-Candidate (CBR-004, §17)
```

Three attempts is a deliberately small, arbitrary-but-bounded number, chosen to keep construction cheap and explainable (every attempt is a real, loggable event) rather than searching until something satisfies the ceiling — the latter risks producing a candidate technically inside the ceiling but built by trying many combinations, which is harder to explain honestly to a customer than "this is what emerged from three straightforward attempts."

## 7. Market-family policy (§43.10, §33, §34) — a real, specific decision per family

| Market family | MVP treatment | Reasoning |
|---|---|---|
| Match Result | Default-enabled | Simple, two-or-three-outcome, widely understood |
| Double Chance | Default-enabled | Simple derivative of Match Result, low structural complexity |
| Draw No Bet | Default-enabled | Simple, two-outcome |
| Total Goals | Default-enabled | Well-understood, single line value, already a core Capability A market |
| Both Teams to Score | Default-enabled | Simple Yes/No, well understood |
| Half-Time Result | **Opt-in only** — eligible only when the planning brief explicitly requests it, never included by default | Real trial data (`U-17.3`) showed inconsistent bookmaker coverage for half-scoped markets at longer lead times; less familiar to a typical customer than the five defaults |
| Correct Score | **Excluded from construction entirely for this MVP** — remains available for Capability A's own customer-supplied-slip analysis (`FootballMarketTaxonomyV1` already includes it there, unchanged), but this framework never selects one automatically | Structurally narrow (many possible outcomes, each individually low-probability by nature of the market's own design, not because SlipGuard is predicting anything) — automatically including a market this specific in a system-constructed candidate risks reading as SlipGuard picking a specific outcome, which is a materially different optics and risk profile than a customer choosing it themselves. A cautious, reversible exclusion, not a permanent architectural one. |

## 8. Ranking rule set (§43.4, §11)

Legs that pass every eligibility gate are ordered by (in this fixed priority order, never reweighted per-request):

1. **Evidence freshness recency** — more recently retrieved evidence ranks first (a tiebreak-quality signal, not a prediction one)
2. **Canonical mapping confidence** — an exact, unambiguous outcome-string mapping ranks above one requiring more parsing (ties into `CBE-005`)
3. **Planning-brief market preference order** — if the customer's brief lists markets in a specific order, legs matching an earlier-listed market rank first
4. **Deterministic tie-break** — fixture kickoff time (earlier first), then fixture ID (ascending)

**Explicitly and permanently absent from this list**: any notion of team strength, form, historical head-to-head record, or implied probability — matching §11/§31's own prohibition list directly, not merely avoiding it by omission.

---

## 9. Odds validity bounds (§8.5)

Per-leg minimum 1.10, maximum 15.00 decimal odds for MVP — bounds chosen to exclude both near-certain, structurally uninteresting legs (odds near 1.00, which contribute almost nothing to combined odds or structural risk) and extreme long-shots (which the existing Risk Engine's own factor design already treats as high structural risk contributors, per `RISK_RULE_SET_2026_1.md`'s existing odds-based factors — this framework doesn't need a second, separate long-shot rule, just a sane construction-time bound so a single extreme leg can't dominate a target-odds calculation before the Risk Engine even runs).

## 10. Same-fixture, competition, and kickoff-time concentration (§14, §15, §16)

**Same-fixture**: one leg per fixture, hard rule (`CBE-008`) — the MVP recommendation from the commission's own §14 is adopted directly, since it removes an entire class of correlation-management complexity for a materially small product cost.

**Competition concentration**: no hard constraint for MVP — naturally bounded by the 3-competition allowlist and the small leg-count ceiling (§12) already limiting how concentrated a candidate can get. Revisit only if the allowlist grows materially.

**Kickoff-time concentration**: no constraint for MVP. `U-17.1`'s own architecture already flagged fixture-time distribution as a revalidation concern (`U-17.5` §9), not a construction-eligibility one — that's where it's handled, not duplicated here.

## 11. Construction algorithm (§43.5, §22)

**Bounded greedy, with limited deterministic replacement** — not a search, not an optimiser:

```
1. Rank all eligible legs (§8)
2. Take the highest-ranked leg not yet representing an already-used fixture
3. Add it to the provisional candidate
4. If leg count target not yet reached and eligible legs remain: repeat from step 2
5. If leg count target reached, or no further eligible legs exist: stop assembling
6. Run whole-slip structural evaluation (§6) — replace weakest contributor up to 3 times if over ceiling
7. Check combined odds against the brief's target range (§12)
   - within range or no target set: return candidate
   - outside range and legs remain that could adjust it: attempt ONE deterministic adjustment (swap the lowest-ranked included leg for the next-ranked eligible one) — not an unbounded search
   - still outside range: return the closest candidate achieved, clearly labelled as outside the requested target, OR return No-Valid-Candidate if the brief explicitly requires hitting the range — see §12
```

This reuses `U-17.1`'s and this commission's own explicit preference ("greedy or hybrid, bounded and explainable... do not introduce an optimisation solver without evidence it is necessary") verbatim, not a novel design.

---

## 12. Leg count and target odds (§19, §18)

**Leg count**: MVP range 2–8, default 5 if the brief doesn't specify — deliberately smaller than the Builder's existing 20-leg maximum. A system-constructed 15-20 leg accumulator would compound structural risk far beyond what a first, cautious construction capability should default to producing, and a smaller range keeps construction (§11) and explanation (§14 below) tractable.

**Target odds**: attempted, never forced over the risk ceiling (`ADR-012`-adjacent principle, adopted directly from the commission's own §18 binding principle: "target odds must never override the structural-risk ceiling or evidence-quality requirements" — this framework treats that as non-negotiable, not merely a preference). If no combination within the leg-count range satisfies both the target range and the risk ceiling, return **No-Valid-Candidate** with reason `CBR-002` (target unreachable within constraints) — never silently relax the ceiling to hit the odds target.

---

## 13. Evidence-quality treatment (§43.12, §12 of the commission)

Adopting the Product Office's own stated preference directly, since it is the more conservative and more defensible option:

```
Fresh        → Eligible
Stale        → Excluded (CBE-006 fails)
Conflicting  → Excluded (CBE-006 fails)
Unavailable  → Excluded (CBE-006 fails)
```

No MVP path allows Stale evidence into a constructed candidate. This is stricter than Capability A's own existing three-tier `AnalysisAvailability` gate (which has a genuine `Limited` middle state) — deliberately so, since Capability B is *originating* selections rather than evaluating ones the customer already committed to, a materially higher bar per `U-17.1`'s own repeated framing of Capability B as qualitatively different from Capability A.

---

## 14. Explainability contract (§43.15, §27)

For every included leg: which eligibility rules it passed (not just "it passed"), its rank position and the specific ranking dimension that placed it there, and its real contribution to combined odds. For every leg considered but excluded: the specific rule ID and plain-language reason (`CBE-001` through `CBE-009`, translated to customer language exactly as `ReasonCode` already is for Capability A's own reason codes — no new translation mechanism, the same pattern reused). For a `No-Valid-Candidate` result: the specific binding constraint (§17). Never a generated narrative sentence about either team — matching §27's own prohibition list directly.

## 15. No-valid-candidate reason register (§43.13, §26)

| Reason ID | Meaning |
|---|---|
| `CBR-001` | Insufficient eligible fixtures within the planning window/competitions |
| `CBR-002` | Target odds unreachable within the leg-count range and risk ceiling |
| `CBR-003` | Insufficient eligible legs after evidence-freshness/market filtering |
| `CBR-004` | Risk ceiling unreachable after 3 replacement attempts |
| `CBR-005` | Requested market(s) unavailable for the selected competitions/window |

Every reason maps to a specific, real gate in §3/§6/§12 — none is a catch-all "something went wrong."

---

## 16. Regeneration boundary (§29) — deliberately minimal, reusing Capability A's own machinery

**Before customer acceptance**: one full regeneration is permitted, re-running construction (§11) against the *same* already-acquired evidence snapshot (no new provider requests, no new request-credit cost) — excluding the fixtures/legs from the just-rejected candidate so a second attempt isn't identical. Editing the planning brief itself (different competitions, markets, leg count) always triggers a genuinely fresh construction run against re-acquired evidence.

**After customer acceptance**: regeneration as its own concept ends entirely — the accepted candidate is now an ordinary `Ready` `BettingSlip` inside an ordinary Planner session (`ADR-013`), and every further adjustment (remove, replace, lock, compare) uses the Planner's own existing, unmodified mechanisms. This framework does not need its own post-acceptance editing model at all — a direct, structural consequence of `ADR-013`'s boundary, not a separate design decision made here.

## 17. Rule versioning (§43.16, §38)

**Candidate Construction Rule Set 2026.1** — a fourth, independent version axis alongside the existing engine version, Rule Set 2026.1 (the structural-risk rule set itself, a different document), and market-taxonomy version, matching the deterministic-risk-mathematics skill's own "four independent version axes, never conflated" principle exactly. A constructed candidate snapshot (`U-17.5` §10) records this version alongside the structural-risk rule-set version it separately used in step 6 of §11 — two version numbers, never merged into one, since they can and will change independently.

## 18. Test scenario pack (§43.17, §40)

The commission's own Scenarios A–J (valid candidate; insufficient fixtures; target odds too high; risk ceiling exceeded with successful/failed replacement; stale evidence exclusion; one market missing; Correct Score requested while excluded — now confirmed as always excluded, so this scenario becomes "any excluded-market request returns `CBR-005`"; duplicate-fixture rejection; odds changed during revalidation; request budget exceeded) are all directly answerable by the rules above and are adopted as the Engineering-ready test pack without modification — each maps to a specific rule ID from §3/§6/§12/§15.

## 19. Data Science risk register (§43.18)

- **Correct Score's exclusion is a product-caution decision, not a mathematical one** — revisit only with explicit Product Office direction, not as a routine model update.
- **The conservative-lowest quote-selection method (§4) may understate real achievable combined odds** relative to what a customer could actually find by shopping bookmakers themselves — an honest tradeoff for determinism and compliance-safety, disclosed here rather than presented as the objectively "best" method.
- **The 3-attempt replacement bound (§6) and 1-attempt odds-adjustment bound (§11) are both arbitrary, chosen numbers**, not derived from any formal analysis — reasonable starting points for MVP, explicitly flagged as tunable once real usage data exists, not load-bearing mathematical constants.

## 20. MVP recommendation (§43.19)

Football only; Premier League/La Liga/Serie A; 1–7 day window; five default-enabled markets (Half-Time Result opt-in, Correct Score excluded); 2–8 legs, default 5; conservative-lowest quote selection; Fresh-only evidence; existing risk ceiling reused (defaults to High band); bounded greedy construction with ≤3 replacement attempts and ≤1 odds-adjustment attempt; one pre-acceptance regeneration; all post-acceptance editing via the existing, unmodified Planner.
