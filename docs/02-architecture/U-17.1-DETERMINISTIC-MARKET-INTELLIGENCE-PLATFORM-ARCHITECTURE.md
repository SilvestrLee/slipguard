## 0. Framing: what this document is and isn't

This is architecture discovery only. No provider is selected, no migration is written, no code changes. Per the commission's own §47, production integration, new mathematics, new UI, live fixture retrieval, and bet placement are all explicitly out of scope here.

Everything in this document is **conditional on one unresolved fact, stated plainly rather than designed around**: as of this writing, `docs/offices/PARSER_OFFICE.md` records that "SlipGuard has zero external evidence sources of any kind — no fixture database, no odds feed, no bookmaker integration exists anywhere in the repository," and that Parser Office's first real task, whenever commissioned, is *source discovery*, not source validation. `docs/02-architecture/U-06.1-ARCHITECTURE-DISCOVERY.md` (§R1, its risk register) already recorded this as a **blocking** finding for exactly this capability, and Product Office's own acceptance of that discovery (`PO-U06.1-AC-001`, 2026-07-26) explicitly deferred Capability B "to a future, separately-scoped programme" for precisely this reason. This document is that programme's architecture discovery — but discovery cannot manufacture a data source that doesn't exist. Every component below that depends on external evidence is designed as an **abstraction a real source can be plugged into**, not as a design that assumes one is already available. §1 makes this the first, load-bearing decision of the whole roadmap.

**Parser Office's U-06.3 (Data Availability & Parser Readiness) must run, and return a real, licensable, technically viable evidence source, before any component in §3 onward can be built** — not merely designed. `TASKS.md` already records U-06.3 as "not started (relevant only if/when Capability B is later authorized, which it has not been)." Architecture Office's job in this document is to make sure that whatever Parser Office eventually finds slots into a coherent platform without a redesign, not to pretend the source question is already closed.

## 2. Constitutional boundaries preserved

Verified directly against current code and governance before writing anything below, not assumed:

- **Programme U-07 is untouched.** `app/Actions/Planner/*`, `app/Domain/Planner/*`, `ADR-008`, `ADR-009`, and the `PlannerSessionStatus` lifecycle (`Draft → Evaluated ⇄ Evaluated → Complete → Exported`, `Abandoned`) are load-bearing and unchanged by this discovery. Capability B's only touchpoint with Capability A is the single integration boundary defined in §7 — everything upstream of that boundary is new, everything downstream is the existing, accepted Planner running exactly as it does today.
- **The deterministic Risk Engine is untouched.** `CalculateStructuralRisk`, `RankLegsByStructuralWeakness`, `FootballMarketTaxonomyV1`, and `NormalizeFootballMarket` remain the single authority for structural scoring. Capability B does not introduce a second scoring system — §7 requires every generated candidate to pass through the *same* engine Capability A already uses.
- **Locked Decisions (`CLAUDE.md`) are unaffected by this discovery and constrain every downstream implementation**: no outcome prediction, no "safe bet" claims, deterministic and explainable risk only, AI may explain but never determine suitability/ranking/selection order, customer money never enters SlipGuard, no autonomous betting, operator independence, regulatory simplicity by design (`ADR-012`). A market-wide construction pipeline is a new *candidate-sourcing* mechanism, not a new decision-making authority — the customer remains the sole acceptor of any generated accumulator, matching Capability A's own `PD-007` principle that the Planner never generates or discovers selections on the customer's behalf **for Capability A**; Capability B is the first and only capability permitted to originate a candidate, and only because SD-001 and this commission explicitly authorize it as a distinct, separately-governed mode — never silently blurred with Capability A's existing "customer supplies everything" contract.
- **Parser Office's existing mandate is respected, not duplicated.** This document does not attempt to rule on evidence-source viability, licensing, or freshness contracts — that is Parser Office's Accountable row per `AUTHORITY_MODEL.md`. Architecture Office's job here is the structure evidence flows through *once Parser Office says a source is viable*, not whether one exists.

## 5. Evidence store, not warehouse (§44.3, §44.4, §14)

The commission's own §14 asks Architecture to choose between a dedicated Evidence Warehouse, an operational evidence store, or a staged combination, and explicitly warns against "designing enterprise-scale infrastructure before provider volume or product usage requires it."

**Recommendation**: begin with an operational evidence store — plain, versioned database tables (fixtures, competitions, teams, markets, each with a `source_provider`, `source_id`, `acquired_at`, `effective_at`, `quality_state`, and a foreign key to whichever internal canonical entity it resolved to) — not a separate warehouse product, not a data lake, not a streaming pipeline. This mirrors this codebase's own established discipline: `SlipAnalysis`/`LegAnalysis` (`ADR-007`) and `PlannerRegenerationEvent` (`ADR-009`) are both "one row per fact, JSON-safe, no separate analytics store" — the same shape should carry over here rather than introducing a second persistence paradigm for one new capability.

"Evidence Warehouse" remains the correct **public, strategic name** for what this becomes once it's serving multiple consumers (§4's "future consumers" column) at real scale — the founder's own instruction during `PO-U07.X.1-001` confirmed this is intentional forward-looking language, not a claim that it exists. Architecture Office's recommendation is that the *first* implementation is simply "the evidence tables," and the Evidence Warehouse name is earned once genuine multi-consumer scale and a caching/freshness strategy (§9 below) make the warehouse framing accurate rather than aspirational.

### Evidence quality states (§13)

Reuse, don't reinvent: `App\Domain\Risk\Results\AnalysisAvailability` already gives this codebase a three-tier pattern (`Full` / `Limited` / `Unavailable`) for exactly this kind of "how much can we trust what we have" question. Recommend a parallel (not shared — evidence quality and analysis availability answer different questions) enum for evidence:

```text
EvidenceQuality: Fresh | Stale | Conflicting | Unavailable
```

`Conflicting` (two providers disagree) has no equivalent in the existing `AnalysisAvailability` enum and is new precisely because multi-provider reconciliation is new to this capability — everything else deliberately mirrors the existing pattern rather than inventing a fourth vocabulary for the same underlying concept of "how much can this be trusted."

## 6. Canonical identity and provider abstraction (§44.5, §11, §30)

A **Provider Adapter** interface (conceptually, not yet a written PHP interface) should expose only canonical shapes — `CanonicalFixture`, `CanonicalCompetition`, `CanonicalTeam`, `CanonicalMarket` — never a provider's own field names past the adapter boundary. This is the same discipline `ExtractPdfText`/`ParseSlipText` (the bounded-scope intake work, 2026-07-28) already applies to a different kind of external input: isolate the messy external shape at one narrow boundary, never let it leak into domain logic.

**Identity resolution is the single hardest unsolved problem in this whole document**, and Architecture Office should say so plainly rather than wave it away: two providers describing "Arsenal vs Chelsea, kicking off 15:00 Saturday" may use entirely different IDs, spellings, or even kickoff-time conventions (timezone handling, provisional vs confirmed kickoff). A canonical identity table with provider-to-canonical mapping rows (`provider_name`, `provider_id`, `canonical_fixture_id`) is the standard shape for this problem, but the matching *logic* (exact string match, fuzzy match, manual reconciliation queue) is genuinely undecided and should not be designed in detail until a real second provider exists to test cross-provider matching against. **Recommendation: build the mapping table now (cheap, low-risk), defer the matching algorithm until Parser Office names at least one real provider** — designing a fuzzy-matching algorithm against zero real payloads risks the same "solving a business problem with unproven complexity" pattern this codebase's own `WORKING_PRINCIPLES.md` already warns against for `NormalizeFootballMarket` (which deliberately uses exact alias matching, not fuzzy matching, for exactly this reason — see `docs/03-data-science/FOOTBALL_MARKET_TAXONOMY_V1.md`). The same discipline should carry over here: exact-match-first, escalate to manual reconciliation on failure, never guess.

This identity system should also strengthen — not duplicate — the Parser Office's existing customer-slip normalization (`FootballMarketTaxonomyV1`'s alias lists). A market alias table shared between "what a customer typed" and "what a provider calls this market" is one taxonomy, not two, per the commission's own §31 and this codebase's own single-source-of-truth discipline established repeatedly this session (`config/slipguard-product-facts.php`, `config/slipguard-planner-capabilities.php`).

## 7. The consequential decision: Planner integration boundary (§44.8, §24, §25)

This is the single most durable, code-relevant decision in this document, and the one Architecture Office recommends be formalized as an ADR (drafted below, `ADR-013`, status Proposed) rather than left as prose in a discovery document — matching exactly how `ADR-008`/`ADR-009` themselves originated as U-07's own discovery-phase boundary decisions.

**Decision**: A generated accumulator candidate never gets its own parallel session, revision, lock, compare, or export system. Once a customer accepts a generated candidate as their starting point, it enters the **existing** Planner exactly the way a customer-entered `BettingSlip` does today: a new `BettingSlip` row is created from the candidate's legs (reusing `SaveBettingSlip`, unmodified), marked `Ready`, and a `PlannerSession` is started against it via the **existing** `StartPlannerSession` action, unmodified. From that moment, Capability B's job is finished — the customer is inside the identical Capability A workflow (revise, lock, remove, replace, compare, confirm, export) that already exists and is frozen.

This directly answers the commission's own §25 "Generated Candidate Ownership" question: there is no new lifecycle state for "generated but not yet accepted." A candidate is either:
1. **not yet a `BettingSlip` at all** — still inside Capability B's own construction pipeline, with no Planner session, no lock semantics, nothing ADR-008/009 need govern; or
2. **a real `BettingSlip`, already `Ready`, already inside an ordinary Planner session** — at which point it is indistinguishable from any other Planner session and needs zero new code in `app/Domain/Planner/*` or `app/Actions/Planner/*`.

This is deliberately the simplest possible boundary: it adds **one new action** (`CreateCandidateBettingSlip` or similar — converts Capability B's internal candidate representation into leg attributes `SaveBettingSlip` already accepts) and **zero new Planner states, zero new Planner actions, zero ADR-008/009 amendments**. The "original slip" panel's copy ("This slip stays exactly as you entered it") is honestly true even for a generated candidate, since by the time a Planner session exists, the `BettingSlip` *is* the customer's accepted starting point, functionally identical to one they typed by hand — the Planner has no way to know or care which intake method produced it, exactly as `PO-U07.5-001`'s bounded-scope intake work already established for Paste Text/PDF/Screenshot (all converge on the same `SaveBettingSlip` → Builder → Planner path).

**What this deliberately avoids**: a second "GeneratedPlannerSession" concept, a "pending candidate" database table with its own review/accept/reject lifecycle, or any special-casing inside `session.blade.php` for "is this session's Revision 1 generated or customer-entered." None of that is needed if the boundary above is honored strictly.

## 8. Planning brief contract (§44.6, §15)

A minimal, honestly-scoped MVP contract (not final — Engineering's call at build time per this repository's own `ARCHITECTURE_OFFICE.md` convention of "decides structure, not implementation"):

```text
PlanningBrief
  target_odds_min: decimal
  target_odds_max: decimal
  max_selections: int (bounded by the existing Builder's own 20-leg ceiling — no new ceiling invented)
  planning_window_days: int
  allowed_competitions: array<CanonicalCompetitionId>
  allowed_markets: array<CanonicalMarketId>   (subset of FootballMarketTaxonomyV1 — never a new taxonomy)
  excluded_markets: array<CanonicalMarketId>
  max_risk_band: RiskBand  (reuses the existing enum — Low/Moderate/High/VeryHigh — never a new scale)
```

Deliberately **not** in MVP scope: minimum-selections, evidence-quality minimums, fixture-diversity/competition-diversity constraints beyond simple inclusion/exclusion lists. The commission's own §15 asks Architecture to decide what's MVP vs deferred — these are recommended deferrals because each adds meaningful construction-algorithm complexity (§10) without which the core "does this even work at all" question can't be answered, matching this session's own repeated finding that unproven complexity should follow proven value, not precede it.

## 9. Candidate pipeline (§44.7, §16–§22)

```text
Planning Brief
  ↓ (Fixture Discovery — Parser-sourced evidence, date/competition filtered)
Eligible Fixture Set
  ↓ (Market Discovery — which markets are Evidence-Fresh and taxonomy-recognised for each fixture)
Eligible Market/Selection Universe
  ↓ (Candidate Eligibility Service — hard rejection: unsupported market, insufficient evidence,
     duplicate fixture, excluded competition, outside window, rule violation)
Screened Candidates
  ↓ (Candidate Ranking Service — Data Science Lab's future mathematical model; NOT designed here,
     explicitly out of scope per the commission's own §47 "new deterministic mathematics")
Ranked Candidates
  ↓ (Accumulator Construction Service — assembles a combination satisfying the brief's
     odds/leg-count/diversity constraints; a bounded/greedy deterministic method recommended
     over an opaque optimiser, per the commission's own explainability requirement, §26)
Constructed Combination
  ↓ (Whole-Slip Evaluation — the EXISTING, unmodified CalculateStructuralRisk/
     RankLegsByStructuralWeakness, exactly as Capability A already uses)
Accepted Combination, or explicit No-Valid-Candidate (§9 below) with a stated reason
  ↓ (Planner Integration Adapter — §7)
New BettingSlip (Ready) → Existing Planner Session, Revision 1
```

**No-valid-candidate handling** (commission §19/§23): recommend this be a first-class, honestly-empty result — never a silently relaxed brief. The service should return which specific constraint(s) could not be satisfied (e.g. "no combination reaches 12.0 combined odds within a Moderate risk ceiling across the selected competitions") so the customer can adjust deliberately, mirroring this codebase's own established pattern of naming *why* something didn't work (`AnalysisAvailability::Unavailable`'s own reason-code discipline) rather than a generic failure message.

**Construction method**: recommend a bounded, deterministic, explainable method (e.g. staged greedy assembly with whole-slip re-validation after each addition, backtracking on rejection) over a black-box optimiser. This is a Data Science Lab decision at implementation time, not one Architecture Office should pre-empt mathematically — but the *architectural* requirement is that whatever method is chosen must be able to state, per selection, which planning-brief constraints it satisfied (§26), which rules out genuinely opaque approaches (e.g. an unexplainable ILP solver with no per-decision trace) regardless of which specific algorithm is eventually chosen.

## 10. Processing and progress architecture (§44.9, §27, §28)

**Recommendation: synchronous, not queued, for MVP.** The commission's own §28 asks Architecture to weigh this; given the MVP scope (§12), one provider, a bounded fixture/competition set, and a deterministic (not iterative-search-heavy) construction method, a synchronous request that emits progress via the same mechanism `PO-U07.X.1-001` already established (`wire:loading`-scoped indicators, a milestone disclosure rendered complete once the real work finishes) is almost certainly sufficient and avoids introducing queue infrastructure, job retry semantics, and a polling/streaming delivery mechanism this codebase has never needed before. **This should be revisited, not assumed forever**, once real fixture/provider volume is known — a queued/job-based model becomes appropriate if construction genuinely takes longer than a request timeout, which cannot be determined without a real provider's actual latency, another reason §1's gating matters.

Milestone labels (matching the commission's own §10/§27, reframed to only claim what's genuinely staged rather than what merely sounds thorough):

```text
Planning brief validated
Eligible fixtures identified
Markets screened
Unsupported candidates removed
Candidates ranked
Accumulator constructed
Whole-slip structural analysis complete
Candidate ready
```

Deliberately shorter than the commission's own 11-stage list in §10 — several of its stages ("Discovering Fixtures," "Checking Provider Coverage," "Preparing Evidence") describe *acquisition* work that, per §1, happens well before a customer clicks "Build," not during the synchronous construction request itself. Presenting acquisition-time work as if it happens live during construction would violate this codebase's own "no fake milestones" discipline (`PO-U07.X.1-001` §9/§13) just as much as a literal fake delay would.

## 11. Failure model (§44.10, §36)

| Failure | Response |
|---|---|
| Provider unavailable | Evidence Store serves last-known-fresh data if within freshness contract; otherwise construction returns "insufficient evidence" — never a silent stale-data substitution |
| Partial provider response | Affected fixtures marked `EvidenceQuality::Unavailable`; excluded from eligibility, not defaulted to eligible |
| Conflicting providers (future, multi-provider) | Reconciliation queue, not automatic majority-wins — matches Parser Office's own "never asserts a source is production-ready... without a stated validation contract" discipline |
| No valid candidate | Explicit, reasoned empty result (§9) — never a relaxed brief |
| Construction timeout (if ever async) | Deferred until §10's synchronous-first recommendation is revisited |

## 12. Security and compliance assessment (§44.12, §39–§41)

- Provider credentials: server-side only, never reaching the customer browser — standard for any external API integration in this stack, no new pattern needed.
- **Compliance flag for the record, not resolved here**: `SD-001`'s own decision log entry already flagged that "gambling-adjacent planning/advisory tools are the kind of thing that can be specifically regulated... genuine external legal/compliance review is recommended before this ships, not merely an internal governance document." Capability B is a materially larger step in that direction than Capability A (SlipGuard would now be *sourcing* selections, not just evaluating customer-supplied ones) — Architecture Office recommends this compliance review happen **before**, not after, Parser Office begins source discovery, since a source that turns out to be legally unusable for this product's positioning wastes the acquisition work entirely.
- `ADR-012`'s boundaries (no fund custody, no autonomous betting, operator independence) are unaffected by this design — Capability B only ever produces a candidate for the customer to review inside the existing, already-compliant Planner; it never places, holds, or executes anything.

## 13. MVP recommendation (§44.13, §42)

Football only. One provider (once Parser Office names one — not assumed here). A small, fixed set of markets already in `FootballMarketTaxonomyV1` (no new market types). A 7-day planning window ceiling. No multi-provider reconciliation. No async/queued construction. No fuzzy identity matching. Deferred entirely: Risk Feed/Labs/public-demonstration consumers (§4's "near-term"/"future" columns) — build the Builder's own path first and prove it before generalizing to other consumers, matching this codebase's own repeatedly-demonstrated preference for proven-value-first sequencing over speculative platform generality.

## 15. Phased roadmap and office handover (§44.14, §43, §46)

**Phase 0 — Parser Office, not Architecture Office.** Evidence-source viability, licensing, and a validation/freshness contract (`docs/offices/PARSER_OFFICE.md`'s own U-06.3 mandate). Nothing below can start in earnest without this.

**Phase 1 — Canonical identity and provider adapter shape** (Engineering, once Phase 0 names a source).

**Phase 2 — Evidence store** (Engineering; Architecture Office's §5 recommendation as the concrete shape).

**Phase 3 — Planning brief and candidate eligibility** (Engineering + UX Studio for the brief-authoring screen).

**Phase 4 — Ranking and construction mathematics** (Data Science Lab — a new rule-set document, in this codebase's own established `RISK_RULE_SET_2026_1.md`-shaped format, not invented ad hoc in code).

**Phase 5 — Planner integration** (Engineering; per `ADR-013` below, this should be the smallest phase of the whole roadmap since it deliberately reuses existing code).

**Phase 6 — Additional consumers** (Risk Feed, Labs, public demonstrations) — not commissioned by this document; a future, separately-scoped decision, exactly as Capability B itself was.

Compliance Office review (§12) should occur **between Phase 0 and Phase 1**, not after implementation begins.
