## 0. What changed since `U-17.1`, and what didn't

`U-17.1` was written before any real provider was chosen — every evidence-dependent component there was deliberately an abstraction, not a design. Three real documents now exist that this one confirms against: `U-17.3` (real payloads from The Odds API and SportMonks) and `U-17.4` (binding compliance constraints: no public launch yet, cache conservatively, fictional data only in public-facing content). **Nothing in `U-17.1`'s core recommendations needs reversing** — its "smallest viable operational evidence store, not a warehouse" call, its deferral of odds-context dependency from MVP eligibility, and its Planner-integration boundary (now `ADR-013`, Proposed) all survive this confirmation pass unchanged. What changes is that every "TBD once a provider exists" placeholder in that document can now be replaced with a real, specific design.

**No new ADR is proposed here.** `ADR-013` already covers the one durable, code-relevant decision (how a candidate meets the Planner). Everything below is implementation-detail-level — adapter contracts, cache TTLs, request-budget shape — appropriately living in this document, not a new ADR.

## 1. Confirmed provider and scope

**Primary provider: The Odds API** (per `U-17.3`'s real trial data, `U-17.4`'s clearance). **No second provider in the first implementation** — `U-17.1`'s own Decision Register #4 recommendation (one-provider MVP) is reinforced, not weakened, by `U-17.3`'s finding that SportMonks' free tier couldn't even validate the target leagues. Football only. Premier League, La Liga, Serie A confirmed reachable (Bundesliga/Ligue 1 not tested in `U-17.3` but present in the provider's own sport-key list, reasonably assumed same-shape — flagged as assumed, not verified, consistent with this session's own discipline).

**Confirmed market families** (from `U-17.3`'s real requests): Match Result, Double Chance, Draw No Bet, Total Goals, Both Teams to Score, Correct Score, Half-Time Result. **Excluded from MVP** (unconfirmed, not proven absent): Team Total Goals, Half-Time/Full-Time.

**Binding compliance constraints from `U-17.4`, carried into every design decision below**: internal/non-public development only; conservative, short-lived caching of raw provider responses pending written clarification; derived structural findings retained separately from raw evidence; fictional data only for anything public-facing; no bookmaker logos/deep-links/affiliate mechanisms.

## 2. Confirmed endpoint shape (the real architectural cost finding)

`U-17.3`'s single most important discovery carries directly into this design: **Match Result and Total Goals are available via one bulk request per competition-window; Double Chance, Draw No Bet, Both Teams to Score, Correct Score, and Half-Time Result each require one authenticated request per fixture.** This is not a detail — it is the entire shape of the acquisition pipeline in §5 below. A planning brief spanning, say, 30 eligible fixtures across 3 competitions with all 7 markets requested would cost roughly 3 bulk requests plus up to 150 per-event requests (30 fixtures × 5 per-event-only markets) before any construction logic runs at all. **This must be visible to whoever sizes a production request budget — it is a real, quota-relevant number, not a rounding error.**

## 3. Provider adapter contract (§44.3)

```text
interface MarketEvidenceProvider
{
    supportedCompetitions(): array<CanonicalCompetitionKey>

    upcomingEvents(competition, dateRange): array<CanonicalFixture>
        // one bulk request per competition per window

    bulkMarkets(competition, dateRange, markets: [MatchResult, TotalGoals]): array<CanonicalMarketQuote>
        // one bulk request; only the two bulk-eligible families

    eventMarkets(fixtureId, markets: array<CanonicalMarketFamily>): array<CanonicalMarketQuote>
        // one request PER fixture PER call — the expensive path, confirmed by U-17.3
}
```

Explicitly, per `U-17.1`'s own §6 boundary (unchanged): this adapter never calculates structural risk, never determines eligibility, never writes to Planner tables, and never decides whether a response should be trusted (that's the Evidence Validator's job, §4 below) — it only translates The Odds API's real, confirmed shapes (`h2h`/`totals`/`double_chance`/`draw_no_bet`/`btts`/`correct_score`/`h2h_h1`) into the canonical shapes in §6.

## 4. Evidence acquisition sequence (§44.6, confirming `U-17.1` §9)

```text
1. Planning brief validated (competitions/window/markets against the MVP allowlist — reject anything outside §1's confirmed set before any provider call)
2. Bulk acquisition: Match Result + Total Goals, one request per competition/window
3. Deterministic fixture reduction using ONLY bulk-acquired facts (competition, date, kickoff, Match Result/Total Goals availability) — never trigger a per-event request for a fixture already excludable on bulk data alone
4. Per-event acquisition: remaining confirmed markets, ONLY for fixtures that survived step 3
5. Canonical normalisation (§6)
6. Evidence-quality tagging (Fresh/Stale/Conflicting/Unavailable — U-17.1 §5's enum, unchanged)
7. Candidate eligibility → ranking → construction → whole-slip evaluation (Data Science Lab's domain, unchanged from U-17.1 §9 — not redesigned here)
8. Planner handoff (ADR-013, unchanged)
```

Step 3's ordering is the direct, load-bearing consequence of §2's cost finding — it is the single cheapest lever available to control request-credit consumption, and it requires no new infrastructure, only sequencing discipline in the acquisition code itself.

## 5. Canonical evidence model (§44.4)

Confirmed field shapes, from real `U-17.3` payloads, not guessed:

```text
CanonicalFixture: id, provider_event_id, competition_key, home_team, away_team, commence_time, retrieved_at

CanonicalMarketQuote: canonical_market (one of the 7 confirmed families), fixture_id, bookmaker_key,
                      outcomes: [{ name, price, point? }], provider_last_update, retrieved_at, evidence_quality

Provenance (on every quote): provider="the_odds_api", provider_market_key (h2h/totals/double_chance/draw_no_bet/btts/correct_score/h2h_h1),
                              acquisition_timestamp, cache_expires_at
```

`outcomes[].point` (confirmed present on `totals`, absent elsewhere) is the line value (e.g. `3` for an Over/Under 3 goals market) — this single field is the reason Total Goals needs a slightly richer outcome shape than the Yes/No-style markets (`btts`) or the team-name-style markets (`h2h`, `draw_no_bet`).

The Double Chance outcome strings ("Arsenal or Draw") require parsing into SlipGuard's own canonical selection representation — this is real, confirmed, non-trivial mapping work, not a formality, and should be scoped explicitly in the Engineering package (§10).

## 7. Cache and evidence-store design (§44.7, confirming `U-17.1` §5 with `U-17.4`'s constraint layered on)

`U-17.1`'s "operational store, not a warehouse" recommendation stands. Concretely, per `U-17.4`'s conservative-pending-clarification instruction:

- Raw provider responses: cached hours, not days; never displayed directly to a customer without passing through normalisation.
- Normalised evidence (`CanonicalFixture`/`CanonicalMarketQuote`): same short TTL as the raw response that produced it — no reason to outlive the raw data's own compliance-conservative lifetime pending `U-17.4`'s written clarification.
- Derived SlipGuard intelligence (structural scores, eligibility results, candidate snapshots): retained indefinitely as SlipGuard's own product data, stored separately, per `U-17.4` §4/§8 exactly.
- Cache TTL must be a single, centrally-configurable value — not scattered across the adapter or acquisition code — so it can be changed the moment `U-17.4`'s provider clarification (§7 there) returns an actual answer, without a redesign.

## 8. Request-credit protection (§44.8)

Directly actioning §2's cost finding: before executing step 4 of §4, calculate the projected per-event request count (eligible-fixture-count × per-event-market-count) and reject or truncate the plan if it exceeds a configured per-planning-request budget. This is a simple arithmetic guard, not a queueing system — consistent with `U-17.1`'s own synchronous-first recommendation (§10 there, unchanged here) and this session's repeated preference for the smallest correct mechanism over speculative infrastructure.

---

## 9. Failure states (§44.9) — extending `U-17.1` §11 with real, observed cases

`U-17.3` directly observed two real "valid key, no data yet" cases (`h2h_h2`, `team_totals` returning `200` with zero priced bookmakers well before kickoff) — this is a **third** evidence state beyond `U-17.1`'s original three (`Fresh`/`Stale`/`Conflicting`/`Unavailable`... actually within `Unavailable` already, on reflection): a market that is *structurally supported* but *not yet priced* by any bookmaker at the current point in time. Recommend this map to `EvidenceQuality::Unavailable` rather than inventing a fifth state — the customer-facing consequence (this selection can't be offered right now) is identical whether the market doesn't exist or simply isn't priced yet, and `U-17.1`'s own enum already has the right shape for it.

## 10. Engineering package boundary (§44.15, §40)

The smallest defensible first package, confirming and narrowing `U-17.1`'s Phase 1/2:

1. `MarketEvidenceProvider` adapter for The Odds API only (§3), behind a `MARKET_WIDE_PLANNER_ENABLED=false` feature flag (per `U-17.4`'s no-public-launch constraint) — internal/staff-only access only, no public route.
2. Canonical evidence tables (§5) — the operational store, not a warehouse.
3. The bulk-then-reduce-then-per-event sequencing (§4) with the request-credit guard (§8).
4. **Explicitly not in this package**: candidate eligibility/ranking/construction (Data Science Lab's own future rule-set document, not pre-empted here); the Planner integration adapter (`ADR-013` defines the boundary; building it is premature before construction logic exists to hand it a candidate); any customer-facing UI.

## 11. Compliance constraint mapping (§44.13 — direct traceability, not restated prose)

| `U-17.4` constraint | Architectural enforcement |
|---|---|
| No public launch | `MARKET_WIDE_PLANNER_ENABLED` flag; no public route registered |
| Conservative caching pending clarification | Single centrally-configured short TTL (§7) |
| Raw/derived separation | Separate storage for `CanonicalMarketQuote` vs. structural-risk output (§7, §5) |
| Fictional data only in public content | Unaffected by this architecture — a content/demo-workspace policy, not a code path this package touches |
| No bookmaker logos/affiliate links | Provenance model (§5) stores `bookmaker_key` as data only, never rendered as a branded UI element in this package's scope |

## 12. Programme risks (§44.17)

- **Request-credit exhaustion in production** is now a concrete, sizeable risk per §2's real cost finding — not previously quantified before `U-17.3`'s real trial.
- **Correct Score's real outcome shape is unconfirmed** (§6) — a parsing assumption here could be wrong; verify against a real payload before building the parser, not after.
- **Compliance's written clarification (`U-17.4` §7) may return answers that require revisiting §7's cache design** — this design deliberately chose the most conservative reasonable posture specifically so that outcome, if it happens, is a config change, not a rebuild.
