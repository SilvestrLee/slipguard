## 0. How To Read This Document

Per this office's own established practice on this programme (`docs/02-architecture/U-06.1-ARCHITECTURE-DISCOVERY.md` §0), agreement with the commissioning handover's framing is not the goal here — architectural correctness is. Two things in the handover's own **§5 Key Questions** turn out not to be answerable by Architecture Office at all, for a reason worth stating up front rather than discovering at the end: they presuppose a system that autonomously *generates* or *chooses* replacement selections, which is Capability B (deferred, unauthorized, no data source exists — `PO-U06.1-AC-001`). Under the actually-authorized Capability A, the customer sources every replacement themselves; the planner's job is to evaluate, rank, and explain what the customer has already entered. This document says so plainly rather than quietly designing an autonomous replacement engine SlipGuard isn't authorized to build.

The one genuinely hard architectural question this document had to resolve — whether "Regenerate" is reachable at all, given `ADR-007`'s known re-analysis gap — **is resolved**, not merely re-flagged. §3 shows why: planner regeneration never needs to re-analyse a `BettingSlip`, so the gap that blocks re-analysis never applies to it.

## 1. Executive Architectural Assessment

**The constitutional question:** *"Exactly how should the Intelligent Planner behave from the user's first click until the planning session ends?"*

**Short answer:** as a small, new bounded context (`app/Domain/Planner/`, per `U-06.1`'s own proposal) that reads a customer's already-`Ready` `BettingSlip`, evaluates and ranks its legs using the unmodified MSC engine, lets the customer lock/remove/replace legs with their own entries, re-evaluates after every edit, and — only once, only at the end — writes the finished selection back to that same slip via the existing `SaveBettingSlip` action. No new math, no async generation step, no touching of `SlipAnalysis` or the `Analysed` lifecycle state at any point.

**Bottom line:** this is buildable now, with the domain model `U-06.1` already sketched, refined here into a concrete lifecycle, a resolved regeneration story, and an explicit list of what is *not* an architecture decision (§8's Open Decisions Register) — several of the handover's "Key Questions" belong to Product Office and Compliance Office, not this office, and are named rather than answered here.

## 2. Grounding — What Already Exists

Nothing below invents a capability; each item is either already implemented or already an accepted architectural decision:

- **`App\Domain\Risk\Engine\CalculateStructuralRisk`** (ADR-007) — pure, deterministic, versioned. Unchanged, unmodified by anything in this document.
- **`App\Domain\Risk\Engine\RankLegsByStructuralWeakness`** (E-06D.1, `docs/03-data-science/WEAKEST_LEG_ATTRIBUTION_MODEL.md`, accepted `PO-U06.2A-AC-001`) — the Marginal Structural Contribution (MSC) model. Given a slip's legs, produces a `LegAttributionRanking`: baseline score/band, and every leg's rank, integer and unrounded `MSC`, score/band without it, and reason-code delta. Already handles a single-leg slip, an `Unavailable` baseline, and a gate-dependent leg correctly (§4 of that specification) — this document reuses all of that, unmodified.
- **`App\Domain\BettingSlip\BettingSlipStatus`** — `Draft → [Ready, Archived]`, `Ready → [Draft, Analysed, Archived]`, `Analysed → [Archived]`, `Archived → []`. Confirmed directly in code, not assumed.
- **`App\Actions\BettingSlip\SaveBettingSlip`** — transactional leg replacement; refuses to touch a slip that has left `Draft` (E-03B, `BettingSlipNotEditableException`).
- **ADR-007** — the Risk Engine/persistence/presentation boundary and its one known, still-open gap: `SlipAnalysis` is one-per-slip (unique constraint) and `Analysed` has no path back to `Ready`, so re-analysing an already-analysed slip is not reachable today.
- **ADR-008 (Proposed)** — the planner's own evaluation logic must be exactly as pure as the Risk Engine; its "Open Dependency" section explicitly declines to resolve the regeneration gap and names it as this work package's job.
- **`docs/02-architecture/U-06.1-ARCHITECTURE-DISCOVERY.md`'s proposed domain model** — `PlannerSession`, `PlannerSelection` (`lock_state`, `sequence_number`, `evaluation_snapshot`), `PlannerRegenerationEvent` (immutable history). This document refines, not replaces, that proposal.

## 3. Resolving the Regeneration Gap (ADR-008's Open Dependency)

**Claim: the ADR-007 re-analysis gap does not block Capability A's planner, at all, if — and only if — planner regeneration is designed to never require re-analysing an already-`Analysed` `BettingSlip`.** This is provable from facts already established, not a new concession:

1. A `PlannerSession` is seeded from a `BettingSlip` that is `Ready`, **never** `Analysed` (§4 makes this an explicit precondition, not an incidental choice).
2. Every regeneration cycle inside a session — lock, unlock, remove, replace, re-evaluate — reads and writes only the *new* `PlannerSelection`/`PlannerRegenerationEvent` tables. It never touches `SlipAnalysis`, never calls `AnalyzeBettingSlip`, and never needs the source slip to change status at all. There is no unique-constraint problem here because these are new tables with no such constraint proposed — `PlannerSelection` rows are expected to be superseded across a session's lifetime; that is what `sequence_number` is *for* (`U-06.1` §4).
3. **Export is the only point of contact with `BettingSlip`, and it happens at most once per session, using a transition that is already legal today**: `Ready → Draft` (already an allowed transition) → `SaveBettingSlip` (already works on a `Draft` slip) → `Draft → Ready` (already allowed). No code change to `BettingSlipStatus::allowedTransitions()` is required.
4. The customer can still `Analyze` the slip normally afterward, through the completely unchanged, existing E-05 report flow. If they want to plan *again* after that, they do so from a **new** slip (or an `Archived`-and-recreated one, the existing pattern) — exactly as `Analysed` slips are already immutable today. Nothing here asks for re-analysis of an `Analysed` slip; the gap ADR-007 flagged is real but is a different question this document does not need answered.

**Consequence:** `ADR-008`'s "Open Dependency" is resolved for Capability A, not merely restated. §7 proposes this as `ADR-009`.

## 4. Scope Correction: What "Replacement" Means Under Capability A

The handover's §5 "Replacement Strategy" questions ("replace one leg at a time? multiple? until acceptable? until diminishing returns?") describe a system that *chooses* what to replace a leg with. That is Capability B — no fixture/odds/market data source exists for that (`U-06.1` §3, unchanged since `PO-U06.1-AC-001` deferred it).

Under Capability A, **the customer sources every replacement**, exactly as they source every original candidate (via the existing E-03 slip builder). The planner's actual job, precisely stated:

1. Evaluate the customer's current candidate set (MSC ranking).
2. Show which leg is weakest, and why (the ranking's already-available facts — score/band delta, reason-code delta).
3. Let the customer lock a leg (keep it, don't touch it), or unlock/remove one and enter a different selection of their own choosing.
4. Re-evaluate after every such edit.
5. Let the customer repeat step 3–4 as many or as few times as they want.
6. Let the customer export the current selection to a real `BettingSlip` whenever they choose.

This means "replace one leg at a time vs. multiple" is not an architectural choice at all — the customer decides, one edit at a time, exactly as they already do in the slip builder. "Replace until acceptable" / "until diminishing returns" describes a *customer's own* stopping decision, not a system-driven optimization loop — SlipGuard has no authority to decide "acceptable" (SD-001: no unexplained suggestion, no black-box suitability determination). What the orchestration layer *can* and *does* provide is the data a customer needs to make that call themselves at every step (§6).

## 5. Planner Lifecycle

Deliberately smaller than `U-06.1`'s original sketch (`Draft → Generating → Generated → (PartiallyLocked ⇄ Regenerating) → Complete → Exported | Abandoned`) — that sketch was written before Capability A vs. B was resolved and had to accommodate either. Capability A has no system-driven candidate generation step at all, and MSC evaluation is already proven synchronous and sub-millisecond (E-06D.1) — there is nothing here that needs an async "Generating" state the way a live-odds fetch under Capability B might have. `PartiallyLocked`/`Regenerating` also collapse: lock state is a per-selection flag (`PlannerSelection.lock_state`, already in `U-06.1`'s own model), not a session-level status, so it never needs its own session state.

```text
enum PlannerSessionStatus {
    Draft      // session created, seeded from a Ready BettingSlip's legs; no evaluation yet.
    Evaluated  // at least one evaluation cycle has run against the current candidate set.
               // Every lock/unlock/remove/replace edit re-enters this same state via a
               // new evaluation cycle (§6) — it is not a per-edit sub-state.
    Complete   // customer has confirmed the current selection is final.
    Exported   // terminal. Selection has been written back to the source BettingSlip.
    Abandoned  // terminal. Reachable from Draft, Evaluated, or Complete (pre-export).
}

allowedTransitions:
    Draft      -> [Evaluated, Abandoned]
    Evaluated  -> [Evaluated, Complete, Abandoned]   // self-loop: re-evaluation after an edit
    Complete   -> [Evaluated, Exported, Abandoned]   // customer can still edit after "Complete"
    Exported   -> []
    Abandoned  -> []
```

This mirrors `BettingSlipStatus`'s own shape exactly (an enum with an explicit `allowedTransitions()`), per the established convention (`ADR-006`) — not a new pattern.

## 6. Orchestration Sequence (the Decision Pipeline)

```text
1. Customer clicks "Plan this accumulator" on an existing Ready BettingSlip.
     -> new PlannerSession (Draft), one PlannerSelection per current leg
        (snapshot of normalized facts + betting_slip_leg_id reference — the
        source slip is never mutated by this step).

2. Orchestration calls RankLegsByStructuralWeakness(current PlannerSelection set)
     -> persists one PlannerRegenerationEvent (sequence_number 0): the full
        LegAttributionRanking (baseline score/band, every leg's rank/MSC/
        reason-code-delta, or gate-dependent flag — unmodified from E-06D.1).
     -> PlannerSession -> Evaluated.

3. Presentation reads the LATEST PlannerRegenerationEvent only — never
   recalculates on read. Identical discipline to ADR-007's Forbidden Call
   Flow, applied to the Planner (ADR-008's own proposal, now made concrete).

4. Customer acts on one leg:
     a. Lock  -> PlannerSelection.lock_state = locked. No re-evaluation
                 (a flag change only; MSC math is uniform over the whole
                 set regardless of lock state, so nothing to recompute).
     b. Unlock -> PlannerSelection.lock_state = unlocked. No re-evaluation.
     c. Remove -> PlannerSelection soft-removed from the active set.
     d. Replace -> customer enters a new selection themselves (same E-03
                   validation rules); a new PlannerSelection row added.
   Any of (c)/(d) triggers step 2 again: a new PlannerRegenerationEvent,
   sequence_number incremented, PREVIOUS events left untouched (immutable
   history, identical in spirit to SlipAnalysis under ADR-007).

5. Customer marks the session Complete whenever they choose (no system-
   forced trigger — see §8, OD-1/OD-2 for whether SlipGuard ever
   proactively suggests this, which this document does not decide).

6. Export (Complete -> Exported, at most once):
     Ready -> Draft (already legal)
     -> SaveBettingSlip(final PlannerSelection legs)  (already legal on Draft)
     -> Draft -> Ready (already legal)
   No SlipAnalysis, no AnalyzeBettingSlip, no Analysed state involved.
   The customer can then Analyze the slip through the existing, unchanged
   E-05 report flow.

7. Abandon (Draft/Evaluated/Complete -> Abandoned, terminal): source
   BettingSlip is untouched throughout — nothing to undo.
```
