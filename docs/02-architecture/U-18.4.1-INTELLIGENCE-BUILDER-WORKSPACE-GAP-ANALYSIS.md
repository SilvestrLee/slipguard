**Commission:** `TASKS.md` §`U-18.4`, per `PO-MVP-004` (`docs/00-governance/DECISION_LOG.md`, 2026-08-03).

## 2. Detailed Findings

### 2.1 Sport Selector

- **Current state:** No sport concept exists anywhere in Capability B. `config/slipguard-market-intelligence.php`'s `allowed_competitions` lists exactly three football competitions (`soccer_epl`, `soccer_spain_la_liga`, `soccer_italy_serie_a`); `app/Domain/Risk/Taxonomy/FootballMarketTaxonomyV1.php` is the only taxonomy; the sole provider integration (`app/Domain/MarketIntelligence/OddsApiProvider.php`) targets football markets. Neither `market_intelligence_fixtures` nor `market_intelligence_market_quotes` (both migrations, 2026-07-29) has a `sport` column — competition keys are opaque football-specific strings, not a queryable sport dimension.
- **Gap:** Total. A selector requires a real sport registry to select *from*; none exists.
- **Bucket:** **Longer-term architecture work.** Building a selector UI with exactly one working option behind it would be decorative, not functional — the selector is a consequence of §2.2, not an independent deliverable.

### 2.2 Sport-Agnostic Data Model / Sport Adapters

- **Current state:** Football is hard-coded at every layer — taxonomy class name, competition key format, provider integration, market family enum values (`h2h`, `totals`, `double_chance`, `draw_no_bet`, `btts`, `h2h_h1` — all football markets). `docs/02-architecture/U-17.1-DETERMINISTIC-MARKET-INTELLIGENCE-PLATFORM-ARCHITECTURE.md` §5 already named this deliberately: the "Evidence Store" is scoped as "simply the evidence tables" for now, with "Evidence Warehouse" (a genuine multi-consumer, and by extension multi-sport, shape) explicitly named as *aspirational*, not built.
- **Gap:** A `Sport → Competition → Event → Market → Selection` abstraction layer, a sport-adapter interface, and (per the handover's own worked example, `if football` must become "ask the sport adapter") a rewrite of every taxonomy/eligibility/construction touch point that currently assumes football.
- **This directly overlaps already-completed Architecture Office work — do not re-derive it.** `docs/architecture/AO-MVP-005-REFERENCE-DATA-OWNERSHIP.md` (2026-08-02) already analysed this exact territory for a related feature (guided fixture/team selection) and recommended **Model B** — a shared Reference Data bounded context, with Capability B as a *consumer*, not an owner — as the correct target architecture, explicitly to prevent Capability B absorbing this scope by accident (Model A). It named two concrete, still-open blockers on Model B: a provider clarification letter (caching/attribution/derived-data terms) drafted but not sent, and no Parser Office source-viability review scoped to reference data. Any sport-adapter design commissioned from this gap analysis should be scoped as the same Model B work, not a second, parallel design.
- **Bucket:** **Longer-term architecture work.** Recommend: a dedicated Architecture Office commission (a new `AO-` work package, or the ADR `AO-MVP-005` itself already recommended once its two named blockers clear), not self-designed here or implemented directly against this document.

### 2.3 Candidate Header Intelligence Display

- **Current state:** `applyConstructed()` (`builder.blade.php:470-491`) computes and exposes combined odds, risk band label, structural score, and per-leg Marginal Structural Contribution (`structural_contribution`) with a `gate_dependent` flag — real, tested, deterministic numbers, not placeholders. All of this is currently shown only *after* `evaluateCandidate()` runs, not as a continuously-live header.
- **Gap:** Two of the four metrics in the handover's worked example — **Evidence Quality** and **Correlation** — have no mathematical definition anywhere in the Risk Engine. Correlation is not merely unbuilt: `docs/product/MVP_SCOPE_LOCK.md` §4.8 records RF-006 (relationship/correlation detection) as **real but permanently held inactive under Rule Set 2026.1**, pending a verifiable event-identity source — a disclosed limitation, not an oversight. **Volatility** has no definition anywhere either.
- **Bucket:** **Longer-term architecture work**, specifically **Data Science Lab authority** — new risk/evidence mathematics cannot be invented by Engineering, per this repository's own precedent (`E-06D`'s directive to design weakest-leg mathematics directly was declined for exactly this reason; Data Science Lab designed the accepted MSC model instead). A presentation-only header re-using the two metrics that already exist (odds, structural score/risk band) is a much smaller, real **immediate post-launch enhancement** — but the header as specified, with all four fields, is gated on new mathematics.

### 2.4 Candidate List as "Intelligence Objects"

- **Current state:** A list of discovered fixtures/options is shown during selection (`activeFixtureKeys`, `selectOutcome()`), and a post-construction leg summary exists (`constructedLegsSummary`: description, odds, structural contribution, gate-dependent flag). Reasoning is present but narrower than specified.
- **Gap:** The vision's required columns — Evidence, Volatility, Correlation, and a general-purpose "Reasoning Badge" on every row (not just accepted legs) — depend on §2.3's missing mathematics for three of five columns.
- **Bucket:** **Longer-term architecture work**, blocked on §2.3's Data Science dependency for full scope. A reduced version (Selection/Market/Fixture/Odds/Risk/Structural Rating only, using only what already exists) is a plausible post-launch UI iteration, but is a new list layout/interaction pattern and must go through the Frontend Work Rule (`docs/05-ux/`) and Mandatory Specialist Design Capability Invocation before implementation regardless of which bucket the data sits in.

### 2.5 Builder Filters

- **Current state:** Six fields exist today, but as a one-time **Planning Brief** consumed once at `findCandidate()` time (`builder.blade.php:139-153`), not as live filters re-slicing an already-generated list: `competitions` (maps to "Competition," not "Sport" — no sport dimension), `windowDays` (a coarse proxy for "Kickoff Time," three fixed buckets not a range), `markets`, `targetOddsMin`/`targetOddsMax` ("Odds Range"), `riskCeiling` ("Risk Band," as a ceiling not a filter).
- **Gap:** "Bookmaker" filtering is not just unbuilt but currently impossible — exactly one provider integration exists (`OddsApiProvider`), so there is nothing to filter *between*; the handover's own sidebar example ("Swap Bookmaker") is equally blocked by this. "Sport," "Structural Rating," "Evidence Quality," "Volatility," "Correlation," "Availability" as filters don't exist, and four of those six need §2.2/§2.3's missing prerequisites. Reframing existing brief fields as persistent, live-adjustable filters (rather than a one-time form) is itself a new interaction pattern, not a data gap.
- **Bucket:** **Longer-term architecture work** overall (most filter dimensions are blocked on §2.2/§2.3, and "Bookmaker" needs a second provider integration — a Parser Office/Compliance Office matter, not Engineering's alone). The subset reframing existing brief fields as live filters is a smaller, real **immediate post-launch enhancement** candidate, gated on UX Studio sign-off for the new interaction pattern, not on new data.

### 2.6 Live Intelligence Sidebar

- **Current state:** Does not exist. Feedback today is inline, appears only after specific actions (`evaluateCandidate`, `tryDifferentCandidate`), and is fully reset by `editBrief()`. The component's own code comment states every domain object is "ephemeral within a single request... never stored as a Livewire property" — there is no cross-navigation workspace state to make a persistent sidebar meaningful yet.
- **Gap:** Total, on two independent axes: (a) a new persistent UI region — a genuinely new component/layout pattern requiring `docs/05-ux/` documentation and Product Office/UX Studio approval before implementation, per `CLAUDE.md`'s Frontend Work Rule and Gap Rule; (b) a "Recommended Actions" mechanism, which — to satisfy `CLAUDE.md`'s Locked Decision that "AI never determines suitability, ranking, confidence, selection order, correlation, or planner/risk outputs" — must be built from the same deterministic, labelled reasoning primitives already proven in this codebase (`CandidateRejectionReason`, `CandidateExclusionReason`, replacement reason labels), not a freeform or AI-generated suggestion list. "Swap Bookmaker" as a recommended action is blocked by §2.5's single-provider finding.
- **Bucket:** **Longer-term architecture work** — the single most architecturally significant UI gap in this analysis, combining a new persistent layout region, a not-yet-designed cross-request workspace persistence model, and (partially) §2.3's missing mathematics for some recommendation types.

### 2.7 Goal-Based Regeneration

- **Current state:** `tryDifferentCandidate()` (`builder.blade.php:518-527`) exists but is narrow: it excludes the current fixture set and re-runs discovery with the *same* brief, with no goal parameter anywhere in `PlanningBrief`, and is capped to exactly one use per session via `$hasRegenerated`.
- **Gap:** Split. "Elite Leagues Only," "Weekend Matches," "Goals Markets Only," "Corners Only" map fairly directly onto existing `PlanningBrief` fields (`competitions`, `windowDays`, `markets`) — a repeatable regenerate against an edited brief (removing the one-shot cap) is a scoped, plausible near-term change using entirely existing inputs. "Reduce Risk" partially exists already (`riskCeiling` is a brief input, though framed as a ceiling, not a directional goal). "Increase Evidence," "Lower Correlation," and "Mixed Sports" are blocked on §2.3's missing mathematics and §2.2's missing sport model respectively.
- **Bucket:** **Split — Immediate post-launch enhancement** for the brief-mappable goals and un-capping regeneration; **Longer-term architecture work** for the goals requiring new mathematics or the sport-agnostic model. Recorded as one row above per the requested single-bucket format, with this split as the operative detail.

### 2.8 Candidate Library Integration

- **Current state:** Does not exist. No persistence model for named, browsable candidate collections exists anywhere in this repository. Confirmed by direct search — no `CandidateLibrary`-named class, migration, or view exists. `ADR-013` is explicit that a Capability B candidate has exactly two states, pre-`BettingSlip` (ephemeral) or an ordinary `Ready` `BettingSlip` (via `SaveBettingSlip`/`StartPlannerSession`) — nothing in between, and no new Planner-adjacent persistence concept is permitted by that ADR.
- **Gap:** Total. A named-collection model ("Today's Safe Picks," "Weekend Builder," etc.) is new domain surface, and per `ADR-013`'s own explicit prohibition, it must not be designed as a third state bolted onto the existing pre-`BettingSlip`/`BettingSlip` boundary — it needs its own bounded design. It also raises the same open editorial-content question already unresolved for SlipGuard Labs (`docs/00-governance/DECISION_LOG.md`, Programme U-13): an admin surface for curated content exists there, but no content has ever been published — a standing Product Office decision each time a curated list ships, not an engineering default.
- **Bucket:** **Longer-term architecture work** — needs an Architecture Office design consistent with `ADR-013`'s existing boundary, and a Product Office decision on editorial ownership of the library's contents before any UI is built against it.

### 2.9 Mixed-Sport Accumulators

- **Current state:** Architecturally impossible today. Exactly one sport (football), one provider, and no `sport` column in either Market Intelligence table. Separately confirmed: Capability A's own Manual Builder does have a free-text `sport` field (`app/Domain/BettingSlip/BettingSlipValidationRules.php:21`), but it is an unconstrained string with no registry or adapter behind it, and belongs to an entirely unrelated feature — it cannot be reused to unlock this.
- **Gap:** Strictly and entirely gated on §2.2 landing first. No meaningful partial progress is possible before a sport-agnostic domain model exists.
- **Bucket:** **Longer-term architecture work** — sequenced after §2.2, not parallel to it.

### 2.10 Intelligence-First Editing (re-score on every change)

- **Current state:** Already true for the one edit type that exists today. `evaluateCandidate()` unconditionally re-runs the full deterministic pipeline (`EvaluateCandidateSelections`, including risk analysis and MSC attribution) on every outcome selection change — it does not merely patch an odds number. This is a case where the current implementation already matches the vision's stated principle, for its current (narrower) scope.
- **Gap:** None for the principle itself. The only real gap is that richer edit types (direct add/remove/swap of individual legs in a persistent list, per §2.4/§2.6) don't exist yet to apply the principle to.
- **Bucket:** **No gap — already satisfied** for existing scope. Any *new* edit surface this principle would need to extend to inherits whichever bucket that edit surface lands in (§2.4/§2.6, both Longer-term).

### 2.11 Footer Toolbar

- **Current state:** Two of eight named actions exist in substance: `acceptCandidate()` (functionally "Save" — converts the candidate into a real `BettingSlip` and Planner session) and `tryDifferentCandidate()` (a limited "Regenerate," see §2.7). The absence of any "Place Bet" action is not a gap — it already independently satisfies `ADR-012`'s Locked Decision, confirmed directly, not merely assumed.
- **Gap:** Duplicate, Compare, Export, Share, Archive don't exist. "Compare" and "Analyse" already exist implicitly once a candidate becomes a real `BettingSlip` (History, Journal, Planner), but not from inside the Builder itself. "Archive," "Export," and a true "Duplicate" of an unsaved candidate all presuppose §2.8's Candidate Library persistence — there is nothing to archive/export/duplicate before a candidate has somewhere to live beyond one request.
- **Bucket:** **Longer-term architecture work** overall, gated on §2.8 for most of the new actions. A bare "Duplicate" that just re-runs the current brief (no persistence needed) is a plausible **immediate post-launch** item on its own, and renaming/relabelling the two existing actions to match this vocabulary is copy-only.

### 2.12 Explainability on Every Change

- **Current state:** The strongest existing foundation in this analysis. `CandidateRejectionReason`, `CandidateExclusionReason`, `ReplacementNeeded::$reason->label()`, and per-leg `structural_contribution`/`gate_dependent` are all real, tested, deterministic, already-labelled reasoning primitives — not narrative text, not AI-generated, fully consistent with `CLAUDE.md`'s "AI may explain verified findings only" boundary.
- **Gap:** Coverage, not mechanism. Only three edit-triggering paths currently exist (discover, select-outcome, regenerate) versus the vision's "every automated change" — but each existing path is already genuinely explainable, and any new edit surface (§2.4/§2.6/§2.7) can reuse this exact pattern rather than inventing a new one.
- **Bucket:** **Immediate post-launch enhancement.** This is the one element where extending coverage is mostly a matter of applying an already-proven, already-accepted mechanism to new surfaces as they land — not new architecture or new mathematics.

## 3. Recommendation

1. **No item in this analysis blocks MVP v1.0 launch.** `MARKET_WIDE_PLANNER_ENABLED` may be flipped per `PO-MVP-004`'s existing authorization and the normal release-quality gates (`MVP_SCOPE_LOCK.md` §10), independent of any Intelligence Builder Workspace work.
2. **Immediate post-launch candidates** (§2.12 explainability coverage extension; the achievable subsets of §2.5 filters, §2.7 regeneration, §2.11 toolbar) can be scoped as ordinary Engineering work packages once launch-readiness work is clear, each still subject to the Frontend Work Rule for any UI-touching change.
3. **The prerequisite for most of the vision** (§2.1, §2.2, §2.6, §2.8, §2.9) is a sport-agnostic Reference Data architecture. This should not be designed piecemeal inside future Builder work — it should be commissioned as its own Architecture Office work package, continuing directly from `AO-MVP-005`'s already-accepted Model B recommendation and its two named open blockers (the provider clarification letter, and Parser Office's reference-data source-viability review), rather than as a second, parallel design effort.
4. **New mathematics** (Evidence Quality, Correlation/Volatility scoring — §2.3/§2.4) is Data Science Lab authority. Correlation specifically is already a known, disclosed, deliberately-inactive gap (RF-006) — this vision does not change that determination and should not be read as implicitly reopening it without a Data Science Lab commission.
5. **New UI/interaction patterns** (the persistent workspace layout, live sidebar, per-row intelligence columns, live filters) require `docs/05-ux/` documentation and Product Office/UX Studio approval before implementation, per the Frontend Work Rule and Gap Rule — none of that documentation exists yet, and this analysis does not create it.
