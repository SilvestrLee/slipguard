## 1. Executive Architecture Assessment

**The constitutional question:** *"What architecture is required to safely, scalably and maintainably realise the Product Office vision for deterministic accumulator planning?"*

**Short answer:** it depends entirely on one fork Product Office has not yet resolved — see §3. One branch of that fork is buildable now, reusing >80% of existing infrastructure with no new external dependency. The other branch is not buildable at all until a separate, currently-unauthorized data-acquisition capability exists. Every downstream artefact in this document is organized around that fork because treating it as settled either way would be an invented assumption, which §5 and §11 of the handover forbid.

**Bottom line:** SlipGuard's existing architecture (`docs/02-architecture/SYSTEM_ARCHITECTURE.md`'s modular Laravel monolith, `ADR-001`–`ADR-007`) is structurally sound and extends cleanly to accommodate a Planner capability. No microservice, new database, or framework change is needed either way. The blockers are not architectural in the "wrong shape" sense — they are unresolved *inputs* the architecture depends on: a data source decision, a persistence-lifecycle gap, and one governance gap (an office referenced in U-06 correspondence that does not exist).

## 3. The Central Architectural Fork

This is the single most consequential finding. It was not stated as an open question in any prior U-06 correspondence but is directly implied by `docs/08-operations/DELIVERY_ROADMAP.md`'s own U-06 entry: *"'generate accumulator candidates' requires some source of available fixtures/markets/odds to select from. This application has none today."*

**Model A — Bounded Planning.** The planner operates only over candidate legs the customer has already entered (via the existing E-03 slip builder or an extended entry flow). The planner's job is to *evaluate, compare, rank, and help restructure* the customer's own candidates — e.g. "these two selections in your list carry most of this slip's risk; here's why; you can lock the others and try a different one for these two." No new fixture/odds/market data source is required. This is fully buildable today: it composes the existing `CalculateStructuralRisk` engine (already deterministic, versioned, tested) with a new session/lock/history layer.

**Model B — Generative Planning.** The planner proposes selections the customer did not enter — genuinely new candidates drawn from a live universe of fixtures, markets, and odds. This is what "Generate" and "Regenerate" imply in the `UX-U06.4-001` interaction catalogue (§7: Generate, Replace, Regenerate). This model requires a fixture/odds/market data source that **does not exist anywhere in this repository** and is explicitly excluded from current scope: `PROJECT.md`'s MVP Non-Goals list "bookmaker parsing" and `docs/01-product/FEATURE_MATRIX.md` marks "Bookmaker parsers" as Post-MVP, unproven. SD-001 removed the "safe accumulator generation" non-goal but did **not** remove "bookmaker parsing" or authorize a data-acquisition capability — `PROJECT.md`'s own text says so explicitly ("This is narrower than the phrase it replaces... what's newly approved is planning assistance, not a guarantee of safety") and the roadmap entry says the same about non-goals being untouched.

**Architecture Office's recommendation:** sequence Model A as U-06's first real deliverable. It is genuinely useful (explainable restructuring/comparison assistance on a customer's own candidates — squarely inside SD-001's actual language: "assists customers in constructing accumulators through deterministic, explainable planning"), requires no new external dependency, and can be built, tested, and shipped under the existing ADR-007 discipline without any data-acquisition decision. Model B should be treated as a distinct, separately-scoped future capability, gated on its own Product Office decision about data acquisition (which itself has real build-vs-buy, licensing, and Compliance Office implications well outside this office's remit).

This is a recommendation, not a decision Architecture Office is entitled to make unilaterally — product scope is Product Office's row in `AUTHORITY_MODEL.md`. It is offered because building against an unresolved fork is the one thing this discovery cannot responsibly do.

## 4. Domain Model — Proposed Planner Bounded Context

Extends `docs/02-architecture/DOMAIN_MODEL.md` with a new bounded context, `app/Domain/Planner/`, kept structurally separate from the existing Risk domain — consistent with `docs/offices/ARCHITECTURE_OFFICE.md`'s existing boundary discipline and preserving the Risk Engine's own versioning axis untouched (Data Science Lab's consultation right, `docs/offices/DATA_SCIENCE_LAB.md` §Relationship, is not affected by this proposal since no math changes).

**`PlannerSession`** — belongs to `User`. Fields (suggested, not final — Engineering's call at build time per `ARCHITECTURE_OFFICE.md`'s "decides structure, not implementation"): `user_id`, `status`, `configuration` (leg-count target, sport/competition filters — Model A only needs "which of my candidates," Model B would need market/fixture filters), `created_at`, `completed_at`.

**`PlannerSelection`** — one row per candidate leg within a session. Fields: `planner_session_id`, `source` (`customer_entered` today; reserved enum slot for a future sourced type under Model B), `lock_state` (`unlocked` / `locked`), `sequence_number` (which regeneration cycle produced/last-touched it), `evaluation_snapshot` (a reference to a structural-risk evaluation of this leg, produced by the existing engine — never recalculated in place, mirroring `SlipAnalysis`/`LegAnalysis`'s immutability).

**`PlannerRegenerationEvent`** — one immutable row per regenerate/replace action, per ADR-007's "historical record, not a working document" precedent. Necessary for the same reason `SlipAnalysis` is immutable: a customer must be able to see what a prior version of their plan looked like and why it changed.

**Relationship to `BettingSlip`:** a `PlannerSession`, once the customer is satisfied, exports into a real `BettingSlip` via the existing `App\Actions\BettingSlip\SaveBettingSlip` action — unchanged. This means the planner never duplicates slip-building logic and the existing E-03/E-05A/E-06B/E-06C pipeline (normalize → risk engine → persist) runs exactly as it does today once a plan becomes a slip. The planner is upstream of `BettingSlip`, not a replacement for any part of it.

## 5. Bounded Contexts & Layer Boundary (ADR-008 candidate)

Filed separately as a proposed ADR, per this office's own Deliverables convention (`docs/offices/ARCHITECTURE_OFFICE.md` §Deliverables: "boundary rulings recorded... where durable"): **`docs/adr/ADR-008-PLANNER-ENGINE-BOUNDARY.md`**, status **Proposed** — mirrors ADR-007's shape but is not self-accepting; per `ARCHITECTURE_OFFICE.md`'s own Prohibited Actions ("never overrides... informally") and the ADR-007 precedent of being a *joint* Product Office + Architecture Office ADR, it requires Product Office co-sign before it moves to Accepted, exactly as ADR-007 did.

The proposal's substance: the planner's evaluation logic (whatever compares/ranks/scores candidate legs within a session) must be as pure as `CalculateStructuralRisk` — no persistence, HTTP, UI, or infrastructure access — with all planner persistence, locking, and history-writing happening in a separate orchestration layer, exactly the same discipline ADR-007 already established for the Risk Engine. This is a **structural extension of an existing, working pattern**, not a new one.

## 6. Planner Lifecycle

Proposed lifecycle for `PlannerSession.status`, following the precedent of `App\Domain\BettingSlip\BettingSlipStatus`'s explicit-transitions design (`ADR-006`):

`Draft` → `Generating` → `Generated` → (`PartiallyLocked` ⇄ `Regenerating`) → `Complete` → (exported to `BettingSlip`, terminal) | `Abandoned` (terminal)

This is a recommendation for Engineering to formalize as an enum with `allowedTransitions()`, matching the existing pattern exactly — not a final specification. The precise transition table is Architecture's decision right per `ARCHITECTURE_OFFICE.md`, but pinning exact guard conditions before Model A/B is resolved (§3) would be premature detail invented ahead of need, which `docs/00-governance/WORKING_PRINCIPLES.md` #2 (cited in this office's own constitution) counsels against.

## 7. Service Catalogue

- `PlannerSessionService` (new) — session CRUD/lifecycle orchestration, analogous to `SaveBettingSlip`.
- Candidate evaluation — **no new service**; reuses `CalculateStructuralRisk` read-only, called per-candidate rather than per-slip. This is the main reason Model A carries so little new architectural risk: the hard mathematical work already exists, is tested (309+ Pest tests), and is versioned.
- `ExportPlannerSessionToBettingSlip` (new, thin action) — wraps `SaveBettingSlip`.
- Explanation rendering — extends the existing `EXPLAINABILITY_SYSTEM.md` pattern; no new AI capability, since SD-001 §Locked Decisions already constrains AI to "explain verified findings only," identical to the existing Risk Report's AI boundary (`docs/03-data-science/RISK_ENGINE.md`'s AI Boundary section, unchanged).

## 8. Integration Overview

- Planner ↔ `BettingSlip`: one-directional export only (§4). Planner never mutates a slip once exported; it does not read a slip's post-export history back.
- Planner ↔ Risk Engine: read-only, per-candidate evaluation calls. No engine change required for Model A.
- Planner ↔ Data Science Lab: **owns** the definition of what makes a candidate leg "suitable" for planning purposes (distinct from, but likely reusing, the existing risk-factor mathematics) — this is explicitly Data Science Lab's determination to make, not Architecture's, per `AUTHORITY_MODEL.md`.
- Planner ↔ a future data-acquisition capability: **only relevant under Model B**, entirely unscoped today.
- Planner ↔ Compliance Office: SD-001 itself flags real regulatory exposure (UK Gambling Commission tipster-adjacent rules) — Architecture recommends Compliance Office review precede any Model B work, and ideally review Model A's copy/interaction design too, since "planning assistance" is new customer-facing framing even in its bounded form.

## 10. Dependency Assessment

**Hard blockers before Model B can proceed at all:**
1. A Product Office decision on data acquisition strategy (build vs. licensed feed vs. manual-only) — separate from SD-001, which explicitly did not authorize this (§3).
2. Resolution of R2 (the regeneration/persistence gap) — separate Product Office decision, per ADR-007's own text.
3. Resolution of R5 (Parser Office's status) — needed before any "Parser Readiness Assessment" (as named in the original U-06.3 scope) can be meaningfully owned by anyone.

**Hard blocker before Model A's "Regenerate" interaction specifically:** R2, independent of R1/R5.

**Not a blocker:** Rule Set 2026.1's formal acceptance status (still "Proposed" per `docs/00-governance/DECISION_LOG.md`) — Engineering already treats the implemented mathematics as certified independently of that pending sign-off (`TASKS.md`'s Production Foundation note), and candidate evaluation reuses that same implementation, not a new one.

## 11. Sequencing Recommendation

1. Product Office resolves the Model A/B fork (§3) — recommend committing to Model A first.
2. Product Office resolves R2 (regeneration persistence gap) and R5 (Parser Office status) — both are decisions this office cannot make unilaterally.
3. Only then: Data Science Lab defines what "suitable" means for candidate evaluation within Model A's bounded scope (this is now a materially smaller, better-defined task than the original U-06.2 mandate, which presumed Model B's generative scope).
4. Only then: UX Studio's U-06.4 proceeds — against a real, accepted architecture rather than an assumed one.
5. Model B (data acquisition, parser/data-source readiness) is deferred as its own future-numbered work package, not sequenced here.

## 12. Readiness Assessment

**Not ready** for U-06.2 (Data Science) or the originally-scoped U-06.3 (Parser/data availability) to proceed as previously assumed complete. This is the honest outcome of genuine discovery, not a rejection of the programme — SD-001's underlying vision (explainable, customer-editable planning assistance, per its own actual wording) is architecturally achievable now, in its Model A form, once §11's two Product Office decisions are made.

**Ready,** conditionally: U-06.2 can proceed today if Product Office explicitly scopes it to Model A only (candidate evaluation and suitability criteria for customer-supplied legs) — that work does not depend on R1 or R5, only on R2 being acknowledged as a known constraint on "Regenerate" until resolved.
