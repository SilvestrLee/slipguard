## 0. How To Read This Document

Per `PO-U04-RR-001`: Programme U-08 is not a new capability — it is the overdue Architecture Office certification of `U-04.1`, continued under new numbering, plus one genuinely new scope item that didn't exist when `U-04.1` was written: **Planner artefact organisation** (Programme U-07 completed after `U-04.1` was drafted). This document does not repeat `U-04.1`'s customer journey, screen inventory, copy, or component specifications — it certifies them as architecturally sound, resolves the domain-model questions `U-04.1` correctly left open, and extends the workspace's information model to include the Planner.

## 1. Executive Architectural Assessment

`U-04.1` is architecturally soundly scoped: History requires no new domain model (it reads `User::bettingSlips()`/`slipAnalyses()`, both already existing, per `ADR-007`'s read-only presentation boundary). Journal requires exactly one new domain concept — a `JournalEntry` — which this document specifies. Planner artefact organisation requires no new domain model either; it requires a navigation and retrieval decision layered on data that already exists (`PlannerSession`, `docs/adr/ADR-009-PLANNER-LIFECYCLE-AND-REGENERATION-BOUNDARY.md`).

**No new ADR is required for History or Planner artefact organisation** — both are pure applications of `ADR-007`'s already-accepted forbidden-call-flow discipline (read persisted state, never recompute). **One new ADR is proposed for Journal** (§9), since a `JournalEntry`'s immutable-reference rule is a genuine new architectural constraint, not an instance of an existing one.

## 2. Grounding — What Already Exists

- `User::bettingSlips(): HasMany`, `User::slipAnalyses(): HasMany` — already exist, already sufficient for History's entire data need.
- `SlipAnalysis`: immutable, one row per analysed slip, `user_id` denormalized from the owning slip (never mass-assigned), `bettingSlip()`/`user()`/`legAnalyses()` relations. No delete path exists today — the precedent this document follows for `JournalEntry`'s own deletability question (§6).
- `PlannerSession`: `user_id`, `source_betting_slip_id`, `exported_betting_slip_id` (nullable), `status` (`Draft`/`Evaluated`/`Complete`/`Exported`/`Abandoned`), `selections()`, `regenerationEvents()`. `User::plannerSessions(): HasMany` already exists (added under `U-07.5`). No customer-facing list of "my past planning sessions" exists yet — the Planner Workspace screen (`U-07.7`) is reachable only by direct link from a specific session or from a Ready slip's "Plan this accumulator" action; there is no index.
- `routes/web.php`: `history` and `journal` are both `Route::view(..., 'coming-soon', ...)` placeholders today — confirmed unchanged since `U-04.1` was written.
- `docs/00-governance/PRODUCT_GLOSSARY.md`: "Journal — a simple record of what the user decided and what they later learned." No existing glossary entry for a Planner-session list; this document does not invent new glossary vocabulary, it names the capability descriptively only (§5).

## 4. Workspace Information Model

Extends `U-04.1` §5's tree with the one addition Planner's completion requires:

```text
Dashboard (existing)
├── Analyze Slip (existing)
├── History (U-04 — replaces coming-soon)
│     └── Analysis Report (existing, U-03 — reused, not modified)
├── Journal (U-04 — replaces coming-soon)
│     └── Journal Entry detail/edit (U-04 — new)
└── Planning History (U-08 — new, see §5)
      └── Planner Workspace (existing, U-07.7 — reused, not modified)
```

The Workspace remains what `U-04.1` §5 already established it to be: the existing authenticated navigation, not a fifth new page. Planning History is a new list screen, structurally identical in kind to History (a reverse-chronological list of cards linking to an existing, unmodified detail screen) — not a new architectural pattern.

## 5. Planning History — New Domain Coverage (Beyond `U-04.1`)

**The gap:** since `U-07.7`, a customer can start, revise, confirm, export, or abandon a Planner session — but has no way to find a past session again once they navigate away, except by returning to the original source slip (which may itself now be `Analysed` or unchanged `Ready`) and noticing it's `hasPlannerHistory()`. There is no customer-facing index.

**Architecture:** a new read-only list screen, structurally identical to History:

- **Data source:** `Auth::user()->plannerSessions()`, already a working relation — no new query surface needed, only a new route/screen.
- **Card content:** source slip reference, current status (`Draft`/`Evaluated`/`Complete`/`Exported`/`Abandoned` — customer-facing labels per `U-06.4`'s already-accepted lifecycle terminology, not renamed here), latest revision's score/band, and — if `Exported` — a link to the resulting slip.
- **Primary action:** open a card → the existing Planner Workspace screen (`planner.session` route), unmodified. A `Draft`/`Evaluated`/`Complete` session reopens into the live, still-editable workspace; an `Exported`/`Abandoned` session reopens into its already-correct terminal-state view (`U-07.7`'s "This planning session has ended" / two-artifact export screen — both already built, neither needs a new state).
- **No new domain model, no new table, no new ADR.** This is a presentation-layer addition over already-existing, already-accepted data — the same category of work as History itself.
- **Ordering:** reverse-chronological by `updated_at`, matching History's own convention (`U-04.1` §6.1) — no new retrieval mechanism.

This resolves the one genuinely new scope item `U-08.1-001` named that `U-04.1` could not have anticipated (Planner artefact organisation), without introducing any capability `PO-CRD-001` §7 deferred.

## 6. Domain Model — `JournalEntry` (Resolves `U-04.1` OI-01)

**Proposed schema** (mirrors `SlipAnalysis`'s own established pattern exactly — denormalized owner, immutable reference, no new pattern invented):

| Column | Type | Notes |
|---|---|---|
| `id` | bigint | |
| `user_id` | FK → `users`, `cascadeOnDelete()` | Denormalized from the entry's own owner, matching `SlipAnalysis.user_id`'s precedent — never mass-assigned. |
| `slip_analysis_id` | FK → `slip_analyses`, `cascadeOnDelete()` | **Immutable after creation** (`U-04.1` §6.3) — not present in any update action's fillable set. One analysis may have zero or many journal entries (not unique) — a customer may reflect more than once on the same result. |
| `reflection` | text | The customer's own free-text note. Editable (`U-04.1` §6.2's "Edit an existing entry inline"). |
| `created_at` / `updated_at` | timestamps | `updated_at` is the natural "last edited" signal Journal Cards can display, if `U-04.1`'s copy wants it — no new field needed. |

**Relations:** `JournalEntry::user(): BelongsTo`, `JournalEntry::slipAnalysis(): BelongsTo`; `SlipAnalysis::journalEntries(): HasMany` added; `User::journalEntries(): HasMany` added — all mirroring existing relation-declaration conventions exactly.

**Cascade behaviour:** `slip_analysis_id` uses `cascadeOnDelete()`, not `restrictOnDelete()` — deliberately different from the Planner's `source_betting_slip_id` precedent (`U-07.5`), because the two situations are not analogous: a `PlannerSession` is a constitutional audit trail whose "permanently preserved" principle (`PD-008`/`PD-009`) requires its source to never disappear out from under it. A `JournalEntry` is the customer's own note *about* an analysis, not a record the platform itself must preserve for audit purposes — and `SlipAnalysis` has no delete path today regardless (§2), so this is presently a theoretical distinction, correctly specified for when one is eventually added rather than left undefined.

**Authorization:** `JournalEntryPolicy` mirrors `SlipAnalysisPolicy` exactly — `view`/`update`/`delete` scoped to `user_id === $journalEntry->user_id`; `create` open to any authenticated user, since the customer decides what to journal, not the platform.

**Deletability (a recommendation, not a unilateral decision):** unlike `SlipAnalysis` (a structural record the platform must not silently lose), a `JournalEntry` is the customer's own authored content. This document recommends allowing customer-initiated deletion — consistent with how a customer already owns and can freely edit the same text — but flags this as **Open Question OQ-1** (§10) rather than deciding it outright, since it is a product posture question (does anything the customer once wrote ever become a permanent record SlipGuard itself relies on?), not a purely technical one.

## 7. Lifecycle Architecture

- **`SlipAnalysis` / `LegAnalysis`:** unchanged, no new state, no new lifecycle — History reads them exactly as `ADR-007` already specifies.
- **`JournalEntry`:** no formal lifecycle/status enum needed — a `JournalEntry` simply exists, is editable (its `reflection` only), and is deletable per §6's recommendation. It does not participate in `BettingSlip`'s or `SlipAnalysis`'s own lifecycle in any way — it is a satellite record, never a gate on either.
- **`PlannerSession`:** entirely unchanged — `ADR-009`'s five-state lifecycle is the authoritative reference; Planning History (§5) only reads it, never introduces a sixth state or a new transition.
- **Archived slips:** `U-04.1` §4 already correctly established that an archived slip's prior analysis remains visible in History regardless of the slip's own `Archived` status, since `SlipAnalysis` is independent of `BettingSlip`'s lifecycle. This document extends the same principle to Planning History: an `Abandoned` Planner session remains visible and reopenable (to its already-correct terminal view) regardless of what later happens to its source slip.

## 8. Navigation Architecture

Extends `U-04.1` §5's entry/exit points:

- **Entry points:** primary nav gains one item (Planning History), alongside the existing Dashboard/Analyze Slip/History/Journal — same nav mechanism (desktop nav + `U-03`'s mobile drawer), no new navigation pattern. Dashboard's existing "Recent Analyses" cards remain History's entry point (`U-04.1` OI-03, still non-blocking, unresolved intentionally — see §10).
- **Exit points:** unchanged from `U-04.1` — Analyze Slip, Dashboard, the Report screen's existing PD-09/PD-10-compliant exit actions. Planning History's own cards exit into the existing Planner Workspace screen's own already-defined exit points (Confirm/Export/Abandon, `U-06.4`) — nothing new.
- **Relationship between Dashboard, Analysis, Planner, and Workspace** (the handover's explicit ask): Dashboard is the summary/orientation screen (unchanged, `U-02`); History and Planning History are the two parallel "browse what already happened" screens (analyses vs. planning sessions), structurally identical in kind; Journal is the customer's own annotation layer *on top of* History's analyses, never on Planner sessions directly (a customer journals about a result, and a Planner session's whole purpose is to produce a *new*, journal-able result once exported — no separate "journal a Planner session" concept is introduced, avoiding a second, parallel annotation surface).

## 9. ADR — Journal Entry Reference Boundary

**Decision:** a `JournalEntry.slip_analysis_id` is immutable after creation — no action may reassign a journal entry to a different analysis. This mirrors `ADR-006`'s established principle (a `BettingSlip`'s own content-identity is never mutated post-lock) applied to a new, smaller domain object.

**Status update (2026-07-27):** formalised and accepted as `docs/adr/ADR-010-JOURNAL-ENTRY-REFERENCE-BOUNDARY.md` (`PO-U08.3-001`) — this section originally proposed the decision inline pending its own numbered ADR; that gap is now closed. Refer to `ADR-010` itself as the authoritative record going forward; this section is retained for context, not restated as a second source of truth.

## 11. Risks Register

| Risk | Mitigation |
|---|---|
| Planning History could be read as inviting exactly the "smart organisation"/history-analytics capability `PO-CRD-001` §7 defers (e.g., "which of my past plans worked out best"). | This document specifies a plain reverse-chronological list only — no aggregation, comparison-across-sessions, or trend view of any kind. Any such feature would be new Product Office-commissioned scope, not an extension of this architecture. |
| A future `tags`/`collections` feature could be tempted to retrofit onto `JournalEntry` or `SlipAnalysis` directly. | Recorded here as an explicit non-goal: if/when Product Office commissions those capabilities, they attach as new, separate tables (e.g., a polymorphic tag-assignment table), never as new columns on `JournalEntry`/`SlipAnalysis`/`PlannerSession` themselves — keeps those already-certified models stable. |

## 12. Extension Strategy (Architectural Extension Points Only — Not Designed)

Per `PO-CRD-001` §7 / `PO-U04-RR-001` §3, the following are named as *where* a future capability would attach, not *how* it would work — none are designed, schemed, or implemented here:

- **Search/filtering/sorting:** would attach as query-scope additions to the same `User::bettingSlips()`/`slipAnalyses()`/`plannerSessions()`/`journalEntries()` relations already in place — no restructuring of History, Journal, or Planning History's base list-read pattern is anticipated.
- **Tags/collections/bookmarks/favourites:** would attach as new, separate association tables (§11) — never as columns on the models this document specifies.
- **Archive management/bulk actions:** would extend `BettingSlipStatus`'s already-existing `Archived` state and `SlipAnalysis`'s no-delete precedent — no new lifecycle concept anticipated.
- **Smart organisation/AI summaries:** explicitly out of architectural consideration entirely at this stage — `PRODUCT_GUARDRAILS.md`'s existing prohibition on manipulative engagement mechanics is the standing constraint any future proposal would need to clear, not something this document pre-designs around.

## 13. Dependency Assessment

- `JournalEntry` (§6): no dependency — can be engineered independently of everything else in this document.
- Planning History (§5): no dependency — reads already-existing `PlannerSession` data.
- Both are independent of each other and of any deferred capability in §12.

## 14. Sequencing Recommendation

No ordering constraint exists between `JournalEntry` and Planning History — either can be engineered first, or both in parallel, without affecting the other. Recommend building whichever the Product Office judges more valuable to customers first, since both are small, independent, additive pieces of work once this architecture is accepted.

Both new pieces of scope (`JournalEntry`, Planning History) are constitutionally complete the moment this document is accepted — no further architectural discovery is anticipated for either. `U-04.1`'s History/Journal screens remain exactly as specified; nothing in that document required amendment.
