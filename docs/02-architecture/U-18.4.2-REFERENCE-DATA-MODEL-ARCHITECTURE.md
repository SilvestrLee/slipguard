## 0. Scope boundary (binding, stated before any design content)

This document designs an architecture that would let multiple sports exist as a technical capability. It does **not** decide that SlipGuard becomes a "Sports Intelligence Platform," and it does not decide that football-first remains or changes as the launch strategy — both are explicitly open questions the founder reserved for a separate decision, to be made *after* this proposal is reviewed (`docs/00-governance/DECISION_LOG.md`, `U-18.4.2` commission entry). Nothing below should be read as, or cited as, a product-identity decision. It also does not reopen `ADR-013` (Capability B ↔ Planner boundary), does not design Evidence Quality/Correlation/Volatility mathematics (Data Science Lab authority, per `PO-REVIEW-001`), and does not authorise building a second sport — that requires its own future Parser Office source-viability review and Product Office commission, exactly as `AO-MVP-005` already established for reference data generally.

## 1. What exists today (verified directly, not assumed)

- **`market_intelligence_fixtures`** (`database/migrations/2026_07_29_000001_...php`): `provider_event_id` (unique), `competition_key`, `home_team`, `away_team`, `commence_time`, `retrieved_at`, `cache_expires_at`. **No `sport` column.**
- **`market_intelligence_market_quotes`**: FK to fixture, `canonical_market`, `provider_market_key`, `bookmaker_key`, `outcomes` (JSON), `provider_last_update`, `retrieved_at`, `cache_expires_at`, `evidence_quality`. Inherits fixture identity via FK — no independent sport dimension needed here once the fixture has one.
- **`MarketEvidenceProvider`** (`app/Domain/MarketIntelligence/MarketEvidenceProvider.php`): `bulkAcquire(string $competitionKey, array $markets)` and `eventMarketQuotes(string $competitionKey, string $providerEventId, array $markets)`. **This interface is already sport-agnostic at the type level** — both parameters are plain strings, nothing in the signature names football. `OddsApiProvider` is its one implementation.
- **`FootballMarketTaxonomyV1`** (`app/Domain/Risk/Taxonomy/FootballMarketTaxonomyV1.php`): a static class returning `MarketDefinition[]`, each with a `marketCode` already namespaced `football.match_result.1x2`-style — the sport prefix is already a convention, not something this proposal has to invent.
- **`config/slipguard-market-intelligence.php`**: `allowed_competitions` (three football competition keys → display names), `bulk_markets`/`per_event_markets`/`default_markets` (all football market keys), `cache_ttl_hours`, `max_per_event_requests`. No sport key anywhere.
- **`PlanningBrief`** (`app/Domain/MarketIntelligence/Construction/PlanningBrief.php`): `competitions`, `windowDays`, `legCountTarget`, `requestedMarkets`, odds/risk fields. No sport field — sport is implicit via the single configured provider.
- **`Construction/*`** (`CandidateSlot`, `CandidateLeg`, `ChosenSlot`, `ConstructedCandidate`, etc.): genuinely sport-neutral by naming and shape already — nothing here is called `Football...`. `CandidateLeg` does reference `MarketFamily`/`NormalizedMarket` (Risk domain, already generic) and `MarketIntelligenceFixture` (the Eloquent model backing the table above). This layer is a real, reusable asset — the football-coupling in this codebase is concentrated in the taxonomy, the config, and the provider binding, not spread evenly through the construction pipeline.
- **`CanonicalFixture`/`CanonicalMarketQuote`** (framework-agnostic value objects): already shaped for a general provider payload, not football-specific by field naming — except `homeTeam`/`awayTeam` on `CanonicalFixture`, a two-participant assumption (see §10).
- **Capability A's Manual Builder** `sport` field (`app/Domain/BettingSlip/BettingSlipValidationRules.php:21`): `'sport' => ['required', 'string', 'max:255']` — free text, unconstrained, no registry behind it, entirely unrelated code path.
- **`U-17.1` §5/§6** already recommended an operational evidence store (built, matches this shape exactly) and flagged canonical identity resolution as "the single hardest unsolved problem," recommending the mapping table be built once a second provider exists to test against — not before. That recommendation stands; this proposal does not attempt identity resolution across multiple providers of the *same* sport, only the orthogonal question of adding a *second sport*.

**Conclusion:** the football-coupling is real but narrower than "everything is hardcoded" might suggest. Three things are football-specific: the taxonomy class, the config values, and the fact that only one provider is bound. The persistence schema and the construction pipeline are already close to sport-neutral in shape. This changes the cost estimate for Phase 1 below — it is a binding/wrapping exercise more than a rewrite.

## 2. The canonical model

`Sport → Competition → Event → Market → Selection → Intelligence Object`

### Sport
A closed, internally-controlled registry entry — **not** a database table. Recommendation: mirror `FootballMarketTaxonomyV1`'s own pattern (a static, versioned, code-defined class), not a new migration. Sports are added by Engineering shipping a new adapter class (see §3), not by an operator typing a row into Filament — consistent with how `MarketFamily` and the existing taxonomy are already code, not data, because they are internal, deterministic, and rarely-changing. Fields: `key` (string, e.g. `football`), `displayName`.

### Competition
Currently a bare string (`competition_key`) inside `market_intelligence_fixtures`, doubling as both "the provider's identifier" and "the canonical identifier" because only one provider exists (`AO-MVP-005` §3.2 already named this exact ambiguity). Recommendation for this proposal: **do not extract a new `competitions` table yet.** Add a `sport_key` column alongside the existing `competition_key` string on `market_intelligence_fixtures` — additive, non-breaking, backfillable to `football` for all existing rows. A full normalized `Competition` entity is the more architecturally complete answer, but nothing in this repository yet needs it (no second provider, no cross-provider competition matching to resolve) — building it now would be exactly the "unproven complexity ahead of proven need" this codebase's own `WORKING_PRINCIPLES.md` and `U-17.1` §6 already warn against for the adjacent identity-resolution problem. Recorded as the deferred target shape, not built here.

### Event
`CanonicalFixture` / `market_intelligence_fixtures`, gaining the `sport_key` column above. **Real open design tension, not resolved here** (see §10): `homeTeam`/`awayTeam` is a two-participant assumption that will not generalize to every sport (a motorsport grid, a golf field). This proposal does not resolve it — it only ensures the schema change proposed here (`sport_key`) doesn't get built in a way that forecloses the eventual fix.

### Market
Already namespace-shaped correctly (`football.match_result.1x2`). A second sport's adapter (§3) supplies its own `MarketDefinition[]` with its own prefix — no shared-taxonomy rewrite needed, only a second implementation of the same shape `FootballMarketTaxonomyV1` already returns.

### Selection
Currently embedded inside `CanonicalMarketQuote.outcomes` (JSON: `{name, price, point?}`), not a first-class object. No schema change is required to generalize this — the shape is already provider/sport-neutral (`point` is already documented as market-specific, not football-specific, in the migration's own comment).

### Intelligence Object
Not a new persisted concept — this proposal maps it onto the **existing** `ChosenSlot`/`CandidateLeg`/`ConstructedCandidate` shapes in `Construction/*`, which already wrap a Selection with computed attributes (`structural_contribution`, `gate_dependent`) once a candidate is evaluated. Per the authority boundary in §0, this document only names the attachment point for Data-Science-Lab-owned attributes (Evidence Quality, Correlation, Volatility) — it does not define them. Concretely: those would become additional, nullable fields on the existing candidate-evaluation shapes once Data Science Lab defines them, not a new object type.

## 3. Sport adapter interface

```text
interface SportAdapter
{
    public function key(): string;                          // 'football'
    public function displayName(): string;                  // 'Football'
    public function marketTaxonomy(): array;                 // MarketDefinition[] — same shape FootballMarketTaxonomyV1 already returns
    public function evidenceProvider(): MarketEvidenceProvider; // per-sport provider binding
}
```

`FootballSportAdapter implements SportAdapter` would compose the **existing, unmodified** `FootballMarketTaxonomyV1` and `OddsApiProvider` — this is the literal mechanism behind the original handover's "ask the sport adapter, never `if football`" instruction. A `SportRegistry` (also static/code-defined, resolved via Laravel's container — a config-driven binding map, `['football' => FootballSportAdapter::class]`, the same pattern `config('slipguard-market-intelligence.allowed_competitions')` already uses for a simpler case) resolves `sport_key → SportAdapter`.

This is a genuinely small interface because `MarketEvidenceProvider` (§1) is already sport-agnostic at the type level — the adapter's job is almost entirely *binding* (which taxonomy, which provider instance), not translating a new abstraction into an old one.

## 4. Persistence design (schema-level, no migration written)

- **Additive only for Phase 1** (§7): one new nullable-then-backfilled `sport_key` column on `market_intelligence_fixtures`, defaulted to `football` for every existing row. `market_intelligence_market_quotes` needs no change — it inherits sport via its fixture FK.
- **Not proposed now**: extracting `competitions`/`teams` into their own normalized tables. `AO-MVP-005` §7 already reached the same conclusion for a related question ("likely reuse of `market_intelligence_fixtures`... rather than a new migration duplicating the same columns") — this proposal stays consistent with that finding rather than re-deriving a heavier design.
- **Capability A's free-text `sport` field** (`BettingSlipValidationRules.php:21`) is a natural future consumer of the same `SportRegistry` (constraining it to real, known sport keys instead of arbitrary text) — noted, not designed or scheduled here; this is `AO-MVP-005` Model B territory revisited from the Manual Builder side, and that document's own recommendation (structured Sport/Market only, post-MVP for Competition/Team/Fixture) is unaffected by this proposal.

---

## 5. Provider abstraction

Because `MarketEvidenceProvider` already takes a generic `competitionKey` string rather than a football-typed value, a second sport's provider is **a second implementation of the existing interface**, bound through `SportAdapter::evidenceProvider()` — zero change to the interface itself, zero change to `OddsApiProvider`. The only real new work is the binding layer (`SportRegistry`) and the discipline of resolving a provider through an adapter instead of the current direct dependency. A second bookmaker/data source for the *same* sport (a distinct question from a second sport) is unaffected by this proposal and remains `AO-MVP-005`'s existing "Bookmaker filtering... needs a second provider integration" finding, unresolved by this document either.

---

## 6. Capability interfaces / Builder architecture boundary

Today, `market-intelligence/builder.blade.php` and its Livewire component depend directly on `FootballMarketTaxonomyV1`, the config's football-only `allowed_competitions`, and (via DI) `OddsApiProvider`. The proposed seam: the Builder resolves a `SportAdapter` from `SportRegistry` (defaulting to `football`, the only registered adapter today) and calls `marketTaxonomy()`/`evidenceProvider()` through it instead of the concrete football classes. `PlanningBrief` gains an optional `sportKey` field (default `football`) so the construction pipeline threads sport through the request explicitly rather than assuming it implicitly. This is a dependency-substitution refactor inside the existing Builder — not a UI redesign, not a new interaction pattern, and therefore not itself subject to the Frontend Work Rule (no visible change results from Phase 1 alone).

## 7. Migration/adoption strategy — recommended: strangler fig, Phase 1 only proposed now

- **Phase 1 (this proposal's actual deliverable, if accepted):** introduce `SportAdapter`/`SportRegistry`, wrap the existing football code in `FootballSportAdapter` with **zero behaviour change** — the adapter's `evidenceProvider()`/`marketTaxonomy()` return the exact same `OddsApiProvider`/`FootballMarketTaxonomyV1` instances used today. Builder and `Construction/*` re-pointed to call through the adapter. Fully covered by the existing test suite (same inputs, same outputs, same classes underneath); no product-facing change; does not touch `MARKET_WIDE_PLANNER_ENABLED` or `MVP_SCOPE_LOCK.md`'s launch readiness in any way — it is a pure internal refactor, schedulable as ordinary Engineering work whenever convenient, not gated on anything else in this document.
- **Phase 2 (explicitly not proposed or authorised here):** a second real `SportAdapter` for an actual second sport, requiring its own Parser Office source-viability review (a genuinely new external data source) and its own Product Office commission — the Sport Selector UI, Mixed-Sport Accumulators, and every other gap-analysis item gated on "the sport-agnostic model" only become buildable once Phase 2 exists, and Phase 2 is deliberately not this document's scope.
- This directly satisfies `PO-MVP-004`'s standing requirement that the existing Builder remain the MVP v1.0 shipping foundation — Phase 1 changes nothing a customer can observe.

## 8. Relationship to `AO-MVP-005`'s two open blockers

`AO-MVP-005` named two blockers on its Model B: an unsent provider clarification letter (caching/attribution/derived-data terms) and no Parser Office source-viability review scoped to reference-data use. **Both blockers gate Phase 2 (a real second sport/provider), not Phase 1 (this proposal).** Phase 1 acquires nothing new, validates nothing new, and licenses nothing new — it wraps the existing, already-cleared `OddsApiProvider` integration in an interface. Neither blocker is cleared by this document, and neither should be read as cleared — they remain exactly as open as `AO-MVP-005` left them, and still gate Phase 2 specifically.

## 9. Recommended `ADR-014` (not written as Accepted)

**Title:** Sport-Agnostic Reference Data & Adapter Boundary

**Core decision, in `ADR-013`'s own concise style:** No code outside the adapter layer may reference `FootballMarketTaxonomyV1`, `OddsApiProvider`, or any other sport-specific class directly — all access to a sport's taxonomy, market definitions, or evidence provider goes through `SportAdapter`, resolved via `SportRegistry`. Reference data (fixtures/events) is sport-scoped via an explicit `sport_key` column, never inferred from competition-key format or provider identity. Adding a new sport requires, in order: (1) a Parser Office source-viability review of that sport's real evidence source, per `AO-MVP-005`'s existing precedent; (2) a new `SportAdapter` implementation; and requires no change to the Builder, the `Construction/*` pipeline, or the `SportAdapter` interface itself. This governs only the adapter/reference-data boundary — it does not touch `ADR-013`'s Capability-B-to-Planner handoff, which remains entirely unaffected downstream of this layer.

**Status if drafted:** Proposed, pending Product Office acceptance of this proposal — same pattern `AO-MVP-005` used for its own `ADR-014` recommendation. Confirmed directly against `docs/adr/ADR-INDEX.md`: `ADR-013` is the last entry currently recorded, so `ADR-014` is genuinely the next free number at time of writing.

## 10. Open questions / explicitly out of scope

- **Two-participant assumption** (`homeTeam`/`awayTeam` on `CanonicalFixture` and the fixtures table): does not generalize to multi-participant sports (motorsport grids, golf fields, tournament brackets). Flagged, not resolved — a real design question for whichever future work package proposes the first non-two-participant sport, not decided by adding `sport_key` alone.
- **`MarketFamily` enum extensibility**: whether a single shared enum grows cross-sport-general cases, or becomes sport-scoped per adapter. Not resolved here — Phase 1 doesn't require an answer since football is the only sport; Phase 2's design should answer it against a real second sport's actual markets, not speculatively.
- **Capability A's free-text `sport` field eventually consuming `SportRegistry`**: noted in §4 as a natural future connection, not scheduled or designed — stays `AO-MVP-005` territory.
- **Whether `Competition` needs a first-class entity/table**: the minimal, additive path (§4) is recommended for now; a full normalized entity remains the more complete long-term shape, deferred pending real second-provider need, consistent with `AO-MVP-005`'s own build-ahead-of-need caution.
- **Filament/Operations visibility into the Sport registry**: not addressed — out of scope for an Architecture-only proposal with one registered sport.
- **Evidence Quality/Correlation/Volatility definitions**: explicitly Data Science Lab's authority, per `PO-REVIEW-001` — this document names only the attachment point (§2, Intelligence Object), not the mathematics.
