| Field | Value |
|---|---|
| Commissioned By | `PO-U10-001` |

## 0. How To Read This Document

This document defines the architecture for a read-first, act-second internal support console. It does not implement anything. Per `PO-U10-001` §6/§7, Engineering implements only after this architecture is accepted, and Compliance Office reviews the privacy-sensitive elements named in §9 before that implementation proceeds — this document identifies exactly which pieces those are rather than assuming they're pre-cleared.

## 1. Executive Architectural Assessment

Most of what this programme asks for is **already available as a pure read model** over data this repository already persists — no new tables are required for customer search, customer overview, analysis visibility, Planner visibility, or Workspace visibility. Two genuinely new domain concepts are required: **Internal Notes** (`SupportNote`) and **Audit Logging** (`OperationsAuditLogEntry`) — neither exists today in any form. **Operational Diagnostics** is a partial case: basic session metadata (IP, user agent, last activity) already exists in Laravel's own `sessions` table (populated automatically by `SESSION_DRIVER=database`, already in use) and needs no new capture — but "application version" and "request identifiers" would require new instrumentation this document deliberately does not design (§8).

**No ADR amendment is required for the read-only visibility surfaces** — they are a direct, internal-facing application of `ADR-007`'s already-accepted principle (presentation reads persisted state, never recalculates, never mutates). **One new ADR is proposed** (§11) for the one genuinely new architectural boundary this programme introduces: that the Operations Console's authorization must never be implemented by modifying the customer-facing policies those same models already have.

## 2. Grounding — What Already Exists

- `User::is_internal` (boolean, migration `2026_07_23_021013`) already gates the entire Filament `/operations` panel via `User::canAccessPanel()`. No role/permission granularity exists beyond this single flag today.
- `app/Filament/Resources/LabsFeatures/` is the only existing Filament resource — a working, current convention to follow (`Resource` class + `Pages/`, `Schemas/`, `Tables/` subdirectories), not to redesign.
- The `sessions` table (Laravel's own scaffolding migration, in use since `SESSION_DRIVER=database`) already stores `user_id`, `ip_address`, `user_agent`, `last_activity` for every active session — populated automatically by the framework, not by any code this repository wrote. This is the existing source for basic diagnostic metadata (§8).
- `BettingSlip`, `SlipAnalysis`, `PlannerSession`, `PlannerSelection`, `PlannerRegenerationEvent`, `JournalEntry` all already exist, all already carry `user_id` (denormalized on the analysis/session/entry, direct on the slip), and all already have timestamps sufficient for a chronological timeline (§7).
- No audit-logging package or mechanism exists anywhere in this repository (`composer.json` checked directly) — Audit Logging (§6) is genuinely greenfield.
- No `SupportNote` or equivalent model exists — Internal Notes (§5) is genuinely greenfield.
- Every existing customer-facing policy (`BettingSlipPolicy`, `SlipAnalysisPolicy`, `PlannerSessionPolicy`, `JournalEntryPolicy`) scopes `view`/`update` strictly to `user_id` ownership, with no internal-user bypass of any kind today.

## 4. Authorization Architecture

The Operations Console is authorized **entirely independently** of the customer-facing policies. Each new Filament resource defines its own `canViewAny()`/`canView()` (Filament's own resource-level authorization, distinct from Eloquent Policies), gated on `auth()->user()->is_internal` — the same check `canAccessPanel()` already performs for panel entry, applied again at the resource level as defence in depth, not because panel-level gating is insufficient today.

**Read access model:** every Operations resource queries the existing models directly (`BettingSlip::query()`, `SlipAnalysis::query()`, etc.) **unscoped by any customer-facing policy** — an internal user views a specific customer's records by an explicit `where('user_id', $customer->id)` (or the customer's own relation), never by a policy check that could accidentally also apply to a customer-facing route. This is the mechanism that makes the "no modification to existing policies" constraint (§3) actually true in code, not just in intent.

**Open Question OQ-1** (§12): today, `is_internal` is a single, undifferentiated flag — any internal user who can access `/operations` at all can, under this architecture, see every customer's data. Whether support visibility should be gated more finely (e.g. a separate `can_view_customer_data` permission, distinct from Labs-feature-management access) is a genuine access-control question this document surfaces rather than resolves — Compliance Office's own review (`PO-U10-001` §8) is the natural place to answer it before implementation.

## 5. Domain Model — `SupportNote` (New)

| Column | Type | Notes |
|---|---|---|
| `id` | bigint | |
| `author_id` | FK → `users`, `restrictOnDelete()` | The internal staff member who wrote it — `restrictOnDelete()`, not `cascadeOnDelete()`, since a note's authorship is itself part of the audit trail (`PO-U10-001` §4's "operator" field) and must survive even if that staff account is later removed. |
| `customer_id` | FK → `users`, `cascadeOnDelete()` | The customer the note is about. Cascades: if a customer account is ever deleted, notes about a now-nonexistent customer serve no purpose. |
| `note` | text | Free text, staff-authored. |
| `created_at` / `updated_at` | timestamps | |

**Visibility:** never surfaced anywhere in the customer-facing product — enforced structurally by this model never being queried from any customer-facing Livewire/Volt component, and by its own Filament-resource-level authorization (§4) requiring `is_internal`.

**Lifecycle:** none — a `SupportNote` simply exists once created. Whether notes are ever editable/deletable by their own author is **Open Question OQ-2** (§12) — this document recommends notes be append-only (immutable once saved, matching the audit-trail spirit of `PO-U10-001` §4 more literally than an editable note would), but does not decide this unilaterally.

## 6. Domain Model — Audit Logging (New)

A single, new `OperationsAuditLogEntry` model — deliberately not a third-party package, per this repository's stated preference for Laravel conventions over new packages, and because the scope needed here (record who did what, to whom, when) is small enough not to justify one.

| Column | Type | Notes |
|---|---|---|
| `id` | bigint | |
| `operator_id` | FK → `users`, `restrictOnDelete()` | Same rationale as `SupportNote.author_id` — the audit trail must outlive the operator's own account. |
| `customer_id` | FK → `users`, nullable, `nullOnDelete()` | Nullable because not every privileged action necessarily targets one customer (e.g. a future bulk operation); `nullOnDelete()` rather than cascade, since the audit record of "an action occurred" should outlive the customer record itself being removed — deleting the customer must not silently erase the fact that they were once looked up or acted upon. |
| `action` | string | A fixed, enumerated set of action codes (e.g. `customer_viewed`, `analysis_viewed`, `planner_session_viewed`, `support_note_created`) — never free text, so the audit trail stays queryable and consistent. The exact catalogue is an implementation-time decision, not architected exhaustively here, mirroring how `ReasonCode`'s catalogue is maintained as a living but structured list. |
| `context` | json, nullable | Structured, non-sensitive metadata about the action (e.g. which `SlipAnalysis` id was viewed) — never free text, never a raw request dump. |
| `created_at` | timestamp only (no `updated_at`) | An audit entry is never updated after creation — enforced by the model declaring no `updated_at` column at all, not merely by convention. |

**What gets logged:** every read of a specific customer's data through the Operations Console (viewing their overview, an analysis, a Planner session, a Journal entry) and every write (creating a `SupportNote`) — matching `PO-U10-001` §4's "every privileged action" requirement read broadly (a support agent looking at a customer's private betting history is itself the privileged action being audited, not just note-writing). **Open Question OQ-3** (§12): whether *every single read* should generate its own audit row (high volume, complete) or only session-level "customer X was opened by operator Y at time Z" events (lower volume, still accountable) is a genuine architecture-versus-operations-cost tradeoff this document flags rather than resolves, since it affects storage growth and is properly informed by Compliance's own retention review (`PO-U10-001` §8).

## 7. Read Models — Customer Search, Overview, and Support Timeline

**Customer Search:** a query against `User::query()`, filterable by `name`/`email` (both already-existing, indexed-appropriate columns) — no new search infrastructure, no new index required beyond what a standard Filament table search already provides. "Username" and "internal identifier" in `PO-U10-001`'s own wording are read here as referring to `email`/`id` respectively — this product has no separate username field (confirmed against `User`'s own migrations) and no separate customer-facing identifier beyond the database `id`; **Open Question OQ-4** flags this reading for Product Office confirmation rather than assuming it silently.

**Customer Overview:** a single Filament resource page composing already-existing relations — `$customer->bettingSlips()->count()`, `$customer->slipAnalyses()->count()`, `$customer->plannerSessions()->count()`, `$customer->journalEntries()->count()`, plus `created_at` (registration) and the `sessions` table's own `last_activity` (last activity, keyed by `user_id`) and most recent `ip_address`/`user_agent` (basic diagnostics, §2). No new persistence.

**Support Timeline:** a merged, sorted collection built at read time from each already-existing model's own timestamp column (`User.created_at`, `SlipAnalysis.created_at`, `PlannerSession.created_at`/`PlannerRegenerationEvent.created_at`, `BettingSlip` export events via `PlannerSession.exported_betting_slip_id`, `JournalEntry.created_at`) — a query-composition concern, not a new table. This mirrors exactly how Planning History (`U-08.1` §5) was specified as a read model over existing data rather than a new persisted view.

**Analysis/Planner/Workspace Visibility:** each is a read-only Filament relation manager or nested resource page attached to the Customer resource, rendering the same underlying `SlipAnalysis`/`PlannerSession`/`PlannerSelection`/`PlannerRegenerationEvent`/`JournalEntry` records the customer-facing product already persists — never a duplicate copy, never a recalculation (`ADR-007`).

## 8. Operational Diagnostics — Partial Scope, Explicitly Bounded

**Already available, no new capture needed:** IP address, user agent, and last-activity timestamp, read directly from the existing `sessions` table joined on `user_id`.

**Explicitly not designed here:** "application version" and "request identifiers" would require new instrumentation (a version constant surfaced into a loggable place; a correlation-id middleware) that does not exist anywhere in this repository today. Building this is new engineering scope in its own right — this document names it as a real gap in what `PO-U10-001` §4 asked for, rather than silently omitting it or silently inventing a lightweight version of it. **Open Question OQ-5**: does Product Office want this closed now (a small, separate, low-risk addition) or deferred? Recommended: defer — session-level diagnostics (already free) cover the overwhelming majority of real support scenarios; request-level tracing is a genuine observability investment better scoped on its own.

## 9. Compliance Review Required Before Implementation (Explicit List, Per `PO-U10-001` §8)

- `SupportNote` content and retention (customer-identifiable free text, staff-authored, never customer-visible).
- `OperationsAuditLogEntry` retention period and the granularity decision in OQ-3.
- The IP address/user agent data already captured by the `sessions` table being surfaced into a new, internal-facing UI for the first time (the data already exists and is already retained; this changes who can see it, not what is collected).
- OQ-1 (whether `is_internal` alone is a sufficiently narrow permission for viewing any customer's private data).

## 10. Navigation Architecture

A new Filament navigation group, "Customer Support," sitting alongside the existing (ungrouped) `LabsFeatureResource` entry — a `CustomerResource` as the entry point (search + overview), with the Analysis/Planner/Workspace/Notes/Audit views reached as nested pages or relation managers on a specific customer record, never as independent top-level resources a support agent could browse without first selecting a customer. This structurally enforces "look at one customer at a time," consistent with the console's own support-workflow purpose.

## 11. Proposed ADR — Operations Console Independent Authorization Boundary

**Proposed decision:** internal-facing Operations Console resources are authorized independently of customer-facing Eloquent policies — never by adding an internal-user bypass branch to `BettingSlipPolicy`/`SlipAnalysisPolicy`/`PlannerSessionPolicy`/`JournalEntryPolicy`. This is a permanent constraint on all future internal tooling, not only this programme's own resources, since the risk it guards against (a customer-facing authorization regression introduced while building internal tooling) applies to any future internal-facing feature. Would stand as `ADR-011` once drafted and jointly accepted, following `ADR-007`/`008`/`009`/`010`'s own acceptance discipline — not self-accepted here, matching this document's own practice of proposing rather than deciding ADRs.

## 13. Risks Register

| Risk | Mitigation |
|---|---|
| Building internal tooling introduces a customer-facing authorization regression. | §4/§11's independent-authorization architecture exists specifically to prevent this — no shared code path between customer policies and Operations resources. |
| Audit log or Support Notes become a second, informal database of customer PII with looser controls than the primary product. | Both are named explicitly for Compliance review (§9) before implementation; neither is built by this document. |
| "Read-only" erodes over time as future small conveniences get added ad hoc (e.g. "just let support fix a typo in a slip name"). | §5 (Explicitly Out of Scope) is restated here as a standing constraint on all future Operations Console work, not only this initial build — any such addition is a new Product Office decision, never an Engineering judgement call. |

## 14. Dependency Assessment

`SupportNote` and `OperationsAuditLogEntry` have no dependency on each other or on any read-model work — all three (notes, audit log, read-only visibility) can be engineered independently or in parallel once accepted.

## 15. Sequencing Recommendation

Recommend read-only visibility (Customer Search/Overview/Analysis/Planner/Workspace views) first — it requires no new persistence and delivers the majority of `PO-U10-001`'s stated support value on its own. `SupportNote` and Audit Logging follow once Compliance's review (§9) resolves OQ-1–OQ-3.

## 16. Readiness Assessment

Read-only visibility is architecturally ready for implementation now. `SupportNote`/Audit Logging are architecturally specified but should wait on Compliance's review per `PO-U10-001` §8's own instruction, not proceed in parallel with it.

## Handover

Constitutional ownership returns to the Product Office for review. Per `PO-U10-001` §8, Compliance Office's review of §9's listed items is expected before Engineering implements `SupportNote`/Audit Logging/diagnostic surfacing — the read-only visibility surfaces (§7) carry no such dependency and could be commissioned to Engineering independently, at Product Office's discretion.
